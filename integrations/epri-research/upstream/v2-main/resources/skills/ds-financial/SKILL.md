# Financial Mode

Read `../report-authoring/SKILL.md` for the reader-first outline and visual hierarchy, then read `../financial-report-research/references/vibe-trading-research-sop.md` progressively when the request needs a multi-step report, user-facing progress, backtest diagnosis, valuation, risk analysis, or simulation assumptions. Load only the relevant sections: sections 1-3 for routing/evidence, section 4 for long-running research goals, section 5 for failures, sections 6-7 for report and calculation modules, and section 8 for the trading boundary. This is adapted guidance; the runtime route, finance contracts, receipts, and available tools in this repository remain authoritative.

1. Confirm the runtime prompt contains `DeepScientist Financial Mode`, the active skills contain `report-authoring`, `ds-financial`, `deepscientist-report-chart`, and the selected specialist skill, and the selected route tools plus `report_chart` are discoverable. Read the report-chart Skill before authoring a data chart. If anything is missing, report the runtime fault precisely; do not claim that a SOP was loaded, search guessed paths, or repeat equivalent preflights.
2. Read the runtime `Financial Task Route` block before any Project, finance, Evidence, or Artifact call. When it is `selected`, copy its exact contract id, version, hash, task kind, specialist, SOP reference, active-specialist list, and provider status; do not reclassify it or recompute the hash. When it is `ambiguous` or `unresolved`, infer one listed candidate from the user's request and use `routeSource=agent_selected`; do not ask the user to choose between factor and general financial research. Ask only for a missing business fact that materially changes the analysis, preferably as one short structured choice.
3. Treat specialist/provider availability as a terminal preflight only when no reviewable route remains. The bundled market-data provider is enabled and started automatically for a market-data route. If the selected specialist was explicitly disabled, point to “Settings → Capability Center → Modes → Financial Mode”. If the route reports `endpoint_missing`, report a local managed-runtime startup fault; the optional diagnostics are under “Settings → Capability Center → Modes → Financial Mode → Market data and simulation”. If one named `finance_*` call reports `provider_error`, connection failure, timeout, or `retry_exhausted`, record the exact gap once, skip that call after the adapter's bounded retry budget, and continue independent finance calls, user-provided data, or primary-source evidence. Publish a clearly labelled `partial` result when reviewable evidence remains; block only when no reviewable route remains. Never invent missing prices/rankings or use generic web prose as a silent substitute.
4. Read `references/publish-completion-contract.md`, `references/report-publication-example.md`, and `references/report-module-cookbook.md` only after the selected specialist and provider are available. For `finance.company-research.v1`, also read `references/company-research-report-map.md` as an optional reader-first map; it is not a second contract. For a bound or write-capable run, treat the authorized project as already created, call `project_workspace(action="status")` once before any financial tool, normally omit identity arguments, and retain its receipt. If the tool reports no binding or a mismatch despite that contract, report a runtime fault; do not create, initialize, reopen, migrate, or substitute a project. A retry envelope, Git repository, or initializer commit alone does not mean the task is a resume; use `intake-audit` only when meaningful prior finance results, artifacts, or research checkpoints exist. For an unbound read-only run, record the explicit `unbound_read_only` preflight gate. It may create conversation-scoped Evidence, Artifacts, cards, and a Science Report solely to render the answer, but must not write project files, Git, schedules, portfolios, or provider state.
5. Use `wq-alpha-research` only for a selected `finance.factor-research.v1` route. A company fundamental review, financial-statement summary, or company comparison remains a company/market-data route; it becomes factor research only when the user asks to discover, implement, validate, or backtest factors on time-aware panel data. Use `market-data-research` for the former and never substitute one specialist for an unavailable one. For a mixed market-to-factor request, publish the market observation before asking whether to create an `idea` factor candidate.
6. Use only the exact runtime tools and the selected SOP. A missing named tool is a single `blocked` gap, not permission to probe with shell commands, generic tool discovery, source searches, or previous session logs.
7. Scale the workflow to the request before calling tools: `explore` stops at mechanisms and candidate sketches, `validate` runs only the checks that answer the question, `compare` reuses one metric contract, `mine` delegates a bounded XAlpha/generic Team campaign, `export` is a local Viewer action, and `submit` is the one Lead-owned `factor_submit` handoff. Do not rebuild the old schema-guided search loop as per-round MCP calls. Worker count may increase exploration coverage, but it never creates a second canonical run. Keep every unavailable capability explicit and allow a useful `partial` handoff.
8. Keep the factor handoff separate from any later external workflow. `factor_submit` records the strongest candidate, role activity, real metrics, charts/tables, limitations, and next actions in one project-owned stream. Historical Portfolio/search files may be read for compatibility, but they are not required for a new run and must not block submission.
9. Use `research_evidence` and `science_artifact` for every Financial Report Mode task and whenever another selected terminal contract requires a report. Visual selection is a required decision, not a decorative afterthought: when verified structured values support comparison, trend, distribution, interval, drawdown, exposure, or scenario analysis, call `report_chart(action="render")` for one lead chart and/or materialize the smallest useful chart-card set. Aim for two to four total visuals only when they answer distinct questions; place them before long evidence and risk detail. If no meaningful visual data exists, pass only `payload.internalVisualWaiverReason` as private validation metadata and never expose that reason in report prose, cards, limitations, data gaps, evidence, or the final reply. Never fabricate points, pass arbitrary ECharts/HTML, or rebuild the same data as another chart. Treat finance tool `reportSuggestions` as candidate routes rather than required modules. Every Financial Report Mode run with reviewable output ends with exactly one `science_artifact(action="publish", displayIntent="open")`, including an allowed provider-degraded Partial Report; only a terminal preflight with no reviewable output and a monitor `no_change` run may finish without a new report. For a report, move in one direction: raw result envelope/receipt -> computed evidence -> selected visual/card drafts -> reader-first conclusion and limitations. Do not narrate tool chronology or force every cookbook module.
10. Keep `asOf`, timezone, currency, coverage, missing symbols, source revisions, and explicit Artifact/Evidence/Card references. Worker handoffs should name the inputs and Git commit that actually produced them; never expose credentials or unrelated private data. Preserve real zero values and distinguish missing data from `no_change`.
11. Never represent correlation as causality, a simulated portfolio as a real account, or a factor candidate as validated. Fundamental fields or a declared schema do not prove point-in-time correctness; keep that coverage `not_available` until announcement, revision, lag, and backfill checks exist. The current search may claim schema-guided macro mutation plus surrogate ranking, but not local Bayesian micro-optimization or multi-island evolution. Real trading is disabled.
12. After material file changes, call `project_workspace(action="checkpoint")` with an allowed stage, real verification, and the route that produced the work (`routeMode`: `explore`, `deepen`, `fuse`, `repair`, or `stop`) before composing the final completion manifest. Project initialization and presentation-only checkpoints are exempt; record `no_material_change` without committing when nothing material changed.
13. When publishing, call `science_artifact(action="status", payload.financeTaskContractId=...)` once after all conditionally required objects and any checkpoint exist, then follow its `financeCompletionGuide.manifestAuthoring` exactly. Copy complete finance-tool `.receipt` and platform-tool `.financeReceipt` objects directly from their outputs; never retype or repair a receipt hash, signature, id, or field. Emit the completion manifest at `science_artifact.payload.financeCompletion` and perform the terminal publish. The publish call must use either `payload.cardDrafts` or fully materialized `payload.cards`, never both. Missing required receipts, Git lineage, refs, report sections, or presentation cards means `partial` or `blocked`, never `completed`.

14. Keep the main conversation fast and readable: emit compact progress cards at material transitions, update existing cards by stable ids, keep the latest five live events visible, and lazy-load large tables/charts/files. Do not append provider envelopes or raw factor rows to the conversation. A report should lead with the current conclusion or blocker, then the most recent metric, then expandable details.

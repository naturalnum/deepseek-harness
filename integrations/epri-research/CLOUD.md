# Account-native Cloud integration

English | [中文](CLOUD.zh.md)

This remains the independent `deepscientist-harness-suite` package with research, Airalogy and workbench plugins. The Cloud adapter adds account-native integration; the original local profile and HTTP service remain separately available. Cloud mode starts no local research HTTP server, uses no global research token, and creates no additional login, Session, Agent or execution controller.

## Responsibilities

| Existing Cloud owners | Research package |
| --- | --- |
| Original authenticated Peer/AccountUse, native Session and approved Workspace/Preset | Research protocols, records, tasks, evidence, routes, reports and immutable execution-package fingerprints |
| Native userQuestions and exact-version human decisions | Existing scientific algorithms, question details and post-answer fingerprint/revision checks |
| Verified preallocated account storage, native FS, project mounts and quotas | One SQLite Store under the files-issued fixed `private/research-suite` directory, with native Session IDs |
| Original managed execution, confinement, command budgets and actual drain | Injectable engine/workflow, OCR and Git transports; existing workbench UI and account-scoped dynamic lab skills |
| Existing sidebar slots and account-bound Connection RPC | Immutable `/research/` assets and a scoped iframe message bridge; no secondary data HTTP transport |

The adapter requires the Host capability-inventory, Session/project, original-Peer and collected-output-release interfaces recorded in the repository's Cloud native patches. Optional Host peer dependencies must resolve to the exact active Host's package instances. Installing a second Harness does not satisfy this requirement.

## Profile composition

Mount `deepscientist-harness-suite/cloud-assets` in the shared Web root with explicit `requestTimeoutMs: 180000`. It declares the package's browser client through the original `clientModules` registry using its Loader tree's installation base, serves immutable assets and injects public addresses; `/research/api` and `/research/auth` do not exist in this mode. Account data always uses the authenticated native `cloudResearch/action` Remote with its actual Session resource. The shared Root needs the original `clientModules` provider; the assets entry's exported dependencies request it without additional settings. Unloading this entry withdraws its browser declaration, public configuration and asset route. Duplicate browser declarations are rejected by the original registry; do not separately declare the same Root browser package. This entry activates no research Host service.

Use [cordis.cloud.patch.yml](cordis.cloud.patch.yml) for the account graph. Register its complete `research-suite` declaration in Root's approved Preset catalog and make it selectable. Preserve the existing Standard declaration. The Cloud recipe also retains the original workbench and research/Airalogy plugin entries. This feature has no dependency on the separate MCP-management feature.

The Cloud example selects the original private `cordis:pe-account-instructions-session` entry and explicit finite source/snapshot limits. Root must retain its original prepared account/project instruction owner and align common tool options with its approved managed profile before approving the research declaration.

Custom skills inherit the existing account-managed provider on the original skills registry. The Cloud research Preset does not install another default filesystem provider, whose standalone defaults discover Host user roots. The independent scientific bundled and account-local published providers still use that same native registry.

The sample configuration specifies a 256 MiB SQLite page allowance, 8 MiB request/reply/input-result allowances, two pending workbench requests, 180-second observer/tool budgets, 4 KiB collected command output, and explicit Python/Git executable paths. Native FS operations need only cover the selected 64 KiB window and the original range-reply overhead. The original HTTP unary carrier separately needs the request/reply envelope allowance for the selected 8 MiB logical RPC limit; this is one bounded HTTP call, not chunked RPC. WebSocket ingress frame limits are independent. The result file is integrity checked; only its bounded receipt travels through collected stdout. No configuration value alone establishes engine or OCR readiness.

`maxOutputBytes` must not exceed the original Root's `commands.commandLimits.maxTailBytes` for either stdout or stderr. The sample selects 4096 bytes per stream. Python returns its small byte-count/hash receipt through stdout and the complete scientific JSON through the bounded FS result file. Git arguments and complete stdout/stderr use the same bounded input/result files instead of the native argv or tail capacity. A fixed configured Git executable runs below the managed Python process, inherits its process group and resource limits, and reads both pipes concurrently within `maxPayloadBytes`; oversized complete JSON fails explicitly. The original managed owner confirms the whole range, including hooks and helpers, before reporting success.

File transfers select `fileChunkBytes: 65536` and `maxConcurrentFileTransfers: 2`. Input is UTF-8 encoded, split into base64 files through original native FS writes, and checked against its exact byte count and SHA-256 by the same managed Python bootstrap before the original script receives JSON. Result, Git and presented-file reads use original `readByteRange`, exact lengths, before/after native versions and the result receipt hash. Each complete snapshot is bounded by the suite's own allowance; short, changed, cancelled or mismatched reads fail without reporting success. The transfer slot remains occupied until actual staging, command observation and collection return. No Cloud FS global limit or copy engine changes.

Cloud tools and workbench replies use the suite's HTTP JSON representation: undefined optional fields on plain records are omitted. Non-finite numbers, negative zero, functions, unsupported object types, accessors, cycles and incomplete arrays reject instead of being silently changed. `maxReplyBytes` bounds complete UTF-8 JSON, including the workbench tool envelope, before a successful result is published. A result failure after a Store write does not undo that write; read current state before retrying a mutation.

An 8 MiB input needs at most 171 staging parts; base64 staging plus two bounded scripts and one 8 MiB result needs at most 19,704,492 project bytes per transfer with the sample limits. The collector retains one result buffer plus one 64 KiB window, without a second full concatenation buffer. Two slots therefore retain at most 16 MiB of result byte buffers plus 128 KiB of windows; UTF-8/JSON conversion can additionally retain up to 32 MiB of decoded UTF-16 text across those slots. These are byte/string allowances, not a whole-process heap bound: original domain values, parsed objects, source skill resources and native FS reservations retain their own limits and ownership.

The startup loader is a UUID-named file written through the original bounded FS provider. Python receives generated relative basenames instead of inline loader source and repeated absolute project paths, preserving room for the complete original 4 KiB guardian configuration, file policy and skill-copy inventory. The loader restores absolute script/input/work/result paths and `EPRI_EXECUTION_ROOT`, removes the exact input parts after validation, and removes its loader/script/work directory in `finally`. Git removes its already compiled script and paired loader before invoking Git, creates no work directory, and writes its result only after Git exits. One account permits one Git transport at a time and rejects overlap before staging; user files with similar names remain visible to Git. Managed worktrees use the associated repository's Git-reported common metadata directory, within the same authorized project; external metadata is refused. Git ignores this metadata without changing user ignore rules. The result retains its original hash/range validation and managed removal. Cancellation, rejected admission or a killed process does not guarantee Python cleanup: staged files remain under original project quotas and unresolved execution remains owned by the original managed range; the Host does not bypass native FS permissions to remove them.

Resource preparation has separate finite concurrency, provider-count, file-count, total-byte, per-file and relative-path limits. The sample selects one concurrent preparation, 64 providers, 1024 files, 32 MiB total, 4 MiB per file and 256-byte relative paths. Bundled previews create no execution. Actual resource copying requires the original native `skill` invocation, original Agent/Workspace admission and the existing managed subprocess. Copies use current-project execution-world addresses, reject symlinks and escapes, preserve user edits, and return a complete source/copy manifest only after all batches succeed. Binary resources retain their bytes. Dynamic lab skills remain opaque, include reviewed evidence, and invalidate only this account's native registry immediately after publication, editing or withdrawal.

## Workbench execution behavior

Readonly metadata uses the existing native Remote. A workbench write, computation, CSV import, automatic record recalculation, OCR extraction or Git action submits a bounded, one-time request tied to the original authenticated Peer, account generation and Session. The native conversation records the operation, request ID and parameter hash. Its Agent calls `research_workbench_execute` with that ID; the tool reads the exact saved parameters and runs through the original native execution owner. The UI waits for the actual domain result, and existing execution-history reads expose progress. This adds a visible chat execution intent to button actions. It does not merely fill an input draft. Missing protocol versions and version conflicts retain the original `NOT_FOUND` / `CONFLICT` recovery decisions through native Remote errors and the existing iframe channel, so a fresh interactive example can create its immutable protocol; account refusals and other native failures retain their original codes.

The request cannot execute after expiry, logout, scope disposal or withdrawal. A missing model/tool response, cancellation or restart reports an unconfirmed operation; pending IDs are not automatically replayed after restart. Refresh the existing records/execution history before retrying with the original domain idempotency key. Actual command cleanup and output reservations remain owned until range and I/O settlement. Source engine terminal observations may be saved during owned cancellation cleanup; revoked requests cannot commit later human record changes.

Direct model-proposed approvals retain the original `userQuestions` flow and exact before/after version checks. Approval details show a generic version only when the reviewed operation has a revision or version; task opening shows its exact method version and source hash. A model cannot supply a human token or approve a different version. Published lab skills remain visible across conversations only within their own account. Git association is restricted to the original native Session project; managed research branches live under that project, never under a host-selected directory.

Long document-search source references wrap within narrow research sidebars, preserving the complete attachment reference.

Cold research conversations reuse the original native history opening snapshot for membership, header and Preset admission before and after the operation. The iterator closes at that snapshot, before native promotion; simply opening the workbench after restart does not create or resume an Agent. The original native prompt alone restores an Agent for execution.

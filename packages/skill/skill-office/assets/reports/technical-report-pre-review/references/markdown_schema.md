# Markdown中间稿规范

文件必须为 UTF-8。元数据使用简单的 YAML front matter；正文包含且仅包含专家1至专家5五个二级标题。每个专家区块内部只使用“审查意见”“回复”两个三级标题，不单列“总体评价”。

示例骨架：

    ---
    project_name: 电力人工智能基础大模型通用构建与训练方法研究
    lead_unit: 某单位
    invited: 5
    returned: 5
    approved: 5
    rejected: 0
    review_basis: 任务书；技术报告；通用科技报告审查依据
    ---

    # 前置审查意见中间稿

    ## 专家1
    审稿人类型：任务符合性与验收证据审稿人
    审查结论：同意通过（修改后）

    ### 审查意见
    1. 对照任务书规定的研究内容、考核指标和成果要求，报告已对主要技术路线和阶段成果形成系统描述，整体上能够对应项目任务主线；但关键量化指标的验收证据仍分散，部分指标仅见结论性表述，现有材料尚不足以形成完整的任务—指标—证据闭环，建议优先补齐关键指标的证据索引并统一总报告中的验收口径。
    2. 从成果与应用要求看，报告已列出……并说明……，能够支撑部分成果完成情况；但……与任务书中的应用要求尚未形成清晰对应，建议在总报告中增加成果、应用场景与任务条款的对应说明。
    3. 报告第X页给出了……，但尚缺……，建议……

    ### 回复
    （待项目组填写）

专家2至专家5采用相同结构。前面的一个或多个编号意见承担本专家视角下的总体判断，后续编号意见再下钻到具体问题；不得额外写“总体评价：”“综合评价：”“总体意见：”等标签。

## 解析约束

- front matter 必须包含 project_name、lead_unit、invited、returned、approved、rejected。
- 初审稿可增加 `review_stage: 初审中间稿`；纳入分报告后的最终版应增加 `review_stage: 盲审意见最终版`、`supplemental_reports` 和 `initial_draft`，值使用单行可读文本，便于现有解析器兼容。
- 数量字段必须是非负整数，且 approved + rejected = returned。
- 必须恰有5个专家区块，编号连续且不重复；不得新增独立的“总体评价”二级标题或第六名专家。
- 每个专家必须有审稿人类型、审查结论、审查意见和回复；专家区块内的三级标题顺序固定为“审查意见→回复”。不得新增“总体评价”“综合评价”“总体意见”等三级标题。
- 每位专家至少1条、至多4条编号意见；编号必须从 `1.` 开始连续递增，不在编号列表前插入无编号评语。
- 每位专家的编号意见中至少应有1条从本专家视角对任务书—报告总体对应、已有支撑和主要风险作综合判断。总体层面意见不单独设数量限制：如存在多个相互独立的宏观判断，可连续占用前面的多个编号；其数量仍受该专家1至4条总意见数约束。
- 总体层面意见可以综合多个任务条款、章节或证据，不强制定位到单一页码；具体问题意见应尽量给出页码、章节、图表编号或可搜索原句，并明确事实、依据、影响和修改动作。
- 正式意见中不要通过“总体评价：”“总体意见：”“综合评价：”等文字显式标识哪一条属于总体层面；通过内容本身体现由总体到具体的层次。
- 回复可以包含多条编号内容；没有真实回复时只能写“（待项目组填写）”。
- 审稿人类型不会写入Word，以保持原表格式；其用途是保存评审视角和便于复核。
- Word不新增总体评价栏、新表格行或独立标签；脚本只按Markdown中的编号顺序写入每名专家原有单元格，因此专家意见在Word中直接从“1.”开始。
- 盲审意见最终版可在第一个专家区块之前增加三级标题“补充审查变更记录”及表格，但二级标题仍必须且只能是专家1至专家5；不得把变更记录解析成第六名专家。

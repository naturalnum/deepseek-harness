# 课题角色、研究内容小点、章内核心研究小点与考核指标全量覆盖规则

本文件约束从任务书、实施方案、预期目标、进度计划、考核要求和用户补充材料中提取当前报告范围内的研究内容，并将其稳定映射到第一章1.3.1“主要研究内容”、第一章1.2“国内外研究现状”、技术章节、验证证据和摘要。

## 1. 先区分课题角色

任务材料中的课题必须按原始顺序登记。前序课题标记为 `technical-research`，最后一个课题固定标记为 `engineering-implementation`，通常承担系统研发、平台实现、集成部署、示范应用或工程验证。每个来源研究内容小点、预期目标、进度事项和考核事项都必须登记 `parent_task_id`，并继承所属课题角色。

任何来源事项除匹配研究内容小点外，还必须匹配所属课题。其他课题内容不得因主题相近、可以补足篇幅或技术上可复用而进入当前章。

## 2. 先确定当前报告范围

任务材料可能同时包含多个课题、专题、承担单位或成果包。建立映射前，必须将事项分为：

- `in-scope`：属于当前报告研究范围；
- `shared-approved`：确属多个研究内容共同需要，且经用户确认可共用；
- `excluded-other-task`：属于其他课题、专题或报告范围；
- `administrative`：人员、经费、组织、节点管理等非技术事项。

只有 `in-scope` 和经确认的 `shared-approved` 内容可以进入正文。`excluded-other-task` 不得通过改名、概括或并列压缩进入标题、正文、公式、图表、实验和结论。

## 3. 区分课题、来源研究内容小点与章内研究小点

先读取 `task_book_scope`，再提取任务材料中的课题、一级研究内容和来源研究内容小点。

总报告按课题设置一级技术章节：

```text
课题原始名称与顺序
→ 课题内全部来源研究内容小点
→ 必要名词化章名
→ 一个技术章节
```

具体课题报告继续按来源研究内容小点设置：

```text
一级研究内容
→ 来源研究内容小点原文
→ 小点原始顺序
→ 必要名词化章名
→ 一个技术章节
```

每个技术章内部再拆解为章内核心研究小点：

```text
来源研究内容小点
+ 对应预期目标
+ 对应进度计划技术
+ 对应考核要求
→ 章内研究小点1（X.1）
→ 章内研究小点2（X.2）
→ 章内研究小点3（X.3）
```

必须区分层级：总报告由课题决定一级技术章，具体课题报告由来源研究内容小点决定一级技术章；章内研究小点始终决定该章的核心二级标题。内部映射必须同时保留课题和研究点关系。

## 4. 技术章数量和顺序

总报告：

- 有几个课题就设置几个技术章；
- 技术章顺序与课题原始顺序一致；
- 一个课题只对应一个技术章；
- 同一课题下的多个来源小点归入该章，不得各自另设一级章。

具体课题报告：

- 有几个来源研究内容小点就设置几个技术章；
- 技术章顺序与小点原始顺序一致；
- 一个来源小点只对应一个技术章；
- 不得合并或拆分来源小点；
- 技术章从第2章开始编号，因为国内外研究现状已并入第一章。

## 5. 技术章标题按课题角色整理

章标题以当前映射单位的来源标题为唯一依据：总报告使用课题名称或一级研究内容，具体课题报告使用来源小点原文。

允许：

- 删除开头的“研究、开展、研发、构建、建立、提出、实现”等任务动作词；
- 调整少量语序；
- 技术研究课题在原文和已确认方案已明确实际技术时，标题落到“技术、方法、算法、模型”等技术中心词；不得用中心词机械包装“机制、建模、体系、定义”等任务性概念；
- 工程实现课题可补足“系统、平台、架构、模块、接口、部署、集成、应用”等工程中心词；
- 统一术语和缩写。

禁止：

- 根据问题分析另行生成扩写标题；
- 增加原文没有的电力对象、人工智能方法或技术作用；
- 在技术研究课题的一级章标题中把“机制、建模、体系、定义”保留为独立命题、中心名词或落脚点，或通过机械增加“技术/方法/算法/模型”改名；
- 增加能力、指标、结果、应用价值或评价词；
- 将进度计划中的多项技术全部堆入一级标题；
- 混入其他课题内容。

## 6. 全文固定章节落点

### 第一章“项目概述”

- `1.1 项目背景与研究意义`：下设`1.1.1 项目研究背景`与`1.1.2 项目研究意义`；
- `1.2 国内外研究现状`：下设`1.2.1 国外研究现状`与`1.2.2 国内研究现状`；
- `1.3 主要研究内容及思路`：下设`1.3.1 主要研究内容`与`1.3.2 研究思路`。

其中`1.3.1 主要研究内容`必须与技术规划书、任务书或等效材料中的当前报告范围研究内容逐项对应，并作适度展开说明；`1.3.2 研究思路`说明总体研究逻辑和技术关系。

### 第2章起技术章节

技术章一级标题之后先直接写无标题章首导入正文，合并原概述和总体技术路线/架构功能，不设置对应二级标题。随后固定为：

```text
X.1 章内研究小点一
X.2 章内研究小点二
X.3 章内研究小点三
X.4 本章小结（默认）
```

问题、背景、研究意义和总体技术路线优先进入章首无标题导入；主要进度技术分配到X.1—X.N；支撑算法、组件和处理步骤进入相应三级标题；各章自身技术要求的能力含义、条件、结果和判定默认融入X.1—X.N或其三级标题，任务书硬指标统一由最后技术章集中承接。`non-evaluation` 主题不得增加独立验证/评估/测试二级节，本章小结紧随最后一个核心研究点；只有 `evaluation-related` 主题且存在大量成体系数据或用户明确要求时，才可在核心研究点后增加独立评估/验证二级节，并将本章小结顺延。

章首无标题导入继续按本文件既有篇幅规则规划；本章小结的篇幅与内容要求统一执行 `references/chapter-summary.md`。


## 7. 章内核心研究小点的拆解

每个技术章默认形成3个核心二级标题；只有预期目标、进度技术点或关键研究事项确实过多且无法合理归并时，才最小扩展到4—5个。拆解时依次读取：

1. 当前技术章来源范围：总报告为所属课题及其全部研究内容小点，具体课题报告为当前来源研究内容小点原文；
2. 预期目标；
3. 进度计划中的技术事项；
4. 考核要求中的功能、性能和测试事项；
5. 用户已确认的补充材料。

核心小点应互不重复并共同构成完整技术链。默认优先归并为3个，不得为了凑足数量引入其他课题内容；扩展到4—5个时必须逐项说明哪个预期目标/进度技术点无法合理归并，也不得把纯管理节点或单一考核数字作为独立小点。

技术链必须有方向性。目录内部同时登记全部核心小点的共同章级问题、chain_order、chain_role、前序输入与后序输出。X.1—X.N每个标题都应使用一个足够具体的计算机/人工智能技术名称；RAG、图神经网络、Transformer、强化学习、大模型等仅表示技术族，不视为足够具体，必须进一步写明具体变体、结构、机制、约束或组合方式。若细化方法由模型在已确认研究边界内提出而非来源已有，应标记 `model_suggested` 并在目录确认时一并让用户确认。

每个章内研究小点必须登记：

- `research_subpoint_index`；
- `derivation_basis`；
- `source_item_ids`；
- `technical_object`、`technical_method`、`technical_role`；
- `power_element`、`specific_computing_technology`、`technology_specificity_basis`、`technology_origin`；
- `shared_chapter_question`、`chain_order`、`chain_role`、`depends_on_previous`、`handoff_from_previous`、`output_to_next`；
- 对应三级标题；
- 对应内部技术要求、正文融入位置和可选证据位置。

## 8. 第一章国内外研究现状与技术章对应

第一章1.2的文献检索主题、技术进展和技术缺口应与报告范围内研究内容保持可追溯关系；总报告按课题研究主题组织，具体课题报告按研究内容小点组织。1.2.1国外研究现状与1.2.2国内研究现状采用一致的研究主题口径，但不要求三级标题机械复制技术章标题。1.3.1“主要研究内容”必须与技术规划书、任务书或等效技术文件中的研究内容逐项对应，并在不增加研究边界的前提下对每项内容稍作展开说明。

每个类别按以下逻辑组织：

```text
对应来源研究内容小点
→ 国内或国外代表性路线
→ 已经解决的问题
→ 现存不足
→ 当前技术章需要处理的技术问题
```

不得把其他课题的研究内容作为第二章技术类别。

## 9. 进度计划、预期目标和考核指标全量覆盖

从预期目标、进度计划和考核要求中提取：

- 研究、研发、构建、实现和集成事项；
- 数据、模型、算法、系统和平台事项；
- 仿真、实验、测试、示范和应用事项；
- 功能、性能、时延、精度、可靠性和安全指标；
- 测试条件、判定标准和能力边界。

映射规则：

- 主要方法、模型、算法、知识构建或工程实现技术进入核心二级标题；
- 支撑技术进入更具体的三级标题；
- 每项内部技术性考核事项必须进入所属技术章X.1—X.N正文或其三级标题，不能只存在于内部矩阵、第一章、总结章或附录；
- 正文至少说明技术能力、电力对象或业务条件、计算或判定方法、单位、阈值、数据或工况条件、证据状态和能力边界；
- 对 REAL_PROJECT_EVIDENCE，有真实结果时给出结果、比较对象和条件；没有结果时只能写成设计目标、验证方案或明确占位，不能写成已达到。该限制不禁止为用户生成明确标记的 REFERENCE_EXPERIMENT、模拟数据和参考结果分析；
- 正式正文不得出现“任务书”“考核指标”“考核要求”“考核细则”“规定指标”或内部编号。

每项内部事项必须登记：

- `assessment_item_id`；
- `planned_section`；
- `content_form`；
- `prose_realization`；
- `source_identity_hidden=true`；
- `evidence_status`；
- `confirmed_location`；
- `evidence_section`（可选）。

## 10. 电力标题语义逐项追溯

X.1、X.2、X.3每个核心二级标题都必须能够从当前研究内容追溯到明确的电力对象、业务场景或运行约束，并在标题中直接体现该对象/约束、具体计算技术和技术作用。

## 11. 章节计划必填映射

每个技术章计划必须记录：

- 所属一级研究内容编号；
- 所属课题编号、课题顺序与课题角色；
- 当前映射单位编号、来源标题和原始顺序；总报告另列课题内全部来源研究内容小点；
- 名词化章标题和处理说明；
- 第二章对应三级类别；
- 章内核心研究小点的标题、序号、来源依据和技术职责；
- 每个小点对应的预期目标、进度技术和考核事项；
- 当前章范围内的内部技术要求隐性覆盖计划；
- 每项内部事项的X.1—X.N正文融入位置、可选证据位置、正文表述方式、来源身份隐藏状态和证据状态；
- 其他课题排除清单。

## 12. 每章生成前后

生成前：

1. 读取当前映射单位的来源标题和名词化章名：总报告读取课题，具体课题报告读取来源小点；
2. 确认本章只使用当前技术章范围相关的 `in-scope` 与 `shared-approved` 事项；
3. 确认一级章标题后直接规划无标题章首导入正文，并覆盖背景与意义、研究主题、概括性技术路线/架构和适合的图示；
4. 确认X.1、X.2、X.3且仅有章内核心研究小点；
5. 检查三个小点覆盖当前章预期目标和主要进度技术；
6. 检查所有内部技术要求均有X.1—X.N正文融入位置，并标记来源身份隐藏；
7. 检查三个核心标题均为完整的电力对象—具体技术—作用表达；
8. 检查三级标题比上位标题更具体；
9. 技术研究课题标题检查任务性概念是否被误作独立命题、中心名词或落脚点。

生成后：

1. 更新每项来源事项和内部技术要求的覆盖状态及正文位置；
2. 检查X.1—X.N均已实质展开；
3. 检查技术能力、条件、单位、目标、证据状态和边界是否完整，且来源身份已隐藏；
4. 检查是否遗漏进度技术或内部技术要求；
5. 检查是否混入其他课题；
6. 检查每个核心标题均可追溯并直接体现电力对象/约束、具体计算技术和技术作用；
7. 更新摘要证据包。

## 13. 覆盖状态

技术事项使用：

- `unmapped`；
- `planned`；
- `drafted`；
- `confirmed`；
- `covered-by-appendix`；
- `not-applicable`。

考核事项还必须登记 `assessment_kind=quantitative|qualitative|mixed`。定量事项需要实际值/范围/相对结果；定性事项也必须在章节确认后登记 `result_realization`，写明已形成的能力、功能、成果状态、适用性或工程效果，不能因无数值阈值而只保留要求原文。摘要阶段按此字段逐项形成 `task_book_assessment_results`。

考核指标额外使用证据状态：

- `target-only`；
- `test-designed`；
- `evidence-partial`；
- `evidence-confirmed`；
- `not-applicable`。

最终组装前，所有范围内技术事项必须为 `confirmed`、`covered-by-appendix` 或有充分理由的 `not-applicable`。内部技术性考核事项必须在所属技术章X.1—X.N正文中具有确认位置，且正文表述不得暴露任务书、考核指标、考核要求、考核细则、规定指标或内部编号，不能只标记为附录覆盖。


## 10. 预期目标、进度与考核技术词的标题级追溯

对每个技术章，除维护来源事项覆盖状态外，还必须维护 `heading_source_term_plan`。从 `expected-output`（预期目标/预期技术能力）、`schedule-plan`（课题进度计划及对应课题区域技术点）和 `assessment-requirement` 中提取关键且有实际含义的技术词。覆盖面较广、能够概括一个研究分支的词标记为 `broad` 并直接进入X.1—X.N二级标题；覆盖面较窄、仅指向具体结构、机制、算法变体、局部约束或局部能力的词标记为 `narrow` 并直接进入相应三级标题。关键技术词应分散到既有技术链中；先尝试在默认3个核心二级标题及其三级标题内合理归并，只有确实无法归并的独立预期目标/进度技术点才允许最小扩展到第4或第5个核心二级标题。

`non-evaluation` 主题中，来源出现“验证、评估、测试、验收、实验”等字样时不得把这些动作词搬进二三级标题；必须追溯其背后的技术含义，例如精度、时延、可靠性、鲁棒性、工况边界、接口适配或联调能力，再选择有实际意义的技术词进入标题。单纯存在这些来源事项不能改变 `report_theme_type`。


## 11. 目录阶段可选技术追溯

每个技术章在正式目录之外维护 `technology_option_sets`。来源未唯一锁定技术路线时，每个核心二级研究点给出2—3个同问题、同作用、同章节边界的候选技术，并记录中文技术签名、关键机制、适配理由、来源状态和唯一推荐项；来源明确唯一路线时使用 `source_locked=true` 且只保留1个来源技术。候选技术是用户确认目录时的伴随选择，不是正式标题，也不能用于把后续章节职责提前引入当前章。

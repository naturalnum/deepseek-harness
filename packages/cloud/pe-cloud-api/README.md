# @deepseek-ai/dsh-pe-cloud-api

English | [中文](README.zh.md)

## Summary

Choose exactly which native RPCs, logical streams, Fetch routes, and settings fields a cloud recipe may expose. Unknown operations remain closed, and a changed native inventory revokes its prior audit. Shared guards run before native Session delegation and actual model dispatch. Account mounting refuses incomplete runtime, project, and configuration-save integration.

Trusted account plugins can call `sessionProject(actualSession)` to reuse Runtime's original Session, Workspace, membership and Preset checks. It returns the registered native Workspace, creates no Session or execution scope, and rejects when the original policy callback or account admission is unavailable.

## Use this package

Mount the root entry in a deployment-owned composition; account mounting requires the complete trusted integration.

### When to choose it

Use this package to enforce reviewed cloud exposure while retaining native Session DTOs and business operations. Authentication, owner selection, project filesystem verification, and account readiness remain prerequisites.

Trusted account plugins can register their own Remote inventory with `CloudAccountApi.registerCapabilityInventory(namespace, inspect)`. The first audit captures the registering fiber's active service, checks every method through the original Gateway and verifies Session resources for account-session rows. Registration and withdrawal revoke the preceding audit; dispatch rechecks the same contribution. The deployment must still approve each exact endpoint, handler and guard. This registration adds neither Fetch routes nor a transport or persistence owner.

### Minimal configuration

The [executed Loader fixture](tests/fixtures/root.cordis.yml) shows the root configuration with empty lists, which expose no operations. A product composition selects the package's `/root` and `/account` entries; the account entry rejects mounting until its required integration exists.

## Understand the implementation

Cloud deployments requiring persisted titles in cold conversation lists compose `@deepseek-ai/dsh-session-projection-cache` with the same account's `sessions`, `sessionProjections` and `storageDomain` providers. Use the native `writeEveryEvents: 200` and `writeIntervalMs: 5000` configuration and retain that entry in the deployment's Runtime `requiredEntryIds`. The native list reads checkpoints without opening conversation bodies; writes are fail-soft, so a failed write leaves a stale or absent hint rather than changing the authoritative title. Existing uncached Sessions acquire a checkpoint through their normal native resume/write/disposal lifecycle; installing the cache does not scan old logs, and read observations containing uncommitted recovery events must not be published as checkpoints. This derived cache remains inside the account's existing private storage and quota; no new storage owner or title generator is installed.

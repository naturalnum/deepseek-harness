# Office image handoff

English | [中文](README.zh.md)

These offline tools verify the retained 251-file v5 Office context and preserve every original resource byte. They do not invoke Docker, change resources or execute an Office image. Historical staged CLI checks remain separate from acceptance of the actual issued account. The current integration policy allows reviewed necessary small patches; the earlier strict upstream migration and implicit 4 GiB free-space proposal are superseded.

`prepare_context.py` preserves the original v5 recipe for historical comparison. Its `--required-builder-free-bytes` input must come from an explicit reviewed peak model; there is no implicit 4 GiB free-space admission. A successful context preparation never admits production import. Only the sole runtime owner may build, import, change the approved task-only infrastructure envelope or select production.

`materialize_v6.py --context <v5-directory> --manifest <v5-manifest.json> --wheelhouse <retained-wheel-directory> --wheel-manifest <measured-wheel-manifest.json> --output <new-owned-directory>` writes a deterministic `context-v6.tar` and `manifest-v6.json`. Use `--owner-inputs <original-directory>` and `--stage1-inputs <actual-stage1-directory>` together for a buildable input set; supplying only one is rejected. With neither, it produces a non-buildable template. The owner directory must contain `base-dpkg.raw`, `base-dpkg.json`, `apt-plan.raw` and `apt-plan.json`. Both JSON records require `baseImage` equal to the exact reviewed c756 image, `architecture: arm64`, `observationKind: actual-readonly-owner-observation` and the original raw file's `rawEvidenceSha256`. Base `packages` and plan `newOrChangedPackages` contain complete `{name, version}` records; `requestedPackages` must retain every original direct apt dependency. Raw base lines use `dpkg-query -W -f '${db:Status-Status}\t${Package}\t${Version}\n'`; raw plan is the original `LC_ALL=C apt-get -s --no-install-recommends install` output for the full requested list. Obtain both from c756 in the same controlled owner observation. The stage-one directory contains the exact reviewed `ACTUAL-STAGE1-PLAN.json`, `APT-STAGE1-SIMULATION.raw` and `APT-STAGE1-SELECTED-METADATA.raw`. Its pinned plan fingerprint is `e5a58884652af1dc840d0f37fedabd8da09edb85901ff4e3001052eb75e7d816`. It selects 192 mutations and an intermediate map of 287 packages; the remaining 59 mutations must reproduce the original complete map of 345 packages. The earlier static 193/58 estimate is superseded. Each phase verifies its complete starting map, repeats simulation against refreshed indexes, rejects downgrades or unplanned changes, installs exact versions, and verifies its complete resulting map. The manifest records each expected map fingerprint.

The default archive includes the complete original 28 hash-locked ARM64 wheels. Its compressed wheel COPY layer remains in the final legacy image even after cleanup and must be counted. Optional `--url-report <pip-dry-run-report.json>` instead requires exactly the same 28 wheel filenames and hashes with official `https://files.pythonhosted.org/` archive URLs. It produces a small context and installs those direct URLs with `--no-index --require-hashes --no-cache-dir --no-compile`; there is no alternate dependency resolution, BuildKit or second daemon. The retained offline wheels remain audit evidence. Without the URL report, a multi-platform wheel filename is shortened to one already declared ARM64-compatible platform tag for USTAR; its archive bytes and hash remain unchanged.

`Dockerfile.v6` retains c756 and uses three stages supported by the original legacy builder. `office-system` installs the actual 192-package Office/graphics/font mutation set using `apt-office`; `office-apt` adds the exact remaining 59-package set using `apt-tex`; `office-complete` adds Python, fonts, the runtime manifest and final permissions in one subsequent RUN without chmod of the apt trees. This separates the working/commit overlaps while preserving the same final 345 package versions. Assets are copied once with modes already frozen, verified without chmod, and exposed at both `/opt/dsh/skills/office` and `/opt/dsh/skills/reports` through an in-image symlink. Already read-only files are not chmodded again. No package, template, license, font family, Python dependency or Native resource byte is removed. The custom `FONTCONFIG_FILE` is unset during both apt phases and set only after the font configuration exists; apt triggers use system configuration.

The owner must review each target separately. First use `docker build --target office-system --build-arg BASE_IMAGE=sha256:<exact-reviewed-c756-digest> -f packages/cloud/pe-opensandbox/runtime/office-completion/Dockerfile.v6 -t <owned-system-tag> - < context-v6.tar`. Only after its actual layer, package, generated-file, memory, inode, commit and cleanup receipts pass review may the owner build the exact same frozen context with `--target office-apt` and an owned apt tag, reusing the normal legacy cache. A cache miss that reruns an earlier phase requires its own current admission; do not automatically approve it. The `office-complete` target requires another separate review. Intermediate images must never be selected for a user account. Source preparation and the prior single-APT admission do not authorize any new physical target.

Each apt RUN stops after package validation and cache cleanup at its own finite 900-second commit checkpoint. The files are `/opt/office-build/apt-office-commit-request.json` and `apt-office-commit-approval.json` for the first phase, and `apt-tex-commit-request.json` and `apt-tex-commit-approval.json` for the second. Requests contain the fixed phase, a fresh request ID, installer fingerprint, actual/expected package-map fingerprints and expected count. Approval must contain exactly `{"requestId":"<live-id>","phase":"<matching-phase>","expectedPackageMapSha256":"<reviewed-map-hash>","decision":"approve"}`. The first layer's approval cannot release the second phase. The sole runtime owner must identify the exact owned build container and verify the request against the frozen manifest, actual upper allocation, context/temporary allocation and remaining commit allowance plus 256 MiB store reserve and 512 MiB memory reserve. The helper cannot observe Host upper directories and does not certify those physical measurements. A stale, wrong-phase or wrong-map approval, refusal or timeout fails the RUN before successful commit; failure does not prove resource release, which the owner must audit physically.

The user has approved only the task backend store ceiling of 4 GiB and its parent memory ceiling of 8 GiB. This is not proof that the build fits, and tenant quotas remain unchanged. The model must include existing layers, apt archives and generated files, Python/venv files, compressed wheel retention when applicable, context extraction, working/committed layer overlap, metadata and at least the reviewed reserve. Missing driver/temporary-path/apt post-install measurements do not count as available capacity. External build success does not establish original-store import capacity. Do not start a known-insufficient build, prune unrelated resources, resize beyond the approved envelope, mount Host dependencies or install dependencies in a running Guest.

Run the offline controls with `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s . -p 'test_*.py'`. Actual qualification must retain original guest security fields, tenant limits and current/rollback data, verify the original SDK and account environment despite Native `--clearenv`, and complete all 13 skill/model tasks, complete resource hashes, cancellation and document visual checks before enabling invocation. A frozen archive and offline checks do not establish Office execution completion.

# Native integration maintenance

English | [中文](native-patches.zh.md)

This reference separates the seven Cloud packages from the native code they consume. It adds no runtime component. The comparison base is `master`, the local native baseline used for this fork's audit; it is not a claim that this is the latest upstream release. Choose the intended upstream revision separately before upgrading.

## Ownership

Cloud packages own account identity, owner routing, tenant policy, storage admission, execution binding and browser revocation. Native DSH owns Agent/Session state, dispatch, configuration application, filesystem primitives, Shell consumers and generic UI. A native callback performs its check at the actual commit or release point; an HTTP precheck cannot replace that check after an await.

Root recipe sealing performs the full native plan validation. Its admission checks use the original plan's constant-time Entry and Fiber mutation-version and retained identity check, retain the provider and health audits, and revoke on a direct native Fiber update before its update waterfall continues. The Fiber revision also detects an attempted update rejected before the waterfall. The version check alone is not a configuration or readiness proof; it tracks Native update APIs and does not detect direct mutation of trusted Host objects.

Generic fixes remain native patches: UTF-8 and complete-frame bounds, cancellation and close results, bounded byte-range previews, [completed-answer file links](../client/ui-primitives/README.md#rendering-agent-output), upload receipts, configuration redaction, width geometry and activation judgment. Moving their engines into Cloud would duplicate native functionality. Keep their owning tests and evaluate them as separate upstream contributions.

The native file tree accepts a prepared `workspaceFileManagement` face; selection, native pickers and editable folder nodes remain in `ui-sidebar-files`. The native upload owner accepts an optional workspace destination separately from attachment bytes and supports a workspace-only stream without retaining a prompt receipt. Its browser completion event refreshes trees whose Cloud backend cannot watch directories. The Connection bridge fences cancelled body reads, flushes an early response before destroying its unread request, and joins original destruction without draining the remaining body. The Cloud adapter registers streaming attachment responses on the existing Connection Fetch registry, and its files owner extends the existing staging companion with versioned workspace publication; no alternate upload, download or account filesystem owner is introduced.

The optional `conversation.hero.header` position preserves the native blank-session welcome by default; Cloud fills it with an empty occupant. Workspace selection, draft identity and the resident composer remain native.

The native composer checks the attachment provider's projected accepted image types before starting a selected file batch. An empty list keeps inline image intake closed and shows localized feedback; the Cloud attachment provider publishes that empty list to match its existing prompt and command policy. Native providers retain their accepted types and file intake.

Cloud account composition reuses the public Native Cordis inspection registry and first-party Host providers through its fixed private runtime builtin. It does not activate the dynamic plugin runner. Standard delegation consumes the original Native model-selection settings service with its disabled defaults; these dependencies do not change the four Native preset declarations.

Native `FileSystem.supportsTextEdit` declares whether the provider implements text editing; Native ToolFS omits `edit` when the Cloud provider returns false, even for an existing preset that enables it. The default remains true for existing providers. This is capability disclosure only: Cloud does not implement atomic edit, and write authorization, version checks, and settlement are unchanged.

Native `FileSystem.scopeRoot` provides optional caller-scoped discovery metadata. The Cloud filesystem returns its original guarded Workspace target; Native agent-instructions stops project-marker discovery at that boundary and preserves failures. Unbounded Native providers keep their existing search, and all filesystem authorization remains with the original provider.

Native `skill-filesystem.includeDefaultUserRoots` allows a deployment to omit default user skill roots when default roots are enabled. Its default is true, preserving Native discovery; an explicit false leaves project and explicitly configured roots available. Cloud profiles must opt in when host user roots lie outside the authorized account scope.

Native bundled skill providers accept optional deployment invocation ceilings: `skill-office.invocation` and `skill-filesystem.bundledInvocation`. Cloud can expose complete immutable packages for inspection and download while withholding model and user invocation until the execution environment is qualified. The filesystem ceiling cannot enable source-disabled invocation or affect other roots; omission preserves Native behavior. Original skill consumers enforce invocation policy, and package bytes remain unchanged.

Gateway `inspectInvocation` exposes its existing strict/SRC resolver as a readonly Host inspection for account capability auditing. It requires an active calling fiber and performs no lookup, authorization or business invocation; normal dispatch retains every original check.

Native [file discovery](../fs/tool-fs-search/src/glob.ts) groups the six VCS names into two exclusion patterns, preserving directory pruning and exclusion when a search starts at or inside VCS metadata. The complete invocation uses 9 argv entries, or 11 with an explicit path, within the original 16-entry Cloud command limit. Execution, output capture and sorting remain Native.

Native [theme settings](../client/ui-theme/README.md) project the original Host write outcome separately from the palette preview. The Appearance row disables choices while loading or saving and after an unconfirmed write; only Host acceptance reports saved. Native settings ordering, persistence and cancellation remain unchanged; refreshing can still cancel an unacknowledged write.

## Upgrade procedure

1. Record the current clean source revision, deployment revision, chosen upstream revision and trusted configuration before changing anything. Source tests and an old running release are different evidence.
2. Inspect `git diff --stat <base> HEAD` and the ownership table. Keep Cloud policy in its package. Remove a native patch only when an equivalent public native capability preserves its actual callers, default behavior, authorization, cancellation and settlement.
3. Export outside the worktree with `git diff --binary --full-index <base> HEAD > /absolute/output/cloud-native.patch`. An optional split into Cloud, native API, native client, native runtime and support patches must cover every changed path once. On the exact base, replay in an isolated Git index and compare the resulting tree with `HEAD^{tree}`; this proves reconstruction, not compatibility with a newer upstream.
4. Review conflicts in an isolated checkout of the chosen upstream. Do not force an old patch over a changed commit point, weaken a guard, duplicate a native engine or enlarge tenant quotas to resolve a conflict.
5. Build the changed artifacts and run their native default and Cloud composition regressions. Configuration work includes `packages/boot/config-editor/tests` and the Cloud approved-control tests; browser changes also need the owning GUI/browser cases. Inspect skipped tests and retain failed results.
6. Stage a versioned product, preserve the previous release, then normally stop and join the original application and verify owner/allocation release before starting its successor. Check real login, model/Shell execution, history, file preview/download and logout. Do not declare closed optional capabilities accepted or turn quarantined state into readiness.

Native patch removal is conditional on equivalent behavior, not on reducing a file count. Optional plugin management, preview, arbitrary SSH, host failover and large-file acceptance require their own runtime evidence; passing this maintenance workflow does not enable them.

Native PTC and terminal spawn requests carry their resolved per-call sandbox policy into the remote provider. Local argv wrapping remains native; the Cloud provider consumes the original confinement handoff and signs the approved policy on the same operation.

The optional Native `ProfileContext.entryAliases` keeps trusted launch-time entry renames consistent across detached boot/HMR reads and the original ConfigEditor. Cloud uses one bounded, explicitly selected historical `presets` to `agent-preset-registry` alias with the original guarded provider; existing profile bytes remain unchanged until an explicit Native save. Ordinary Native profiles have no alias.

The native attachment staging provider exposes a phase-scoped storage-capacity error for its own prepublication I/O only after its descriptor and temporary name are released. Cloud preserves that exact failure across its original mutation settlement and the original Native receipt mapping; it does not infer capacity from a source error, a queue reservation or a filesystem precheck.

Independent account plugins reuse `CloudAccountApi.sessionProject(actualSession)` through Runtime's original `projectForSession` callback; missing callback or current business admission rejects access. This Host-only method creates no Session, Agent or execution authority.

The native SubprocessHandle has optional `releaseCollected()`; Cloud collected handles delegate it to their original ManagedCommandOperation.release(). The consumer copies output first. Original range/I/O settlement retains reservations and unknown cleanup, so a single native research tool can run sequential workflow/Git commands without retaining every completed output until final projection.

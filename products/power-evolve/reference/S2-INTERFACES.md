# S2 云工作区与产物实施接口

本页固定 S2 并行开发使用的请求字段和资源归属。产品当前状态与已验收证据分别见 [ARCHITECTURE.md](ARCHITECTURE.md) 和 [TRIAL-S1-NATIVE.md](TRIAL-S1-NATIVE.md)。

## 工作区与会话

- 一个用户可以拥有多个云工作区。平台生成 `workspaceId`，以 `(userId, workspaceId)` 授权；标题只用于显示，不能作为文件路径或权限依据。每个用户保留一个默认工作区，现有 S1 工作区及文件原地保留。
- Session 创建时指定可选 `workspaceId`；省略时绑定该用户的默认工作区。`pe_sessions.workspace_id` 在创建后不可改变。相同创建请求 ID 重试返回原 Session；若重试携带不同工作区则返回冲突。
- 原生 DSH Web 的 Workspace 列表展示当前用户所有工作区及各自 Session。各工作区在执行环境内都呈现为 `/workspace`；客户端选中的 Workspace ID 只决定新 Session 的归属，不决定平台信任的路径。
- 原生文件浏览器按已授权 Session 的 `workspace_id` 读写。平台接口每次核验用户、Session 和工作区的关系。旧的默认工作区文件入口在 S2 迁移期间保持原有语义，不得成为访问其他工作区的绕路。
- 创建工作区使用用户身份和稳定请求 ID；标题长度 1–80，单用户工作区数量有部署上限。列举与创建结果不包含物理存储路径。

## 沙盒可写挂载

- 一个 Session 的每次云执行仍使用其独立的 Sandbox Pod UID、runner 实例与命令记录；不同 Session 不复用进程状态。同一用户的持久 Home 目前也是共用可写目录，因此一个用户同时最多有一个可写云 Pod，即使其 Session 属于不同工作区。不同用户互不占用对方的槽位。
- 平台记录用户挂载槽位的 Session、工作区、代次、Pod UID 和交接状态。Kubernetes 资源名按用户槽位固定；Pod 标签和运行令牌绑定本次 Session。创建、复用、停止必须核验当前槽位与执行租约。旧执行者在交接后不得重新创建旧 Session 的 Pod。
- 交接先停止旧 Pod，并持久记录对应 Pod UID 的 kubelet 停止证据，再允许新 Pod 挂载。正在创建、结果不确定、Pod 消失但缺少停止证据时保持阻塞，交给对账或人工处置；数据库租约过期本身不等于进程停止。
- 平台直接修改工作区文件时须遵守相同的写入排他规则。不同 Session 对同一工作区的 Git 操作按交接顺序可见；沙盒回收不删除持久文件。

## 产物

- 用户在原生 Web 文件界面选择当前 Session 工作区内的文件并显式发布。平台验证 Session 归属及路径，从授权文件复制字节到沙盒不可见的私有产物目录，计算内容摘要，最后在 PG 提交不可变元数据。发布请求具有稳定 ID；相同请求重试返回同一产物，参数冲突返回 409。
- 产物元数据包含用户、工作区、Session、源相对路径、文件名、MIME、字节数、摘要和创建时间。列表按用户及可选 Session/工作区过滤，分页；预览只开放有界文本与受支持媒体；下载使用认证的流式响应。每次列举、预览和下载都重新核验用户归属。
- 产物发布不依赖解析模型回复或命令 stdout。源文件之后变化或沙盒回收不改变已发布的产物。产物存储不挂载进 Sandbox。

## S2 组合验收

两个账号分别创建两个工作区；各自从原生 Web 选择工作区、新建 Session、执行 Git 修改、发布文件、预览和下载。核对 PG 中的 Session 归属、文件与产物字节；验证相同工作区跨 Session 的挂载交接、两个用户同时执行、重复发布、越权请求、沙盒回收与重启恢复。缺少旧 Pod 停止证据时不得启动新 Pod。

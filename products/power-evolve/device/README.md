# Local device bundle

English | [中文](README.zh.md)

This standalone `dsh` bundle starts a local-only authorization page and a paired device worker. The current OS user grants project directories; absolute paths and the device token remain in its private local state. Commands run in disposable Docker containers with the granted project at `/workspace`, an enrollment-specific persistent Home at `/home/agent`, and selected read-only Skill packages. Private credentials, journals and coordination directories are not mounted. Cloud file transfers require an explicit action on the device page.

The Platform freezes enabled Skill versions at input acceptance. Dispatch `materials` bind their archive, manifest and instruction digests; the original Device, process and execution must be authorized before and after a package read. The Worker reauthorizes every package even on a cache hit, verifies the original manifest and all binary file digests, and syncs individual packages before read-only mounting. Package code runs only through an accepted command; ordinary Skill descriptions and resources require no execution container. Home and old package versions survive container cleanup. The [material protocol](../contracts/README.md) defines the limits and version compatibility.

On macOS/Linux, an upstream native `flock` excludes another worker using the same private root. The journal stores the accepted request digest, creation owner, immutable image/container IDs and an observed stopped state before cleanup. A cold recovery never creates or starts a replacement command; missing identities and old journals require review and block new commands. Absence alone is not a stop observation. The Platform freezes the original command and timeout, binds a distinct worker process to its dispatch, and registers the exact container before issuing one start permission. The original process and queued inputs are journaled before claiming. A lost claim acknowledgement may be retried by that same live process; cold `claiming` recovery uses the no-start closure below. A lost registration acknowledgement never authorizes a second start. Stop reports retain the original process/dispatch and a stable retry ID; matching durable terminal acknowledgements permit local cleanup. Revoked credentials can clean up only their existing work, not obtain new work. Unknown effects remain reserved in PostgreSQL without an automatic continuation.

A strict cold `claiming` entry has frozen queued inputs and an original process, without claimed dispatch, image, container, stop or result facts. The Worker holds its private journal and shared writer locks while the Platform permanently closes that original claim. The Platform checks the frozen identities and absence of start authority, fences later claim/register/finish calls, and saves one immutable receipt with at most one continuation; disabled accounts receive no new continuation. The Worker syncs the stable closure ID before requesting it and its matching receipt before retiring the original uncaptured slot, then removes the journal entry. ACK loss and interrupted cleanup retry the same closure without rebuilding an old reservation or clearing another writer. This records permanent no-start authority, not a Docker stop or command result.

Cold `claimed`/`created` entries without result or stop facts first request the same permanent closure with their original dispatch. A successful closure precedes a synced private cleanup record under `sealed-creations/`. If the original container is found, its exact non-running observation and confirmed removal precede slot retirement. If creation was not attempted, or the original name is still absent, the sealed intent can retire without a fabricated stop observation; an absent creation with a saved image keeps its cleanup record for later polls. The Worker processes one disk record per poll, including while another command runs, and removes only the exact original non-running container. Foreign or running observations and failed synchronization retain the original evidence. Existing records must pass file and directory synchronization again before retirement. Completed cleanup records are deleted only after the original journal no longer needs them; absent creations remain pending across restart. Cleanup never recreates the old writer slot or clears another writer.

The Platform's `/devices/agent/registered` endpoint accepts the original registration fields and verifies only an existing matching capture. Its response always has `canStart:false`; missing capture, changed ownership and permanently sealed execution are refused without changing execution facts. Only the exact `device_claim_start_unconfirmed` closure refusal permits recovery through this query. A failed query still allows the Device to stop its exact local writer and save the observation, but cannot authorize start or finish reporting.

Independent Platform approval may close a stopped unknown execution as `closed_unknown` only after rechecking its original request, enrollment, process, dispatch, exact container and stop-record digest. Closure retains the original output and stop facts and enqueues at most one continuation in the original Session. The Device may retry its unchanged stop report after closure or revocation; the ACK permits cleanup without new start authority. Work with prior start authority but missing stop facts, and incomplete legacy identities, remains blocked. The native execution area shows read-only facts and links to the existing independent approval console.

All cooperating Device Profiles of one OS user use the same configured `coordinationRoot`, independently of their private journals. One persistent writer slot serializes commands and explicit transfers, including unrelated or overlapping project directories. Command intent precedes Platform claim and Docker creation; stopping or losing a process never clears unknown work. Captured slots clear after exact-container removal and a matching known or independently closed stop ACK, or after the permanent no-start closure and durable cleanup described above. A durable `waiting` entry can resume after restart because it never submitted a claim. This conservative serialization does not isolate other OS applications or separate OS users. Changing the coordination root requires stopping existing writers and reconciling their recorded work.

Explicit local authorization records the physical root's decimal dev/ino identity. Legacy grants require local reauthorization; replacing the physical directory requires a new grant. Transfers retain a shared kernel-lock descriptor in their bounded Python helper, even after the parent dies. Descriptor-relative traversal rejects symbolic links and nonregular files; reads are bounded to 2 MiB and imports create without overwriting. An interrupted import may have committed its destination, so inspect before retrying. Cloud receives directory IDs and labels, never local paths; root, Home and overlapping private/coordination directories cannot be granted.

The [bundle configuration](cordis.patch.yml) sets the shared coordination root, Python executable, file deadline, polling, contact-loss, platform/Docker request and picker timeouts, plus the Docker stop grace period. Python 3.9 or later is required on macOS/Linux. The Home remains owned by the Device OS user with mode `0700`; the execution UID `1000` requires compatible bind-mount identity mapping. The current Mac/OrbStack integration verifies actual Home writes and restart reuse; ordinary Linux with a different host UID needs a deployment identity adaptation. Shutdown closes admission, waits for actual helper exit, local actions and the bounded command stop attempt, then attempts both writer and journal lock release; an unconfirmed Docker writer remains recorded. Full desktop recovery and Electron delivery remain defined by [desktop completion](../DESKTOP-COMPLETION.md). Device readiness is distinct from WebServer availability when a plugin fails to activate.

Use the [slice 5 trial guide](../TRIAL-SLICE5.md) to pair a device and test cloud and desktop execution. The web server must bind loopback. This bundle does not include the cloud host's Agent loop or platform database credentials.

This record covers the three clean-source ARM64 images from [release build evidence](QA-RELEASE-BUILD.md) running together through the formal deployment entry points. The fixed cloud candidate remains unchanged. Native browser acceptance is incomplete: both available browsers rejected the temporary local HTTPS certificate. No browser security setting or system trust store was changed.

## Creation recovery and online programming

Real online-programming acceptance exposed a creation-recovery defect: an image pull timed out after a writable mount reservation was committed, and subsequent workers refused that same reservation indefinitely. `265c057b0d` permits a first identity capture to resume an undispatched execution; `f29874e07d` permits observation of the same owned reservation and existing resources while capturing the Pending Pod UID in its creating instance. Missing resources are not recreated, and a changed captured UID remains refused. Ten execution/account tests and 28 creation, PostgreSQL, mount-handoff and finalizer tests passed. Kubernetes and Runner fault tests use deterministic substitutes; they do not establish the physical failure path.

The [new clean application image](QA-RELEASE-BUILD.md#creation-recovery-image) first updated Platform, then Host and the TLS proxy after the original execution settled. Local registry-test cleanup required a node restart, which replaced the original Pending Pod before the old instance record had captured its UID. The same Sandbox UID, owner, generation and binding remained. This is the supported legacy-null path: the worker captured the existing owned Pod, dispatched the original previously undispatched execution, and completed exactly one Session continuation with default egress refused. No request was resubmitted, generation advanced or stop evidence manufactured. `legacy-creation-recovery-proof.json` marks `originalPodPreserved: false`; rejecting replacement after capture has deterministic and real-PG evidence.

A separate real-cluster drill kept the node unschedulable until creation timed out, with the original Pending Pod UID and stop finalizer captured in PG while the mount slot remained reserved and the execution had no Runner identity. One targeted Platform child-process crash restarted its container in the same Platform Pod. The Sandbox UID, Pending Pod UID, generation and binding remained unchanged. Restoring node scheduling let the original request complete with one execution, one marker line and one completed Session continuation; another user's file read returned 404. The driver restored the node and left the default NetworkPolicy unchanged. `original-pod-recovery-proof.json` records this single-node scheduling-delay recovery; it does not cover an already dispatched command, an image-pull failure or browser interaction.

Two native Sessions then used real DeepSeek to clone `octocat/Hello-World` at fixed commit `7fd1a60b01f91b314f59955a4e4d4e80d8edf11d`, install exact `is-number@7.0.0` into separate initially absent npm caches, pass two Node tests each, and commit their own files. The recorded lock integrity matched the independently read npm metadata. Commands and working directories matched their durable requests; repeated native input IDs admitted one operation, each execution completed one continuation, the users had different Pod UIDs, and a foreign file read returned 404. Only the cluster-resolved GitHub and npm addresses on TCP 443 were temporarily admitted, and the original policy was restored. This covers that public repository and pure-JavaScript dependency with install scripts disabled, not arbitrary dependencies, production egress or browser interaction.

The first programming model turn returned HTTP 503 and recorded no execution. Its failed consumed input remains in history; a separate QA request completed the programming work. A driver defect compared serialized object key order and skipped policy restoration; a guarded operator restore returned the exact default policy, and the corrected driver uses semantic comparison. The successful two-user attempt restored policy in its own cleanup. Earlier failure evidence remains separate. `online-programming-proof.json`, `online-programming-proof-provider-503.json`, `online-policy-restored-after-failed-programming.json` and `online-creation-failure.json` retain these outcomes. Fresh logins after the update read histories equal to PG, downloaded the unchanged earlier markers, and retained SSH continuation and foreign-result denial; `readback-proof.json` records this readback and `readback-proof-ssh-image.json` retains the earlier image result.

## Creation cancellation and account revocation

Source review found that cancelling an undispatched execution after creation timed out left its reserved mount and creating instance outside automatic cleanup, blocking another Session. `07f584c7ce` adds cleanup under the original execution lease, with the exact reservation, generation, binding and captured Pod UID checked in PostgreSQL. Native stop evidence is committed before removing the original Pod finalizer; the reservation is released only after the original Sandbox, Pod, Service and Secret are absent. Unknown or replaced identities remain blocked. The existing trusted Platform owns this cleanup; Host authority, plugins, schema and deployment services are unchanged. The focused creation and execution suites passed 35 tests against independent real PG databases with deterministic Kubernetes and Runner substitutes. Independent implementation and test reviews found no blocking defect.

The [current clean application image](QA-RELEASE-BUILD.md#creation-cancellation-image) passed two separate real-cluster checks. Each admitted one native input despite duplicate submission, captured an unscheduled original Pending Pod, and waited for the configured creation timeout without a Runner execution identity. Another user's cancellation returned 404. Repeated owner cancellation in one check, and an administrator's repeated account-disable request in the other, cleaned up the original resources while the node remained unschedulable. PG retained native `UNSCHEDULED_DELETING` evidence for that exact Pod and Sandbox UID in both the instance and mount slot before release; the cancelled command created no marker. Revocation returned `account_disabled`, produced no Session continuation, and rejected the old user token with 401. After cancellation or account restoration, a different Session of the same user executed once in generation +1, produced one marker and one completed continuation, and refused foreign file reads. Both drivers restored node scheduling and the default NetworkPolicy; the revocation driver also restored the account. These checks cover unscheduled creation cancellation, not every scheduled-container failure or browser interaction.

The isolated QA originally contained only ordinary accounts, so its first revocation attempt stopped before any task was accepted or node changed. The product's explicit existing-identity bootstrap promoted the exact QA Alice account to administrator, recorded one bootstrap and audit row, and increased its account revision once. Temporary Platform configuration and Secret projection were removed after the restored deployment became ready; the original Secret bytes and Host template were retained. Alice remains the QA administrator; candidate accounts were not changed. `qa-admin-bootstrap-proof.json`, `creation-revoke-proof-no-admin.json`, `creation-cancel-proof.json` and `creation-revoke-proof.json` record these outcomes. Already-terminal stranded cancellations from older versions still require operator reconciliation as described in the [application contract](../application/README.md); this change does not manufacture stop evidence for them.

## Remaining gates

The new composition still needs native browser login, streaming, file controls and approval-page acceptance with trusted HTTPS. The local certificate expires after three days; trusting it requires the user's confirmation. Protocol results cannot close browser acceptance. Organization-registry pulls, the target architecture, external PostgreSQL, shared storage across physical nodes, production ingress, mixed-load capacity and organization identity integration remain subject to S7 target-environment acceptance. Existing fixed-trial evidence retains its recorded scope.

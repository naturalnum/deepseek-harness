# OpenSSH target for isolated QA

English | [中文](README.zh.md)

## Summary

This directory supplies a real OpenSSH target for controlled SSH acceptance. Its configuration accepts password or public-key authentication and passes ordinary commands to each account's `/bin/sh`. It is separate from the Connector Runner and from product authorization. Runtime behavior, image construction, and live integration remain unverified; the root integration task owns serial verification and cleanup.

## Accounts and runtime files

The image defines `qa-alice` (UID/GID 11001) and `qa-bob` (UID/GID 11002), without sudo or root login. Startup creates each Home with mode `0700`, including `work space` and `quote's space` directories. The daemon starts as root to initialize passwords and change session identity; authenticated commands run as the selected account. This fixture deliberately permits arbitrary controlled test commands.

[configure.mjs](configure.mjs) reads these root-owned, owner-only files from a read-only mount at `/run/ssh-target-input`. Password files contain exact nonempty UTF-8 text without newline or control characters; public-key files contain bare Ed25519, RSA, or NIST ECDSA OpenSSH public-key lines without options. Missing, oversized, malformed, or permissive input prevents startup with a fixed diagnostic.

| Input filename | Content |
| --- | --- |
| `ssh_host_ed25519_key` | Unencrypted OpenSSH Ed25519 host private key |
| `qa-alice.password`, `qa-bob.password` | Independent account passwords |
| `qa-alice.authorized_keys`, `qa-bob.authorized_keys` | Each account's accepted public keys |

The host key is supplied by the operator and is never regenerated by startup. Keep its private source or Kubernetes Secret to preserve the pinned fingerprint. Client private keys and their passphrases remain outside the target; encrypted client keys use the same public-key authentication as plain keys. Startup copies only public keys into root-controlled readable files and updates the disposable container's password hashes.

[sshd_config](sshd_config) selects port 2222, disables root login, forwarding, PTYs, user RC files, and user environment injection, and uses ERROR-level daemon logging. [entrypoint.sh](entrypoint.sh) replaces itself with `sshd` after configuration and clears its inherited environment. No repository credential, provider secret, or host Workspace is needed.

## Integration reference

The following commands are preparation references, not recorded live evidence. They require Node 22, OpenSSH `ssh-keygen`, Docker, k3d, kubectl, and an explicitly selected existing cluster with gVisor and enforced NetworkPolicy. Use one new owned `pe-connector-*` namespace following the [Connector access procedure](../../connector-runner/deploy/README.md), separate from writable Sandbox namespaces. Only the root integration task starts infrastructure.

Choose a new absolute `PE_SSH_FIXTURE_PRIVATE_DIR` outside the repository whose parent already exists. [prepare-private.mjs](prepare-private.mjs) refuses existing directories, creates `0700` directories and `0600` files, and generates one host key plus independent passwords, plain Ed25519 keys, encrypted Ed25519 keys, and passphrase files for both accounts. The askpass helper supplies passphrases from private files rather than command arguments or plaintext environment values. Preparation prints no credentials. A failed preparation leaves partial private material for the operator to inspect and remove; use a fresh directory to retry.

```sh
node products/power-evolve/deploy/ssh-target-fixture/prepare-private.mjs "$PE_SSH_FIXTURE_PRIVATE_DIR"
docker build -t "$PE_SSH_FIXTURE_IMAGE" products/power-evolve/deploy/ssh-target-fixture
k3d image import "$PE_SSH_FIXTURE_IMAGE" -c "$PE_K3D_CLUSTER"
kubectl --context "$PE_KUBE_CONTEXT" -n "$PE_CONNECTOR_NAMESPACE" create secret generic power-evolve-ssh-target-input --from-file="$PE_SSH_FIXTURE_PRIVATE_DIR/server"
```

Only the `server/` files enter the target Secret. Keep `client/` and `materials.json` private; the latter records file references and the public host fingerprint. The Docker context is this source directory alone, and [.dockerignore](.dockerignore) admits only the Dockerfile and three runtime source/configuration files. Debian installation removes generated host keys in the same image layer; no runtime credentials enter the image. Its base matches the cached Connector Runner Node base, but installing OpenSSH still requires Debian package access when the root task builds.

[kubernetes.example.yaml](kubernetes.example.yaml) contains a Deployment, ClusterIP Service, and NetworkPolicy with the example namespace `pe-connector-real-ssh-qa` and image `pe-ssh-target-fixture:qa`. Change both in a private copy before applying; it creates neither namespace nor Secret. The target mounts only the five input files, exposes no host port, accepts ingress from same-namespace Connector Runner Pods, and denies target egress. `imagePullPolicy: Never` requires prior import. Its root daemon needs the listed capabilities and a writable disposable root filesystem for `/etc/shadow`; this is target configuration, not Runner configuration.

Deploy the independently healthy forbidden listener in the same namespace, using the existing Connector deployment procedure. Configure the current rebuilt Runner image, scoped Platform kubeconfig, and the target's actual Pod IP plus port 2222 in the destination allowlist. Pin the fingerprint from `materials.json`. A target Pod replacement changes its IP and requires deliberate allowlist/connection updates; the Service is available for control inspection, not assumed to satisfy Runner IP-policy checks. One independent PG database and one Host/Platform pair can hold both product users.

## Acceptance coverage

Each product user should own a connection to its matching Unix account. Serial verification must cover all three credential forms, wrong password/key/passphrase, host-key mismatch, exact trusted approval, rejection without command execution, cross-user denial, and continuation in the originating Session. Use the current Runner image for execution-effect uncertainty and duplicate-call checks.

| Case | Remote observation |
| --- | --- |
| Ordinary command | `id -un`, `pwd`, and `printf` return actual account, directory, and bytes |
| Password, plain key, encrypted key | Each independently authenticates for both accounts |
| Working directory | Absolute path, `~`, `~/work space`, and `~/quote's space` produce the selected directory |
| Missing directory | Nonzero exit; a command marker is absent |
| Account separation | Each account writes its own Home; the other account cannot read that Home |
| Persistence and cleanup | Host fingerprint survives target replacement; temporary Runner resources are removed |

Use Platform's working-directory field to exercise its command rendering rather than embedding all directory changes in the proposed command. Public-key authentication does not send the client's passphrase to OpenSSH. Configuration semantics are documented in the [Debian OpenSSH manual](https://manpages.debian.org/bookworm/openssh-server/sshd_config.5.en.html).

<a id="known-limitations"></a>

## Known limitations

This is a disposable QA target, not a production SSH service, restricted-command broker, or implementation of product ownership and approval. Accounts share the target operating system and `/tmp`; Home permissions do not provide separate kernels or chroots. There is no forced command or `qa:ping` substitute. Arbitrary test commands may read account-accessible system files and modify that account's disposable state. Do not mount product storage, client private keys, or production secrets.

The example Homes are `emptyDir` volumes and disappear with the Pod. Preserve only the operator-owned host key when testing identity continuity. Password changes require container restart; authorized keys are copied at startup. NetworkPolicy enforcement, gVisor capabilities, package availability, askpass on the operator's OS, daemon configuration, authentication, directories, command results, and live product recovery require root-owned runtime verification. Static source checks alone establish none of these outcomes.

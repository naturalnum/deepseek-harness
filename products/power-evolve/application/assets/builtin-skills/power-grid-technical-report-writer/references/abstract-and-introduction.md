# 摘要、项目概述与发展现状生成规则

## 1. 摘要不得在全文结束后临时概括

摘要规则属于强制状态约束，不是仅在最终阶段参考的写作建议。不得等主体全文完成后，才依赖模型对长上下文的临时记忆自由提炼摘要。

目录和中心主旨确认后，必须初始化 `abstract_evidence`，结构见 `schemas/abstract-evidence.schema.json`，模板见 `templates/abstract-evidence.json`。该证据包用于持续记录：

- 领域现状和现实需求；
- 现有技术不足及其技术原因；
- 关键挑战及其与研究点的对应关系，挑战数量原则上与研究点数量一致；
- 各主要研究点的问题、技术名称、核心机制和形成能力；
- 各研究点对应的已确认章节；
- `task_book_assessment_results`：当前报告范围内任务书考核指标的对应结果，包括定量指标的实际数值/结果与定性指标的能力、功能或成果结果，以及证据状态、测试/适用条件和正文位置；
- `supplementary_result_metrics`：仅在确有解释价值时补充的非任务书指标，全文摘要最多1—2个，不按研究点机械配指标；
- 总体结论、研究前景、应用价值、应用前景、适用条件和能力边界；
- 默认五个关键词的候选与最终方案。

每个技术章节的计划阶段应说明该章是否贡献于某个摘要研究点、对应哪项关键挑战，以及准备形成哪些摘要证据。每个章节正文经用户确认后，必须立即更新 `abstract_evidence`，而不是只保存笼统的章节摘要。未由正文或实验确认的内容只能标记为 `planned`、`partially-verified` 或 `insufficient`，不得提前写成已实现效果。

## 2. 摘要生成时点与独立准备阶段

摘要必须在主体技术章节和总结性结论基本确认后生成，以已确认正文和 `abstract_evidence` 中的证据为依据。不得根据早期目录猜测成果，不得写入正文尚未出现的方法、指标或结论。

从 `BODY_CONFIRMED` 进入摘要生成前，必须完成独立的摘要准备阶段：

1. 重新读取本文件，而不是依赖项目开始时的旧记忆；
2. 读取 `abstract_evidence`，检查关键挑战、研究点及其对应关系是否完整；
3. 将全部技术章节归并到主要研究点，默认可归并为三条主要研究线，但研究点数量应服从项目实际内容；
4. 检查每个研究点是否均具备“问题—技术—核心机制—能力—证据—条件”；
5. 逐项核对当前报告范围内任务书考核指标：定量指标准备实际结果、条件和正文依据；定性指标准备对应的能力/功能/成果结果和正文依据。任务书考核指标是摘要第三段指标性结果的主集；非任务书指标仅在明显有助于解释核心效果时补充1—2个，超过2个必须删减；
6. 基于业务对象、现实痛点和业务能力需求生成3—5个“业务需求背景分析”首句候选，写入 `business_need_opening_candidates`；候选之间应采用不同切入角度但保持同一事实边界；选出1句作为推荐首句并写入 `selected_business_need_opening`；
7. 锁定五个关键词：前两个通用领域词，后三个选择最具代表性的研究点技术词；
8. 锁定中文摘要篇幅：正文总有效字数700—800字；第一段200—250字；第二段300—350字；第三段不另设固定区间，以补足总字数并完成结果、结论与前景表达为准；
9. 锁定挑战与研究点的排序表达方案。第一段和第二段必须在连续自然段中使用明确顺序词，可采用“第一、第二、第三……”或“首先、其次、再次……”等同类表达，前后顺序必须对应；
10. 形成内部三段式提纲后，先生成中文摘要，再基于已定稿中文摘要同步生成英文摘要和英文关键词。英文摘要不得独立扩写新的技术、指标、结果或前景。

生成摘要时，应以“摘要规则 + 摘要证据包 + 三段式内部提纲”为主要输入。全文只用于必要的事实回查，不得把整篇长文作为唯一输入后自由概括。

## 3. 摘要固定组织方式与篇幅

中文摘要固定采用三个连续自然段，摘要正文总有效字数控制在700—800字。有效字数按“中文字符逐字计数，连续英文或数字记为一个词”的方式统计，不计摘要标题与关键词。第一段控制在200—250字，第二段控制在300—350字；第三段不单设固定字数区间，以补足700—800字总篇幅并完成结果、结论、研究前景和应用前景表达为准。

第一段提出现状、需求与挑战；第二段将原有各研究点内容合并为一个研究工作段；第三段以任务书考核指标对应结果为主，集中说明定量/定性结果、总体结论、研究前景与应用前景，非任务书指标按需最多补充1—2个。无论项目研究点数量如何变化，三段结构均不得改变。

### 3.1 内容摘要首句：先生成业务需求背景候选，再选一句入正文

正式中文摘要仍只有三个自然段，但在生成第一段前必须先形成 **3—5个首句候选**。这些候选是摘要产物的伴随选择项，不计入摘要正文，也不得全部写进最终摘要。

候选首句必须直接从当前电力业务场景切入，至少体现“业务对象/运行场景 + 现实问题或能力缺口 + 需要具备的业务能力”中的两项，优先回答“为什么当前业务需要这项研究”，而不是泛泛介绍技术发展。候选可以分别从运行压力、人工处置瓶颈、数据/知识使用困难、时效/可靠性需求或工程协同需求等角度切入，但不得为了差异化新增事实。

首句候选规则：

- 默认生成3—5句，彼此不能只是同义词替换；
- 不以“近年来，随着……快速发展”“随着人工智能技术不断发展”等泛化句式开头；
- 不在首句提前写具体算法、模型、实验指标或研究结果；
- 每句都必须能够单独作为第一段第一句，并与后续现实需求、现有不足和挑战自然衔接；
- 生成后标记1句 `selected_business_need_opening` 作为推荐首句；若用户未单独指定，最终 `abstract_cn` 第一整句必须使用该推荐句；用户选择其他候选时，只替换首句并同步调整英文摘要对应首句，不改变事实边界。

### 第一段：现状、需求与挑战

先说明研究领域或应用场景的现状，再指出现实需求及现有技术的不足，最后归纳本文需要解决的若干关键挑战。

本段必须同时写清：

- 问题发生的实际场景；
- 当前业务或科学任务需要具备的能力；
- 现有技术表现出的不足；
- 形成这些不足的技术原因；
- 本文需要解决的关键挑战。

关键挑战应与第二段中的研究点建立清晰对应关系。项目有几个主要研究点，原则上就归纳几个关键挑战；默认三研究点项目通常对应三项挑战。确需一项挑战由多个研究点共同解决，或一个研究点同时回应多项挑战时，必须在 `abstract_evidence` 中登记对应关系和原因，不得为了凑数量机械拆分或合并。

本段必须对关键挑战使用明确的顺序词进行排序。默认三项挑战时，可使用“第一、第二、第三”或“首先、其次、再次”等自然衔接方式；挑战多于三项时按实际数量继续排序。排序词必须嵌入自然段，不得改写为项目符号或编号列表。该要求是摘要专属结构规则，不属于机械列举。

挑战既要描述现象，也要说明困难形成的原因，但不得在本段提前展开具体方法、模型结构和实验结果。不得以“近年来，随着……快速发展”作为默认开头，也不得把本段写成政策背景或意义口号。

### 第二段：合并说明全部研究点

将原第二、第三、第四段的研究内容合并为一个连续自然段，按第一段挑战的顺序依次介绍全部主要研究点。每个研究点仍必须保留以下内部语义链：

`挑战或问题 → 提出的研究点 → 核心技术机制 → 实现的能力或解决效果`

默认三研究点项目应在本段形成三个逻辑清晰的句组，每个句组分别对应一个研究点；句组之间可使用必要的承接关系，但不得使用编号列表、段内小标题或章节编号。研究点数量不是三项时，按实际数量组织句组，不能遗漏任何主要研究点，也不能把多个研究点压缩成只有技术名称的并列清单。

本段必须按照第一段挑战的顺序，用明确的顺序词介绍对应技术点。可使用“第一、第二、第三”或“首先、其次、再次”等表达；排序位置必须与第一段挑战逐项对应。允许第一段和第二段采用不同但等价的顺序词体系，但不得改变挑战—研究点映射顺序。

各研究点应保持逻辑平行，但不要求句式和长度完全一致。若后续研究点依赖前序研究点，应使用少量文字说明输入、承接、约束、集成或反馈关系。承担系统集成、工程应用或综合优化作用的研究点，应写清其如何整合其他成果并形成面向实际场景的完整解决方案。

本段的主要表达任务是完整说明“本项目开展了哪些研究以及如何解决对应挑战”。虽然包含多个研究点，但每个句组仍应只突出一个主机制和一个代表性能力，避免用一个超长句连续堆叠多项技术、动作和效果。

### 第三段：任务书考核结果、总体结论与研究应用前景

第三段的指标性结果必须以**当前报告范围内任务书考核指标**为主线，不再从各技术章节自由挑选大量普通实验指标。任务书中的定量指标和定性指标都必须建立对应结果：

- **定量考核指标**：写正文已有依据的实际数值、范围、相对结果或可确认结果，并尽量交代必要测试条件/比较对象；不要在摘要中机械复述“应达到/不低于/不超过××”的任务书门槛。
- **定性考核指标**：即使没有数值阈值，也不得遗漏。应写成正文已经形成或证实的能力、功能、流程、系统成果、适用性或工程效果，例如“形成了……能力”“实现了……功能”“建立了……支撑关系”，并能追溯到正文位置。
- 同类考核指标较多时允许压缩成一个句组，但 `abstract_evidence.task_book_assessment_results` 中仍须逐项登记，不能因为摘要篇幅而静默漏掉。

除任务书考核指标外，**非任务书指标默认不写**。只有某个普通实验指标能够明显帮助解释核心方法效果、且不写会使结论难以理解时，才允许补充；整个中文摘要最多补充1—2个非任务书指标，不得按每个研究点分别配一个，也不得把摘要第三段写成指标流水账。 若当前项目确无任务书或当前报告范围不存在可用考核指标，则不虚构“任务书指标”，改为从已确认正文中选择1—2个最能代表整体效果且证据充分的结果指标作为第三段结果支撑。

在这些结果基础上，总结各研究点共同解决了什么总体问题，形成了什么综合能力。随后说明仍需深入研究的技术问题、可继续拓展的研究方向，以及成果的工程价值、适用场景、推广条件和应用前景。研究前景与应用前景必须建立在已经确认的定量/定性结果和明确适用条件上，不得脱离证据作宽泛展望。

摘要整体逻辑固定为：

`业务需求背景首句 → 领域现状与现实需求 → 按顺序归纳关键挑战 → 按对应顺序说明全部研究点及其技术机制与能力（同一段） → 任务书定量/定性考核结果 → 可选1—2个补充指标 → 总体结论 → 研究前景 → 应用价值、条件与前景`

### 3.2 英文摘要同步生成

`generate_abstract` 阶段必须在同一次产出中同时生成中文摘要、中文关键词、英文摘要和英文关键词。英文摘要以最终中文摘要为唯一内容基准，保持相同的三段结构、挑战顺序、研究点顺序、技术名称、数值、结论和能力边界，不另行增加材料。英文关键词应与中文关键词逐项对应并保持相同顺序。

英文摘要不设置独立字数或词数门槛；其首要要求是忠实、完整地对应中文摘要，不因翻译压缩而遗漏关键挑战、核心技术点或代表性结果。

## 4. 摘要生成后的内部一致性检查

摘要草案生成后、展示给用户前，必须在内部完成语义检查。语义、证据和中英文对应关系仍由模型依据下列规则检查；编排器另使用确定性门禁校验中文摘要篇幅、三段结构、顺序词和双语字段是否齐全。以下任一项不满足时必须先自行修订：

- 中文摘要正文是否恰好形成三个连续自然段；
- 中文摘要正文总有效字数是否为700—800字，第一段是否为200—250字，第二段是否为300—350字；
- 第一段关键挑战和第二段研究点是否均使用明确顺序词，并保持挑战—研究点的对应顺序；
- 是否在同一次摘要产出中同时提供英文摘要和英文关键词，且英文内容与中文摘要逐段对应；
- 第一段是否同时包含现状、需求、不足、技术原因和关键挑战；
- 关键挑战数量是否原则上与主要研究点数量一致，挑战与研究点对应关系是否清晰；
- 第二段是否覆盖全部主要研究点，并且每个研究点均包含问题、技术名称、核心机制和能力；
- 是否已生成3—5个业务需求背景首句候选，推荐首句是否属于候选集合，且中文摘要第一整句是否使用推荐/用户选定候选；
- 第三段是否以任务书考核指标结果为主，是否同时覆盖定量和定性考核要求；定性指标是否给出了对应能力/功能/成果结果，而不是只保留要求原文；
- 非任务书指标是否确有必要且全文摘要最多1—2个；是否存在按研究点机械堆指标或自由挑选大量普通实验指标；
- 第三段是否在结果之后包含总体结论、研究前景、应用价值、应用前景和适用条件；
- 摘要中的技术名称、能力声明、数值和前景判断是否能在 `abstract_evidence` 或已确认正文中找到依据；
- 是否出现正文中不存在的新技术、新缩写、新指标或新应用结论；
- 是否出现章节编号、任务书口吻、目录式复述或分点；
- 是否存在过多过渡词、无信息过渡句或长串并列；
- 三个自然段是否分别承担“背景与挑战、合并研究工作、结果与前景”的唯一主要任务；
- 关键词是否符合默认五关键词结构。

检查的是语义字段是否完整，不是机械要求每个研究点句组都出现“针对、提出、通过、实现”等固定词语。允许句式变化，但不允许信息缺项。

## 5. 摘要表达要求

摘要表达同时执行 `narrative-focus-and-power-grounding.md`。三个自然段分别承担背景与挑战、研究工作、结果与前景三个主要表达任务。除摘要专属排序词外，过渡词只在逻辑关系无法由内容本身体现时使用，不得为了显得连贯而连续加入“此外、同时、进一步、在此基础上、因此、综上”等过渡句。第一段用于排序挑战、第二段用于排序技术点的“第一、第二、第三”或“首先、其次、再次”等表达属于本摘要结构的必要标记，不按模板化过渡词处理。

第二段虽然合并多个研究点，但不应写成一个充满顿号和逗号的超长句。优先用多个完整句子或清晰句组分别表达各研究点，按“问题—机制—能力”重组，再用必要的因果、先后、约束、包含或反馈关系连接。核心技术章多于三章时，先归并研究线，不把所有章名压缩为一串并列短语。

- 摘要必须使用三个完整、连贯的自然段，不使用分点；
- 不出现章节编号、图表编号、公式编号和参考文献标号；
- 不写“任务书要求”“课题安排”等材料来源表述；
- 不引入正文没有出现的技术或结果；
- 任务书定量考核结果必须与正文、表格和结论保持一致；任务书定性考核要求必须在摘要中转写为有正文依据的对应能力、功能或成果结果；
- 非任务书指标按需最多补充1—2个，除非用户明确要求，不得在摘要中继续增加；
- 方法名称应稳定，不在摘要中临时创造新缩写；
- 研究前景应指出可继续解决的技术问题或可验证方向，不写抽象口号；
- 应用前景应落到具体业务能力、工程条件、适用场景或部署路径；
- 摘要正文可使用 `templates/abstract.md` 组装，但正式输出不得保留内部占位、段落标签或注释。

## 6. 关键词

关键词默认严格为五个，并在摘要准备阶段提前锁定：

1. 第一个关键词：通用领域词，表明所属研究领域；
2. 第二个关键词：通用领域词，表明核心研究对象或业务领域；
3. 第三个关键词：对应第一核心研究点的计算机/人工智能/算法技术词；
4. 第四个关键词：对应第二核心研究点的计算机/人工智能/算法技术词；
5. 第五个关键词：对应第三核心研究点的计算机/人工智能/算法技术词。

默认三研究点项目中，后三个关键词分别对应三个研究点，并优先选用可检索、稳定、具有明确计算机技术含义的名词或名词短语，例如深度学习、图神经网络、马尔科夫链、扩散模型、贝叶斯优化、对比学习、强化学习、知识图谱等。研究点多于三项时，应选择区分度最高、最能代表主要技术链的三个计算机技术词；研究点少于三项时，可从核心算法、模型、概率推断、优化、知识或系统技术中补足。后三个关键词不得仅使用电网、调度、设备、智能化、数字化、技术研究、系统应用等业务对象或泛化词。

关键词应使用规范、稳定、便于检索的名词或名词短语，不使用完整句子，不选择“技术研究”“智能化”“数字化”等过于宽泛且缺少区分度的词，也不选择仅在正文局部出现的次要术语。第3—5个关键词属于技术关键词专位，即使对应技术词在一般写作风格规则中被视为专业术语，也不得因为术语化或计算机领域属性被改写成业务词。

除非用户明确指定其他数量或排列方式，必须只生成五个关键词，不得增加第六个关键词。

## 7. 第一章“项目概述”

第一章必须命名为“项目概述”，不得使用“引言”“绪论”或其他名称。二级、三级标题固定为：

```text
1.1 项目背景与研究意义
1.1.1 项目研究背景
1.1.2 项目研究意义
1.2 国内外研究现状
1.2.1 国外研究现状
1.2.2 国内研究现状
1.3 主要研究内容及思路
1.3.1 主要研究内容
1.3.2 研究思路
```

第一章不得再增加同级二级标题，也不再单设“国内外发展现状”一级章。技术章节从第2章起按报告范围映射。

### 7.1 项目研究背景

从具体电力业务场景、运行对象、现实需求和已有条件开场，说明项目面对的实际问题、当前能力缺口及问题形成的业务或技术背景。背景用于说明“为什么需要开展这项研究”，不提前展开后续技术方案，不写成政策、行业口号和技术发展史的长篇堆叠。引用政策、行业数据、工程指标或权威结论时必须有来源。

### 7.2 项目研究意义

在背景基础上说明解决上述问题后能够改善的运行能力、工程效率、安全水平、技术认识或业务支撑能力。研究意义必须与项目真实问题和预期成果对应，不做脱离研究边界的价值拔高。

### 7.3 国外研究现状

按当前报告范围内的研究主题组织国外代表性工作。每个主题先概括共同技术路线，再综合代表性文献，说明取得的进展、成熟度、适用条件和仍未解决的问题。不得逐篇文献机械罗列，也不得为了形成对比虚构差异。

### 7.4 国内研究现状

采用与国外研究现状一致的研究主题和比较口径，综合国内代表性工作、工程应用、成熟度、适用条件和不足。国外与国内两节文献数量可以不同，但研究主题应可对应，便于归纳与本项目相关的技术缺口。

生成1.2前必须在章节计划中锁定一种作者指代样式：默认“XXX等人”，也可以统一选择“XXX团队”。1.2.1和1.2.2必须沿用同一选择。机构、标准组织和官方项目直接使用正式名称，不纳入人名指代样式。

### 7.5 主要研究内容

`1.3.1 主要研究内容`必须与技术规划书、任务书或等效技术文件中的当前报告范围研究内容逐项对应，并保持原始顺序和边界。对每项研究内容可以稍作展开，以便说明研究对象、主要问题、核心任务和预期形成的技术能力，但不得增加来源文件没有的研究方向、算法、指标、成果或应用结论。

总报告中，每个课题或一级研究内容与后续一个技术章一一对应；具体课题报告中，每个来源研究内容小点与后续一个技术章一一对应。此节是目录映射和后续章节边界的主要依据。

### 7.6 研究思路

`1.3.2 研究思路`说明各研究内容之间的总体逻辑、依赖关系、输入输出、关键处理链、研究推进顺序和验证思路。适合时安排总体研究思路图。

本节不再承担“章节安排”职责，不逐章复述目录，不使用“第二章、第三章”等章号说明全文组织。

## 8. 技术章节的章首无标题导入正文

技术章节从第2章起。一级章标题之后直接写章首导入正文，不设置“概述”“技术路线”“技术架构”“技术路线与总体架构”等二级标题。原概述和路线/架构信息在该无标题正文中合并完成：

1. 简要说明与本章主题直接相关的背景、现实问题和研究意义，类似第一章背景与意义，但只服务当前技术主题；
2. 自然引出本章研究对象、核心问题和研究主题；
3. 概括本章总体技术路线或系统架构，说明关键输入、主要处理链、模型/算法/模块关系、输出和能力边界；
4. 适合时优先采用“文字说明 + 技术路线图/架构图”的图文结合方式。

以5万字全文为基准，该章首导入正文目标约800—1200字；其他全文目标字数按约1.6%—2.4%同比例规划。该范围用于章节计划和写作控制，不应通过重复背景或空泛过渡凑字数。

章首导入之后默认进入X.1、X.2、X.3三个核心研究小点；若存在经确认的必要扩展，则继续进入X.4或X.5核心研究小点。

## 9. 技术章节“本章小结”

本章小结的结构位置、篇幅、总—分—总组织、成果归纳、实验结果使用方式、生成时机与验收统一执行 `references/chapter-summary.md`。本文件不再维护另一套小结正文规则。

## 10. 独立报告口吻

摘要、项目概述、国内外研究现状和技术章节均不得出现“任务书中要求”“课题一提出”“根据最终材料”等来源口吻。外部要求应转化为报告自身的研究目标、性能约束和验证标准。

正式正文不得使用具体章节编号、上一章或下一章进行跨章互引。需要说明研究关系时，直接使用技术对象名称、研究内容名称或“本文、前文、后文、前述方法、在此基础上”等自然表达。

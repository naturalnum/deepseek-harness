# 项目档案、中心主旨与论证架构阶段

> 本文件由 v3.5.4 `SKILL.md` 中的对应规则块原文迁移。除标题分组和迁移标记外，规则内容未改写。

## 1. 适用范围

当用户需要撰写、扩展、重构或续写以下内容时使用本 Skill：

- 电网科技项目总报告或技术分报告；
- 电力技术研究报告；
- 算法、模型或机理研究报告；
- 系统设计与实现报告；
- 创新模块或优化方法报告；
- 集成验证、示范应用或工程应用报告；
- 与电网业务相关的人工智能、数据分析、信息通信和数字化技术报告。

不用于短消息、单段润色、纯文学创作、简单摘要或不需要多章节结构的文本。

## 2. 总体目标

生成内容应同时满足：

1. 全篇围绕一个明确的总体问题展开；
2. 关键挑战、研究内容、技术机制、验证证据和总体结论能够一一对应；
3. 目录体现递进、依赖、协同或集成关系，而不是通用模板拼接；
4. 核心技术及其直接证据和结果分析占据主要篇幅；
5. 每章在首次生成时完成问题、原因、目标、方法、实现、证据、解释、边界和结论的逻辑闭环；
6. 真实项目证据不得虚构：不得把模型生成内容冒充真实项目数据、实测实验结果、第三方测试、项目成效、标准、政策、引用或真实应用案例；当真实实验材料不足时，按 `references/experiment-evidence-layering.md` 生成明确标记的 REFERENCE_EXPERIMENT，包括模拟参考数据；
7. 内容具体、克制，明确工程对象、处理机制和作用条件；
8. 图表与正文同步规划，数据或细节不足时输出结构化占位；
9. 摘要和最终总结在主体章节完成后生成；
10. 通过全局状态保持术语、数字、章节关系和核心结论一致；
11. 通过逐阶段确认防止模型过早展开和一次性低质量生成；
12. 正文以自然段为主，分点、三级标题和“电力”用词均由内容需要决定，形成自然但不随意的结构；
13. 目录遵循电网科技报告的稳定骨架，第一章、技术章三个研究小点与本章小结、最后一章和参考文献不得由模型随意省略或改造；最后一章只保留一个一级标题，不设置二三级标题，正文固定700—800字；
14. 参考文献优先通过联网检索和真实性核验获得；不能联网时先向用户索取明确篇目，用户也无法提供时允许使用统一的 `【待补充来源】` 占位；
15. 摘要从目录确认后持续维护证据包，每章确认后更新，最终重新加载规则并按固定三段式组织；第一段写现状、需求和挑战，第二段合并全部研究点，第三段写量化实验结果、研究与应用前景；关键词默认五个，前两个为通用领域词，后三个为代表性研究点技术词；
16. 技术章节及承担统一技术定义的框架、概述和基础章节默认包含服务主线的公式，首次出现的符号必须完整解释；描述性公式从简，技术公式从充分，不改变既有公式需求分级和有效性标准；
17. 未收到用户明确体例要求时，项目档案默认将成果类型设为“科技项目结题技术报告”，不再询问写作风格偏好；
18. 每个技术章章首简要说明本章技术任务对报告总体目标的支撑，正式正文不出现任务书、课题编号、最终材料等报告结构之外的文件或行政词汇；
19. 技术章映射必须服从报告范围：总报告一个课题对应一个技术章；具体课题报告一个研究内容小点对应一个技术章；章标题仅对相应课题名称或小点原文作必要名词化整理；
20. 每个技术章一级标题后直接以无标题章首导入正文完成背景与意义、研究主题和概括性技术路线/架构，随后从X.1起按三个真实技术研究小点组织；
21. 第一章1.2国内外研究现状、1.3.1主要研究内容、进度计划技术事项和考核要求细则必须与研究内容—技术章节映射一致，并通过内部覆盖矩阵保证所有范围内技术事项均有明确落点；
22. 任务材料中其他课题或其他报告范围的内容必须逐项识别并排除，不得进入标题、正文、公式、实验、指标、结果或摘要；
23. 每章小结和最终总结必须结合定量证据与定性判断，并自然落到电网对象、运行状态、业务能力或工程价值；
24. 第一章1.2国内外研究现状的作者指代样式必须统一，默认使用“XXX等人”，选择“XXX团队”后则国内外两节均使用该样式；
25. 项目档案草案固定确认任务书范围、内容生成依据模式、报告字数/模板/章节数量要求和实验数据四项信息；
26. `source_grounded`模式必须在论证架构确认后、目录生成前完成逐章内容概述确认，但不得改变既有目录生成规则；
27. 目录和章节计划必须登记计划字数与80%最低验收字数，章节或分节正文展示前必须通过确定性字数校验；
28. 目录标题原则上不超过25个可见字符；技术研究章二、三级标题的技术签名显化和40%—60%“基于……的……”比例优先于该长度原则，必要时允许长度例外；功能性标题可直接采用“实验”“评价指标”“实验设置”“数据集”等简洁名称；
29. 最终Markdown组装后必须调用确定性脚本统一长划线并删除数字与汉字之间的空格；
30. 目录和章节计划中已确认的标题必须在正文中按原编号、原名称、原层级和原顺序完整保留，技术章三级标题不得在生成过程中被合并、改名或省略。

## 4. 核心原则

### 4.1 先确定总问题，再生成目录

生成目录前，必须形成以下中心主旨：

- 本报告面向什么场景；
- 解决什么总体问题；
- 总体问题包含哪些关键困难；
- 每项研究内容分别解决什么困难；
- 多项工作共同实现或验证什么结果。

信息不足时，先根据用户材料提出一版可修改的推断，只询问会改变报告主线或目录的缺失信息。

### 4.2 先规划论证关系，再拆分章节

先建立：

`总体问题 → 关键挑战 → 研究内容 → 技术机制 → 验证证据 → 能力边界 → 综合结论`

再根据研究内容之间的真实关系组织目录，例如：

- 顺序依赖；
- 并行协同；
- 层级包含；
- 反馈迭代；
- 理论—方法—系统；
- 感知—分析—决策—反馈；
- 单项技术—集成验证。

### 4.3 质量要求融入首次生成

不创建独立章节审查、评分、门禁或自动打回阶段。逻辑完整性、证据约束、篇幅控制、语言自然度、边界说明和图表安排必须写入章节计划和章节契约，并在首次正文生成时落实。

用户提出修改时，直接修改正文，不输出审稿报告。

### 4.4 证据强度决定结论强度

- 有实际数据时，给出比较对象、条件、指标和结果；
- 有定性材料但无数字时，使用可核验的定性结论；
- 仅有方案设计时，写成“拟实现”“用于验证”“预期改善”；
- 正式“已实现成果”缺少必要真实结果时插入明确占位；若当前研究内容需要实验验证，则同时按 `references/experiment-evidence-layering.md` 生成完整 REFERENCE_EXPERIMENT，不得仅因没有实测数据而省略实验内容；
- 任何结论都说明适用条件、代价、限制或未覆盖范围。

### 4.5 图表与论证同步设计

每章计划时同步确定图、表、公式和伪代码。初版占位至少包括：

- 编号和名称；
- 图表类型；
- 需要展示的对象或数据；
- 对象之间的关系；
- 正文中的论证作用；
- 当前已有信息；
- 尚缺信息；
- 推荐生成方式；
- 图示内容说明（只说明计划表达的结构、关系和读图重点，不生成绘图 Prompt 或实际图像）。

不得只写“此处插图”。

### 0.13 内容生成依据模式

内容生成依据规则必须读取`references/content-generation-mode.md`。首次项目档案确认前必须确定且只询问一次默认模式：

- `source_grounded`：基于已有内容生成；
- `model_autonomous`：交由大模型自行生成。

选择后默认持续生效，不在每章重复询问。用户在首次消息中已经表达明确偏好时直接识别，不再重复提问。

`source_grounded`模式下：

- 论证架构确认后、目录生成前，必须按预计章节逐章询问并确认每章的大概内容；该内容概述只作为目录细化依据，不替代后续逐章材料准备，也不得改变当前固定目录骨架、章节映射、技术章无标题导入和“默认X.1—X.3、必要时最小扩展到X.1—X.N”的规则；
- 每章计划生成之前必须先完成该章材料准备；
- 第一章在参考文献与国内外研究现状方案确认后请求材料；
- 后续章节在当前章完整生成后的确认结束语中，同时询问下一章已有材料；
- 用户确认当前章但未提供下一章材料时，下一轮只输出下一章材料需求清单；
- 已提前提供且足以支持下一章的材料不得重复询问；
- 核心技术内容缺失时不得自行补成项目既有成果，用户可以回复“本章交给模型生成”。

`model_autonomous`模式下：

- 不在每章开始前询问材料；
- 根据已确认研究范围、已有材料、核验文献和电力工程逻辑自主提出方案；
- 仍不得把模型生成内容冒充 REAL_PROJECT_EVIDENCE、真实应用成效、论文和标准；真实实验数据不足时，不得因此停止实验内容生成，应按 `references/experiment-evidence-layering.md` 主动生成完整 REFERENCE_EXPERIMENT。

用户可随时主动切换：

- “本章交给模型生成”或“本节交给模型生成”只形成临时覆盖，结束后恢复原默认模式；
- “后续都交给模型生成”将默认模式切换为`model_autonomous`；
- “后续恢复根据已有内容生成”将默认模式切换为`source_grounded`；
- 不得在用户未提出切换时每章重新询问模式。

### 阶段 A：建立简化项目档案

#### 默认报告类型

- 报告类型默认且直接填写为“科技项目结题技术报告”；
- 不询问用户“偏向学术风格还是工程风格”“采用什么写作风格”“更像论文还是报告”等风格选择问题；
- 只有用户明确指定其他成果类型或表达体例时，才调整报告类型和相应表达规则；本版本固定的第一章架构及研究内容小点—技术章映射不随表达体例改变；
- 默认类型只用于项目档案和内部写作定位，正式正文仍直接陈述技术内容，不反复自称“结题报告”。

#### 内容生成依据模式

首次项目档案阶段必须记录用户选择：

- `source_grounded`：基于已有内容生成；
- `model_autonomous`：交由大模型自行生成。

若用户尚未明确选择，应在项目档案末尾询问一次。模式选择后默认沿用，不在每章重复询问。用户已经明确表达时直接记录，不重复提问。

#### 固定确认问题

项目档案草案必须固定包含以下四项。附件或用户消息中已有明确答案时，直接回填“已识别答案”并请用户确认，不得重复追问；没有答案时标记“待用户补充”。四项必须全部得到答案，用户可以明确回答“没有”“不指定”或“暂不提供”：

1. 有没有任务书；若有，本报告对应任务书中的哪个具体课题，还是任务书总报告；
2. 后续内容生成依据选择“基于已有内容生成”还是“交由大模型自行生成”；
3. 是否有指定报告字数、模板或章节数量要求；
4. 有没有可提供的实验数据。没有也可以，而且不会限制实验部分起草；后续只要当前研究内容需要验证，就会对缺失项生成明确标记的参考实验，包括实验设置、候选数据集、对比/消融设计、模拟参考数据和结果分析，供用户补做实验或替换，不作为已完成项目事实。即使用户只提供部分实验数据，也可对缺失实验项继续生成参考内容。

#### 允许输出

只输出：

- 报告题目或暂定题目；
- 报告类型：科技项目结题技术报告（默认）；
- 内容生成依据模式：`source_grounded`、`model_autonomous`或“待用户选择”；
- 项目背景；
- 电网业务或技术场景；
- 总体问题初步理解；
- 目标读者；
- 报告用途；
- 一级研究内容及其技术子项；
- 进度计划中的技术研究、研发、实现和验证事项；
- 考核要求中的技术指标、功能、性能、测试条件和成果能力；
- 不进入技术正文的纯行政事项；
- 可使用材料；
- 已知数据和结果；
- 目标篇幅和格式；
- 特殊要求；
- 上述四项固定确认问题的已知答案或待补充状态；
- 除四项固定问题外，最多补充三项真正影响架构的缺失信息；缺失信息不得包含写作风格偏好，除非用户已明确要求改变默认报告类型。

#### 禁止输出

- 正式中心主旨；
- 论证架构；
- 完整目录；
- 章节计划；
- 正文；
- 摘要和结论。

#### 结束语

> 请一次性确认或补充以上项目档案及四项固定信息。四项均明确后，我再提炼中心主旨和论证架构。

### 阶段 B：建立中心主旨和论证架构

仅在项目档案确认后执行。

#### 允许输出

1. 一句话总体问题；
2. 关键挑战；
3. 先确认报告范围；总报告按来源顺序给出“课题名称—课题原始顺序—课题内研究内容小点—名词化技术章标题”映射，具体课题报告继续给出“一级研究内容—研究内容小点原文—小点原始顺序—名词化技术章标题”映射，并说明仅做了哪些语法整理；
4. 为每个技术章先规划无标题章首导入正文，再默认拆解并预设章内核心研究小点X.1、X.2、X.3；若来源覆盖确有必要则最小扩展到4—5个；逐项说明其研究内容、预期目标、进度计划或考核要求依据，以及电力对象/约束、具体计算技术、技术具体性依据、技术来源状态、技术作用和承接关系；
5. 给出第一章1.2.1国外研究现状与1.2.2国内研究现状的主题组织方案；两节围绕相同研究范围展开，但不再增加与技术章一一对应的四级标题；
6. 建立研究内容、进度计划技术事项和考核细则的内部全量覆盖矩阵，并先标记 `in-scope`、`shared-approved`、`excluded-other-task` 与 `administrative`；
7. 研究内容之间的依赖、协同或闭环关系；
8. 多项工作共同形成的总体能力；
9. 当前材料能够支持的结论边界；
10. 仍需后续补充的信息。

#### 禁止输出

- 正式目录；
- 篇幅预算；
- 章节正文。

#### 结束语

- `model_autonomous`模式：

> 请确认或修改以上中心主旨、研究内容—技术章节映射及细则覆盖关系。确认后，我再设计目录和篇幅。

- `source_grounded`模式：

> 请确认或修改以上中心主旨和章节映射。确认后，请按预计章节补充每章大概内容，再进入原目录生成阶段。

### 阶段 B2：基于已有内容生成时收集逐章内容概述

仅在`source_grounded`模式且论证架构已经确认后执行。该阶段位于目录生成之前，但不得改动本Skill原有目录规则。

#### 允许输出

按已确认的第一章固定结构、研究内容—技术章映射和总结章，列出逐章内容概述表，要求用户为每章提供：

- 本章已有内容大意，建议使用3—8句话；
- 已有方法、公式、系统模块或实现要点；
- 已有实验、数据、指标和结论；
- 希望重点展开或避免展开的内容；
- 没有现成内容时明确写“无”。

该阶段只收集内容依据，不生成目录，不重新设计章数，不改变第一章固定结构、技术章从第2章起的一一映射、无标题章首导入、X.1—X.N核心小点和总结章规则。后续逐章材料准备仍然执行，已经提供的内容不得重复询问。

#### 结束语

> 请按章补充或确认每章大概内容。全部章节概述明确后，我再按原有固定规则生成目录和篇幅。

## 10. 首轮回复固定规则

首次触发本 Skill 时，必须：

1. 简短说明将按阶段推进；
2. 读取用户材料并主动整理项目档案；
3. 输出项目档案草案；
4. 最多提出三项架构级缺失信息；
5. 若用户尚未明确，询问一次后续采用“基于已有内容生成”还是“交由大模型自行生成”；
6. 请求用户确认项目档案和模式选择；
7. 到此停止。

首次回复不得出现：

- 完整目录；
- 章节正文；
- 摘要草稿；
- “以下为完整报告”；
- 连续数千字的技术内容。

### 实验数据缺失时的用户说明口径（v1.1.7）

当项目档案识别到“没有实验数据”或“只有部分实验数据”时，不得把它描述为“因此验证/应用成效只能写成方案论证、案例化场景和预期效果”，也不得仅强调“不虚构实测数据”后停止。应明确说明：没有实测数据**不会限制实验部分起草**，后续将按 `references/experiment-evidence-layering.md` 生成完整的参考实验设置、数据集方案、对比方法、对比/消融等实验、模拟参考数据和结果分析，并用显式标签与真实项目证据区分，供用户后续补做或替换。

### 0.7 目录结构不是自由创作

目录阶段必须执行 `references/outline-hard-rules.md`。当前固定架构为：第一章整合项目背景与研究意义、国内外研究现状、主要研究内容及思路；技术章从第2章起；技术章章首采用无标题导入正文；随后固定X.1—X.N核心研究小点并以本章小结收束。

以下要求属于硬规则：

- 第一章必须且只能命名为“项目概述”，二级标题依次为“项目背景与研究意义”“国内外研究现状”“主要研究内容及思路”；
- 第一章三级标题固定为1.1.1“项目研究背景”、1.1.2“项目研究意义”、1.2.1“国外研究现状”、1.2.2“国内研究现状”、1.3.1“主要研究内容”、1.3.2“研究思路”；
- `1.3.1 主要研究内容`必须与技术规划书、任务书或等效技术文件中的当前报告范围研究内容逐项对应，并在不改变边界的前提下稍作展开；
- 不再单设“国内外发展现状”一级章，技术章从第2章起按报告范围分支：总报告一个课题对应一个技术章，具体课题报告一个来源研究内容小点对应一个技术章；
- 技术章一级标题后直接规划无标题章首导入正文，不设置“概述”“技术路线”“技术架构”等二级功能标题；
- 章首导入正文必须包含本章背景与意义、研究主题引入、概括性技术路线/架构和适合的图示；以5万字全文为基准目标约800—1200字，其他总字数按1.6%—2.4%同比例规划；
- 每个技术章默认设置X.1、X.2、X.3三个核心技术二级标题，分别对应章内核心研究小点；只有预期目标、进度技术点或关键研究事项确实过多且无法在不失真的情况下合理归并时，才允许最小扩展到4—5个核心二级标题；每个核心二级标题默认继续生成2—4个三级标题，窄技术点确需标题级覆盖时最多5个；
- X.1—X.N必须先定义共同 `shared_chapter_question`，再按明确的先后承接关系拆解；每个核心二级标题先确定原始具体技术，再形成用于目录显示的中文语义 `technical_signature` 后组装标题；英文模型名和英文缩写不得直接裸露在二、三级目录标题中，中文表达应能让读者大致判断技术路线而不是机械展开长译名。RAG、图神经网络、Transformer、强化学习等技术族以及Span抽取、双塔匹配、置信校准、参数更新等任务动作都不能单独体现创新；“基于具体技术签名的……”作为优先显化句式，目录阶段必须先按标题总数规划数量，使每个技术研究章以及全文二、三级技术标题的使用比例都处于40%—60%；同时技术研究章二、三级标题只以“技术/方法”收束，按每章约40%技术、60%方法以及全文技术结尾35%—45%独立规划；所有二、三级技术标题仍须独立保留电力领域语义；
- X.1—X.N每个核心二级标题都必须显式识别电力对象、业务场景或运行约束，并同时体现具体计算技术与技术作用；二级标题出现“的”时，“的”后完整主语必须独立带有强电力相关词；
- 目录生成时还必须为技术路线未被来源唯一锁定的核心研究点建立 `technology_option_sets`：每个核心二级研究点给出2—3个同问题、同作用、同章节边界下的可选技术，分别写明中文技术签名、关键机制、适配理由和推荐项；正式目录只采用推荐/确认的一项。来源已经唯一指定技术路线时 `source_locked=true`，可只列1个来源技术，不得虚构替代方案；
- 预期目标、进度计划及对应课题区域考核要求中的关键技术词必须通过 `heading_source_term_plan` 按“概括性→二级、窄技术点→三级”分散进入目录；内部技术性考核事项同时在所属技术章X.1—X.N正文中隐性覆盖；
- 先自动判定 `report_theme_type`；`non-evaluation` 主题的二、三级标题不得出现验证、评估、评价、测评、验收、测试、试验、实验类章节词，全部核心研究点后直接为本章小结；只有 `evaluation-related` 主题且存在大量成体系数据或用户明确要求，才可在全部核心研究点后增加一个评估/验证节并将本章小结再顺延1位；
- 本章小结统一执行 `references/chapter-summary.md`；目录阶段只登记其结构位置、编号与计划篇幅字段，不维护另一套正文规则；
- 最后一章必须为“总结”“总结与展望”或“结论”，只设置一个一级标题，不设置任何二级、三级或更低级标题；该章正文计划固定700—800字，建议 target_words=750、minimum_words=700；其后设置参考文献；
- 目录中一级、二级、三级标题原则上不超过25个可见字符；技术研究章二、三级标题必须优先保留具体技术签名并满足40%—60%“基于……的……”比例，必要时允许长度例外；评估类功能标题仅在 `evaluation-related` 主题中允许简洁命名，非评估主题不得以功能标题绕过禁用规则。

若目录草案不满足这些要求，不得提交给用户确认。能够运行脚本时，使用 `scripts/validate_outline.py` 校验后再输出。

### 0.8 技术章章首无标题导入、三个研究小点与小结是硬规则

每个技术章采用：

```text
# X 技术章标题
[无标题章首导入正文：背景与意义 + 研究主题 + 概括性技术路线/架构 + 图示]
## X.1 章内研究小点一
### X.1.1 ...
### X.1.2 ...
## X.2 章内研究小点二
### X.2.1 ...
### X.2.2 ...
## X.3 章内研究小点三
### X.3.1 ...
### X.3.2 ...
## X.N 必要时扩展的研究小点（N≤5）
### X.N.1 ...
### X.N.2 ...
## X.(N+1) 本章小结
```

章首导入正文不是编号小节，不得显示“概述”“技术路线”“技术架构”等标题。技术研究课题与工程实现课题的路线差异通过正文内容和图示体现，不再通过固定X.2功能标题区分。

核心研究小点必须从当前章来源研究内容、预期目标、进度计划和内部技术要求中拆解，共同形成完整技术链。默认用3个核心二级标题完成归并；只有确实存在无法在不失真的情况下归并的独立预期目标/进度技术点时，才最小增加第4或第5个核心二级标题，并逐项登记扩展来源与必要性。能下沉到三级标题或并入既有二级研究点的内容不得触发扩展。

以下要求必须执行：

- X.1—X.N分别按连续顺序登记 `research_subpoint_index`、`derivation_basis` 和来源事项编号；
- 核心二级标题及其技术类三级标题都必须独立表达“电力对象或业务约束 + 具体技术签名 + 技术作用”，不得出现纯计算机标题；二级标题“的”后完整主语必须有强电力词；“基于……的……”句式只显化技术路线，不能覆盖或替代电力领域语义；
- 每个核心二级节必须展开2—4个三级标题，目录确认后进入标题锁定清单；同一技术章内所有技术类三级标题的任务主语必须互不重复，“基于……的……”标题重点比较“的”之后的完整任务主语，直接复合标题则比较去除 `technical_signature` 后的电力对象/业务与技术作用；不得只替换前置算法而重复相同后半段职责；
- 全文所有技术章X.1—X.N逐项满足“电力对象/约束 + 具体计算技术 + 技术作用”，不再使用全局比例替代逐项检查；
- `non-evaluation` 主题在全部核心研究点后直接设置本章小结；仅 `evaluation-related` 主题启用独立评估/验证例外时，在核心研究点后增加一个评估/验证节，小结再顺延1位；
- 本章小结正文规则统一引用 `references/chapter-summary.md`；
- 章首导入继续按本阶段既有篇幅规则规划；本章小结篇幅统一由 `references/chapter-summary.md` 规定。

具体规则必须读取 `references/report-architecture.md`、`references/outline-hard-rules.md`、`references/technical-title-naming.md`、`references/three-subpoint-and-indicator-coverage.md` 与 `references/research-content-traceability.md`。

### 0.14 研究内容驱动的章节映射与全量覆盖

研究内容映射规则必须优先读取 `references/report-scope-chapter-mapping.md`，再读取 `references/research-content-traceability.md`，并贯穿项目档案、论证架构、目录、第一章研究现状、章节计划、正文、摘要和最终组装。

`当前报告范围 → task_book_scope → 课题与课题角色 → 一级研究内容与研究内容小点 → 映射单位 → 名词化章名 → 一个技术章节 → X.1—X.N核心研究小点 → 范围内进度技术与内部技术要求落点`

必须遵守：

- 总报告范围内有几个课题，就设置几个技术章节，顺序与课题原始顺序一致；具体课题报告按研究内容小点数量和原始顺序设置技术章；
- 第一章1.3.1必须把当前范围研究内容逐项写出并适度展开，内部映射与后续技术章保持一致；
- 总报告中一个课题只对应一个技术章，课题内多个小点下沉到该章X.1—X.N及三级标题；具体课题报告一个小点只对应一个技术章；
- 第一章1.2国外、国内研究现状的检索主题与技术章范围一致，但不再设置与技术章一一对应的四级标题；
- 每项内部技术性考核事项必须在所属技术章X.1—X.N正文或其三级标题中隐性覆盖；
- 其他课题或其他报告范围事项标记为 `excluded-other-task`，不得映射到任何章节；只有经用户确认的共用基础可标记为 `shared-approved`；
- 纯管理事项可不进入技术正文，但必须登记处理方式；不得为追求覆盖而虚构技术内容或完成结果。

内部必须维护 `research_content_coverage`。来源性名称和编号只保存在内部映射中，正式正文按独立报告口吻表达。

### 阶段 C：生成目录和篇幅预算

仅在论证架构确认后执行；`source_grounded`模式还必须完成逐章内容概述确认。

目录必须先套用 `references/outline-hard-rules.md` 与 `references/report-architecture.md`，再执行报告范围映射、技术标题命名、研究内容追溯和三个研究小点覆盖规则。不得从空白开始自由设计。

- `1.3 主要研究内容及思路`，固定下设`1.3.1 主要研究内容`和`1.3.2 研究思路`；

- 最后一章“总结/总结与展望/结论”（仅一级标题，正文700—800字）和参考文献。

第X章 技术章标题

  X.2 核心技术二级标题

  X.3 核心技术二级标题

    X.N.2 具体三级标题二

第一章结构、技术章核心研究点与本章小结、最后一章和参考文献属于固定项。技术章核心研究点数量默认3个，仅来源化覆盖确有必要时扩展到4—5个。最后一章的固定形态是“单一一级标题 + 700—800字连续正文”，不得再拆二三级标题。`non-evaluation` 主题不得出现独立实验、测试、应用验证或评估类二级/三级节；`evaluation-related` 主题的此类节也只是条件例外，不是固定项。

- 摘要或总结成稿。

### 阶段 C2：参考文献检索与第一章国内外研究现状组织

仅在目录确认后执行，且必须在第一章章节计划之前完成。

目录确认后，应先在内部初始化 `abstract_evidence`，不得提前生成摘要正文。

#### 网络可用时

1. 根据已确认的技术章映射单位制定第一章1.2国内外研究现状的检索主题、技术缺口和文献检索式；
2. 搜索原始论文、标准、官方文档和数据集说明；
3. 打开论文或权威落地页，核验题名、作者、出版物、年份、DOI或稳定标识；
4. 判断论文原文是否真正支持拟写入正文的结论；
5. 将文献分为奠基工作、近期进展、最接近工作和比较基线；
6. 国外研究现状和国内研究现状均围绕当前报告范围内主要技术主题说明代表性路线、已有进展和不足，不再设置与技术章一一对应的额外四级标题；
7. 在生成第一章1.2正文前锁定作者指代样式：`author_et_al`对应“XXX等人”，`author_team`对应“XXX团队”；默认使用 `author_et_al`，两节必须一致；

# 一级标题与首个二级标题之间的无标题过渡正文规则

本文件统一约束报告正文中一级标题与其后首个二级标题之间的正文过渡。目标是避免出现“一级标题下一行立即接二级标题”的空壳章节结构。该规则作用于正文生成与最终审核，不改变已确认目录中的标题层级。

## 1. 通用硬规则

只要某一级章节下存在二级标题，一级标题之后就必须先出现一段或若干段**无标题正文**，再进入该章第一个二级标题。不得出现以下结构：

```text
# 第1章 项目概述
## 1.1 项目背景与研究意义
```

应改为：

```text
# 第1章 项目概述

[无标题过渡正文]

## 1.1 项目背景与研究意义
```

无标题过渡正文必须承担实际内容作用，不能只写“本章主要介绍以下内容”“本章分为三节”等目录复述。

## 2. 第一章及一般非技术章节

第一章“项目概述”以及其他没有更长章首导入专项规则、但确实存在二级标题的非技术章节，一级标题与首个二级标题之间的无标题过渡正文控制在 **50—100字**。

这50—100字应优先完成以下任务：

- 概括本章要回答的总体问题；
- 说明本章各部分为什么需要放在同一章中；
- 自然引出后续二级内容，但不逐条复述二级标题名称；
- 与全文目标建立必要联系。

不得用空泛套话、章节编号清单或“首先/其次/最后”机械复述目录来凑满50—100字。

## 3. 技术章节的更具体规则优先

第2章起的技术章节已经执行“章首无标题导入正文”专项规则。以5万字报告为基准，该部分约800—1200字，因此天然满足“一级标题与首个二级标题不得相邻”的要求。

技术章节**不得为了满足本文件再额外插入一段50—100字短引言**，也不得把原有800—1200字章首导入压缩成50—100字。技术章继续执行 `references/report-architecture.md`、`references/technical-chapter-generation.md` 中更具体的章首导入规则。

## 4. 最终总结章例外

最终“总结 / 总结与展望 / 结论”章不设置二级标题，因此本规则不适用。该章继续执行 `references/conclusion-and-outlook.md` 的单一级标题规则。

## 5. 生成与验收

正文生成前应在章节计划中明确 `heading_bridge_requirement`：

- `short_50_100`：第一章或一般非技术章节；
- `technical_chapter_intro`：技术章，使用既有长章首导入；
- `not_applicable`：没有二级标题的章节。

正文展示给用户前必须检查：

1. 一级标题后是否先有正文而不是直接出现二级标题；
2. `short_50_100` 模式下正文是否为50—100字；
3. `technical_chapter_intro` 模式下是否保留原长篇章首导入规则；
4. 过渡正文是否有真实内容，而不是目录复述。

# 技术章“本章小结”统一规则

> 本文件是 `power-grid-technical-report-writer` 中“本章小结”正文内容、篇幅、生成和验收的**唯一权威规则源**。
> 其他阶段文件、架构文件、模板和预检文件只保留结构位置、调用时机或字段登记，并统一引用本文件；不得复制另一套小结正文规则。

## 1. 适用范围与概念边界

本文件只适用于第2章起各技术章节末尾的“本章小结”，不适用于全文最后一章“总结 / 总结与展望 / 结论”。最终总结章继续执行 `references/conclusion-and-outlook.md` 的“单一一级标题 + 700—800字连续正文”规则。

本章小结属于技术章的功能性收束标题，不属于 X.1—X.N 核心技术研究小点，不参与核心技术标题的“电力对象 + 中文技术签名 + 技术作用”完整关系检查，也不计入“基于……的……”40%—60%标题比例。

## 2. 结构位置与编号

每个技术章必须以本章小结结束：

- 默认结构为“无标题章首导入正文 + X.1—X.N核心研究小点 + X.4本章小结”；若因预期目标确实过多而扩展到N=4—5个核心研究点，则本章小结顺延为X.(N+1)；
- `non-evaluation` 主题在全部核心研究点之后直接设置本章小结，不得设置验证/评估/测试/实验类二三级标题；只有 `evaluation-related` 主题且存在大量成体系数据或用户明确要求独立评估/验证节时，才允许在核心研究点之后增加该节，本章小结再顺延1位；
- 不得为了形式完整额外增加核心技术二级标题；只有预期目标/进度技术点无法合理归并时才允许最小扩展到4—5个，并必须可追溯；
- 本章小结不得代替 X.1—X.N 对内部技术要求、实验结果或技术主张的正文覆盖。

## 3. 章节计划与篇幅

章节计划阶段必须把本章小结作为独立生成单元进行规划，并登记开头“总”、中部“分”和结尾“总”各自需要覆盖的内容，以及可直接用于小结的实验数据、性能结果、规模数据或前文技术分析结论。

本章小结采用固定篇幅控制：

- 正文总体控制在 **500—600字**；
- 开头“总”控制在 **100—150字**；
- 中部“分”以 **约300字** 为目标，通常控制在约280—330字；
- 结尾“总”控制在 **100—150字**；当本章实验结果较丰富、需要集中说明多组关键结果时，结尾可以酌情增加，但整篇小结仍应优先控制在500—600字内；
- 本章小结执行本文件的固定篇幅规则，不再使用普通章节“计划字数×80%”作为最低篇幅判定；
- 不得通过重复背景、重复目录、空洞过渡、无效列表或无技术意义数字凑篇幅。

## 4. 生成时机与确认门

分节生成时：

1. 不得在 X.1—X.N 任一核心小节末尾提前生成整章小结；
2. 全部核心研究小点以及已启用的独立验证节全部完成并确认后，再单独生成“本章小结”；
3. 本章小结通过固定篇幅、内容和审核门禁并得到确认后，当前技术章才可进入 `CHAPTER_CONFIRMED`。

整章生成模式同样必须把本章小结作为章节最后的独立收束部分，不得在中途反复总结整章。

## 5. 正文组织：总—分—总

本章小结必须采用“总—分—总”的连续论述结构，优先写成三个自然段，不写成汇报式清单。

### 5.1 开头“总”：100—150字

简洁总述：

- 本章研究对象和研究主题；
- 需要解决的核心电力技术问题；
- 本章形成的总体技术成果或总体能力；
- 在总体技术成果或总体能力之后，用一句简洁的话说明本章方法相较传统方法、常规方案或已有处理方式体现出的主要优势，例如在信息利用、特征表达、适配能力、推理链完整性、计算效率、鲁棒性或业务可用性方面的改善。

比较优势必须与本章实际技术路线相匹配，不要展开成国内外现状比较，也不要在开头重新大段重复章首背景或逐条复述目录标题。

### 5.2 中部“分”：约300字

围绕 X.1—X.N 核心研究小点依次归纳主要成果，并用有承接关系的连续表述串成一条成果链。每一项应尽量同时包含：

- 具体形成了什么技术能力、模型、方法、数据/知识产物或工程能力；
- 与该成果直接对应的**普通实验结果**，包括对比实验、消融实验、敏感性、鲁棒性、泛化性、效率或常规性能测试中的代表性数据；这些结果优先放在中部，并紧跟对应方法说明“采用了什么技术 → 得到什么数值/现象 → 说明该方法在哪一方面更有效”；
- 与前后研究小点之间的输入输出、承接、融合或补偿关系；
- 中部可以自然覆盖一般性能要求，但**任务书中特别提出、需要在章末集中体现的目标或要求不要在中部重复展开**，统一留到结尾“总”结合对应方法和结果进行综合说明；正文不得出现“预期目标”“考核指标”“考核要求”“指标完成情况”等来源化或验收化措辞。

中部的“分”是成果归纳，不是把 X.1—X.N 标题换句话再写一遍。各研究点应按照真实技术链组织，例如“形成基础表示 → 完成关键推理/识别 → 实现后续优化/决策/应用”，避免三段互不相干的并列罗列。

### 5.3 结尾“总”：100—150字

综合收束：

- 各核心研究成果如何共同形成完整技术链；
- 对项目总体目标的支撑；
- 对电网设备、运行状态、调度业务、运检业务或工程应用的实际意义；
- 若任务书、技术规划书或用户材料对本章**特别提出了明确目标、性能要求或验收关注点**，优先在结尾集中覆盖：直接写对应方法、代表性结果和效果，不说明这些内容“来自任务书/属于指标”，而是自然呈现“采用什么方法 → 取得什么效果 → 相比传统方法、常规方案或基线的优越性体现在哪里”；
- 普通对比、消融、敏感性等实验结果原则上已经在中部随X.1—X.N归纳；结尾只选择与本章总体贡献、特别目标/要求最相关的关键数据再次综合，不把所有表格数值重复一遍；当本章实验数据较为丰富时，可适当增加结尾篇幅；
- 当没有可直接引用的实验数据时，根据前文技术原理、方法设计、流程分析和已有结果综合归纳本章在哪些性能维度上形成提升，例如准确性、鲁棒性、泛化能力、迁移适配能力、推理可靠性、处理效率、知识利用能力或工程可用性；重点解释**方法为什么优于传统方法或常规方案**以及这种优势如何转化为当前电力业务效果，不编造精确数值。

结尾不再额外展开限制、缺点、未完成事项或待验证事项，也不使用“尚不能、仍不足、受限于”等防御性收束来削弱本章已经形成的技术贡献。

## 6. 实验结果、模拟数据与章末统一说明

本章小结允许直接使用本章实验部分已经出现的数据，并按“方法—结果—效果”进行归纳：

- **第二段中部**按核心二级研究点归纳普通实验效果：每个X.i最多选择1个最具代表性的指标进入本章小结，并与具体技术机制绑定解释；某节没有实验或没有可靠量化结果时不强行写指标，改用定性技术效果归纳。正文实验可以展示多个指标，但单个实验分析正文最多重点解释2个；
- **第三段结尾**只有在当前章属于最后一个技术章节时，才将任务书硬指标自然转写为对应的实际结果和技术效果并集中承接；写自然结果和业务意义，不复述“超过××、不低于××、小于××”等任务书阈值句式，不出现“指标要求、目标值、考核完成、满足要求”等验收口吻；其他技术章仅收束本章自己的技术指标，不提前承担最后技术章的硬指标集中说明；
- 若实验结果来自模型生成的模拟实验，第二、第三段都可以直接使用这些数值进行正常结果分析，**不需要在每个数值前后反复写“模拟”“参考”**；
- 若本章实际使用了模型生成的模拟实验数据，在“本章小结”三段正文之后、整章最末尾增加一次统一说明即可；该说明不计入小结500—600字；
- 推荐说明：`说明：本章未由实际材料提供的实验数据为模拟生成数据，用于实验设计与结果展示，后续可根据实际实验结果替换。`
- 若本章实验数据全部来自用户材料、已核验来源或真实实验，则不添加上述说明；
- 定量内容始终服务于技术贡献表达，不得把“本章包含几个小节、提出几个方法、形成几个模块、包含多少图表公式”等结构数量当作技术成果。

## 7. 表达与叙述要求

本章小结默认使用连续自然段，不写成“第一点、第二点、第三点”的汇报提纲，也不使用大量项目符号替代论述。

必须避免：

- 在正文中用中文引号、英文引号、书名号反复包裹技术词、概念名、方法名、结论性短语或所谓“亮点”；默认直接写技术名称和结论。只有必须保持原文名称、标准条款原句或不可替代的直接引用时才保留引号；
- 逐节复述目录；
- 只写“完成了……、实现了……”而没有技术内容；
- 只做价值拔高而没有成果落点；
- 使用章节数量、标题数量等无技术意义数字；
- 使用“任务书要求、考核指标、课题X、最终材料”等外部来源口吻；
- 使用“上一章、下一章、第X章”等具体跨章互引；
- 引入正文完全没有涉及的新技术或新应用。

需要衔接时直接使用技术对象、研究内容或“本文、前述方法、在此基础上”等自然表达。

## 8. 电力领域落点

小结必须让读者明确知道技术成果作用于什么电力对象、运行状态、业务过程或工程场景。结论不能只停留在通用计算机能力，如“提高了准确性”“增强了鲁棒性”，还应说明这种性能提升对当前电网研究对象、运检流程、调度决策或工程应用产生了什么实际作用。

## 9. 数据、语料与知识构建类章节专项补充

当当前章属于数据、语料或知识构建类章节时，中部成果归纳还应覆盖：

1. 解决了哪些电力数据、语料或知识缺口；
2. X.1—X.N 如何形成连续的数据/知识技术链；
3. 形成了什么可复用的数据、语料、知识图谱、规则库、索引或知识产物；
4. 哪些质量、完整性、覆盖度、检索效果或下游应用结果能够说明这些产物的技术价值。

不得因为该类章节偏数据工程，就省略整体技术成果、结果依据和电力应用意义。

## 10. 展示前检查

本章小结展示或提交审核前至少检查：

1. 是否位于技术章最后，编号是否为默认 X.4 或验证例外下的 X.5；
2. 是否采用“总—分—总”连续正文，且开头约100—150字、中部约300字、结尾约100—150字；
3. 全文是否控制在500—600字；
4. 开头是否说明总体成果，并用一句话概括相较传统方法的主要优势；
5. 中部是否分别归纳 X.1—X.N 的成果，并自然覆盖原有目标和性能要求而不暴露“指标/目标/考核”来源化措辞；
6. 中部是否体现各研究点之间的承接关系，而不是并列复述标题；
7. 每个核心二级研究点是否最多只选择1个代表性效果指标进入小结；无实验研究点是否没有强塞指标；若为最后技术章，结尾是否自然覆盖任务书硬指标对应的实际结果与效果且未复述阈值式验收口吻；没有实验数据时，是否根据前文分析明确归纳提升了哪些性能及其原因；
8. 是否明确体现电力对象、业务或工程意义；
9. 是否避免额外写限制、缺点、待验证事项或“做不到什么”的防御性内容；
10. 如本章使用了模型生成的模拟实验数据，是否只在小结正文之后、整章最末尾统一提示一次，而没有在每个实验标题、表题、数值或结果句中反复强调“参考/模拟”；
11. 是否避免外部来源口吻、跨章编号互引和无技术意义数字。
12. 本章小结正文是否基本不用引号包裹技术词、概念名或结论性短语；如存在引号，是否确有保留原文名称、标准条款或直接引用的必要。

任一关键项不满足时，应修改本章小结后再进入章节审核或用户确认。

# 报告总体架构规则

本文件规定科技项目结题技术报告的一级、二级、三级固定结构。目录阶段必须先套用本架构，并优先读取 `report-scope-chapter-mapping.md` 判断总报告或具体课题报告，再补充技术章节。不得改变下列骨架。若用户明确要求其他整体结构，应在项目档案中记录结构例外，而不是由模型自行漂移。

## 1. 全文固定骨架

```text
图、表目录条目（排版阶段直接续接主目录，不显示独立“图目录”“表目录”标题）

第1章 项目概述
  1.1 项目背景与研究意义
    1.1.1 项目研究背景
    1.1.2 项目研究意义
  1.2 国内外研究现状
    1.2.1 国外研究现状
    1.2.2 国内研究现状
  1.3 主要研究内容及思路
    1.3.1 主要研究内容
    1.3.2 研究思路

第2章起 按报告范围映射的技术章节
  [章节标题后的无标题章首导入正文]
  X.1 章内研究小点一
  X.2 章内研究小点二
  X.3 章内研究小点三
  X.4 本章小结（默认）

最后一章 总结 / 总结与展望 / 结论
参考文献
```

第一章不得命名为“引言”“绪论”或单独的“概述”，必须使用“项目概述”。国内外研究现状不再单独设置为第二章；技术章节从第2章开始编号。

## 2. 第一章“项目概述”

第一章二级标题必须且仅采用以下三节，并按顺序排列：

1. `1.1 项目背景与研究意义`；
2. `1.2 国内外研究现状`；
3. `1.3 主要研究内容及思路`。

第一章三级标题固定为：

```text
1.1.1 项目研究背景
1.1.2 项目研究意义
1.2.1 国外研究现状
1.2.2 国内研究现状
1.3.1 主要研究内容
1.3.2 研究思路
```

不得在第一章增加与上述结构并列的其他二级标题；确需进一步细分时优先通过自然段、表格或图示完成，不默认扩展到四级标题。

第一章一级标题“第1章 项目概述”之后不得立即出现 `1.1`。必须先写50—100字无标题过渡正文，再进入 `1.1 项目背景与研究意义`。具体执行 `references/heading-transition.md`。

### 2.1 项目背景与研究意义

#### 2.1.1 项目研究背景

从电力业务场景、运行对象、现实约束、已有能力和待解决问题出发，说明项目开展的技术与工程背景。背景应服务于后续研究主题，不写成长篇政策罗列或通用技术发展史。

#### 2.1.2 项目研究意义

围绕项目解决上述问题后能够形成的技术能力、工程价值、业务作用和可验证改善说明研究意义。不得只写宏观口号，也不得提前把尚未验证的目标写成已完成成果。

### 2.2 国内外研究现状

固定采用：

```text
1.2.1 国外研究现状
1.2.2 国内研究现状
```

两节围绕当前报告范围内的主要技术主题，分别说明代表性路线、已有进展、可核验成果和仍存不足。作者指代样式必须统一：默认使用“XXX等人”，经计划确认后也可统一使用“XXX团队”。机构、标准组织使用正式名称。不得逐篇文献机械罗列，不得虚构无法核验的文献事实。

研究现状的技术主题必须与后续技术章节覆盖的研究内容一致，但不再要求设置与技术章一一对应的额外三级标题，也不得为了映射技术章而扩展到四级标题。每一节内部通过自然段按技术主题组织即可。

### 2.3 主要研究内容及思路

#### 2.3.1 主要研究内容

本节必须与技术规划书、任务书或等效技术文件中属于当前报告范围的“研究内容”保持对应。要求：

- 按来源研究内容的原始顺序组织，不合并、不遗漏、不跨课题借用；
- 不能只复制标题，应在每项研究内容后稍作展开，说明研究对象、拟解决问题、主要技术方向和预期形成的能力或产物；
- 展开只允许使用来源材料、用户确认信息或后续技术章已确认的技术边界，不得新增无依据算法、数据、指标或完成结果；
- 总报告应覆盖全部课题范围内研究内容，具体课题报告仅覆盖当前课题研究内容。

#### 2.3.2 研究思路

说明研究内容之间的总体逻辑、依赖关系、输入输出关系、关键处理链和研究推进思路。应回答“各研究内容为什么这样衔接、整体如何从问题走向技术实现与验证”。适合时应配置总体研究思路图或技术关系图。该节不承担逐章目录复述功能，正文原则上不使用“第二章、第三章”等章节编号说明全文结构。

## 3. 课题角色与技术章节映射

目录生成前必须先按任务材料区分课题角色。前序课题均按技术研究组织，最后一个课题固定按工程实现组织，通常承担系统研发、平台实现、集成部署、示范应用或工程验证。每个研究内容小点继承所属课题角色。

技术章节从第2章起编号，并先读取 `task_book_scope`，不得由模型自由设计章数。

总报告执行：

```text
课题原始顺序与课题角色
→ 课题名称及课题内全部研究内容小点
→ 必要的名词化与标题用词整理
→ 一个技术章节
```

- 有几个课题就设置几个技术章；
- 一个课题只承担一个技术章，不得拆分或合并课题；
- 课题内多个研究内容小点默认归并到该章X.1—X.3，并在确有来源覆盖需要时最小扩展为X.1—X.N，再通过其三级标题展开。

具体课题报告执行：

```text
所属课题与课题角色
→ 研究内容小点原文
→ 必要的名词化与标题用词整理
→ 一个技术章节
```

- 有几个研究内容小点就设置几个技术章；
- 技术章顺序与小点原始顺序一致；
- 一个技术章只承担一个研究内容小点；
- 不得把多个小点合并成一个章，也不得把一个小点拆成多个章。

以下规则对总报告和具体课题报告均适用：

- 不得把其他课题的小点、进度技术、指标、数据、案例或成果写入当前章；
- 章标题不得增加当前映射单位来源标题没有提及的对象、算法、能力、指标或结论；
- 技术研究课题标题不得把“机制、建模、体系、定义”作为独立命题、中心名词或落脚点，也不得机械改名；应直接描述实际采用的具体技术、方法、算法或模型；`report_theme_type=non-evaluation` 时，二、三级标题另外禁用验证、评估、评价、测评、评测、验收、测试、试验、实验类章节词；
- 工程实现课题标题应落到系统、平台、架构、模块、接口、部署、集成或应用能力。

## 4. 技术章标题的名词化整理

当前映射单位的来源标题已经是名词性技术短语时，直接作为章标题。若原文带有任务动作词，应仅做语法整理，不做内容扩写。

允许删除开头的“研究、开展、研发、构建、建立、提出、实现”等任务动作词，或调整少量语序使标题能够独立成立。禁止在原文之外增加新的电力对象、人工智能方法、评价性限定词、进度计划、考核指标或实验结果。

## 5. 技术章章首无标题导入正文

技术章不再设置“X.1 概述”和“X.2 技术路线/技术架构”等功能性二级标题。章节一级标题之后直接进入一段或若干自然段的章首导入正文，随后再进入核心二级标题。核心二级标题必须与当前一级标题的研究对象、核心问题和核心输出形成直接父子逻辑：每个二级标题都应是完成该一级标题研究主线所必需的直接子问题、关键步骤或核心输出。判断重点不是标题里是否出现“数据处理、模型优化、系统实现、性能分析”等词，而是该标题承担的研究任务是否属于本章主线；即使技术上相关，若只是项目外围内容、相邻章内容或后续章可独立成立的研究任务，也不得放入本章。

章首导入正文必须同时包含：

1. 简要背景介绍：说明本章研究对象、应用/工程场景、现实问题和研究价值，作用类似第一章的“背景与研究意义”，但聚焦本章主题，不重复第一章；
2. 研究主题引入：明确本章要解决的核心技术问题、目标能力、主要输入输出和适用边界；
3. 概括性技术路线：用连贯文字说明主要处理阶段、关键模型/算法/模块关系、输出与反馈；
4. 图文结合：技术关系适合可视化时，优先安排技术路线图、总体架构图、数据流/知识流/控制流图或研究思路图。

章首导入不设置任何“概述”“技术路线”“技术架构”二级标题，也不计入X.1—X.N核心研究小点。

篇幅按全文计划字数同比例规划：以5万字报告为基准，章首导入正文目标约800—1200字，即约占全文计划字数的1.6%—2.4%。其他总字数按该比例折算。该范围用于篇幅规划和生成控制，具体可结合章节复杂度小幅调整，但不得缩成几十字的形式性开场。

## 6. 技术章三个核心研究小点

每个技术章正文结构为：

```text
[无标题章首导入正文]
X.1 章内研究小点一
X.2 章内研究小点二
X.3 章内研究小点三
X.4 本章小结（默认）
```

默认由X.1、X.2、X.3形成核心技术二级标题。只有当前章预期目标、进度技术点或关键研究事项确实无法合理归并时，才允许最小扩展为4—5个核心技术二级标题，并逐项记录新增标题的来源依据。全部研究小点从当前章研究内容、预期目标、进度计划和内部技术要求中拆解，共同覆盖本章完整技术链。二级标题完整说明电力对象或约束、具体技术签名和作用，禁止纯计算机标题。三级技术标题与二级标题执行同等级的“双显化”要求：每个三级标题都必须独立写出可识别的电力对象/业务/运行约束，以及具体模型/算法变体、关键机制、约束或组合方式；不能只写Span抽取、双塔匹配、实体识别、置信校准、样本重加权、参数更新等任务动作，也不能依赖上位标题补足电力语义或技术签名。

先判定 `report_theme_type`。`non-evaluation` 主题不设置任何验证、评估、评价、测评、评测、验收、测试、试验、实验类二级或三级节；有限测试条件、量化结果和边界分析转写为精度、可靠性、时延、工况适应性、性能边界、集成能力等技术语义并嵌入X.1—X.N正文，本章小结位于最后一个核心研究点之后。只有 `evaluation-related` 主题且数据量大、分析体系独立，或用户明确要求时，才允许在最后一个核心研究点之后增加一个评估/验证类二级节，并记录例外原因，本章小结再顺延一位。

## 7. 核心二级标题与三级标题

技术章X.1—X.N章内核心研究小点标题按核心技术标题管理。标题应：

- 只服务当前技术章对应的研究内容范围；
- 全部核心标题共同覆盖预期目标、进度计划主要技术和考核要求；
- 每个标题体现电力对象或业务约束、具体人工智能/数据/知识/算法/系统技术和实际作用；
- 不得为了满足形式要求添加来源没有支持的术语；
- 不使用“关键技术、核心方法、技术实现、模型研究”等低信息标题；
- 技术研究课题标题不得把“机制、建模、体系、定义”作为独立命题、中心名词或落脚点；`non-evaluation` 主题二、三级标题不得出现验证/评估/评价/测评/评测/验收/测试/试验/实验类章节词；
- 二级标题必须完整说明对象、具体 `technical_signature` 和作用；每个三级技术标题也必须独立显化自己的 `technical_signature`，不得只继承上位标题的具体性。
- 每个核心二级标题还必须显式包含具有区分度的细粒度计算机/人工智能技术；“人工智能、机器学习、深度学习、神经网络、大模型、优化算法”等上位概念不能承担创新技术角色，RAG、图神经网络、Transformer、强化学习等技术族名称也不能直接作为最终粒度；Span抽取、双塔匹配、置信校准、样本重加权、参数更新等操作名称同样不算技术签名，必须继续明确具体模型/算法变体、结构、机制、约束或组合方式；“基于具体技术签名的……”实行40%—60%双向硬门禁，但句式比例不能替代电力领域语义；每个技术研究章及全文二、三级技术标题的使用比例均必须处于40%—60%，且每条技术标题都必须独立保留电力对象/业务/运行约束，其余标题采用“电力对象/约束 + 直接复合技术签名 + 技术作用”表达；
- X.1—X.N必须围绕同一 `shared_chapter_question` 形成先后承接链；默认三节结构下，X.2利用X.1产出，X.3进一步利用前序产出完成后续推理、优化、决策、集成或验证。

本章小结属于功能性标题，不适用核心技术标题的对象—方法—作用完整关系要求。有限测试与结果分析优先作为X.1—X.N下的具体三级标题；仅在满足例外条件时，实验设置、实验结果、系统测试或应用验证可单设二级功能标题。

## 8. 三级标题和结构差异

核心二级标题数量默认3个，来源目标过多且无法合理归并时最小扩展到4—5个。章节差异通过三级标题、公式、图表和嵌入式证据安排体现：

- X.1—X.N必须分别展开默认2—4个三级标题；仅当窄技术点或预期目标确需标题级覆盖时，单个核心研究点最多扩到5个；
- 各核心二级节的三级标题数量可以不同，但编号必须从1开始连续；
- 不得机械复制三个核心标题的内容和三级结构，也不得以避免对称为由省略某一组；
- 三级技术标题用于独立算法、模型、具体方法、组件、接口或处理阶段，必须来自当前研究边界，并独立显化具体技术签名；只有 `evaluation-related` 主题的评估/验证类三级标题可按其实际评价对象保持相对简洁，`non-evaluation` 主题不得使用此类章节词。

## 9. 范围隔离与全量覆盖

每章只允许使用当前报告范围内与本章研究内容相关的内容，以及经用户明确确认的共用基础。任务材料中其他课题、专题或报告范围的研究内容、方法、指标、数据、案例和成果不得进入标题、正文、公式、图表、实验或结论。

本章范围内的预期目标、进度计划和内部技术要求必须具有明确落点。相关要求必须进入所属技术章X.1—X.N正文或其三级标题，并转写为报告自身的技术目标、设计约束、性能描述、适用条件、结果证据和能力边界。正式正文不得出现“任务书”“考核指标”“考核要求”“考核细则”“规定指标”或内部编号。不能把缺失的实现或结果写成已完成事实。

## 10. 本章小结

每个技术章必须以“本章小结”结束。`non-evaluation` 主题的小结编号位于最后一个核心研究点之后；仅 `evaluation-related` 主题按合法例外设置独立评估/验证二级节时再顺延一位。

本章小结的结构位置、篇幅、总—分—总组织、成果归纳、实验结果使用方式、生成时机与验收统一执行 `references/chapter-summary.md`。本文件不再维护另一套小结正文规则。

## 11. 全文核心标题逐项电力语义

所有技术章X.1—X.N逐项执行“电力对象/业务场景/运行约束 + 具体计算技术 + 技术作用”要求，不再以全局比例作为通过条件。每个标题都必须让读者仅从标题本身识别其电力研究对象或约束；已经出现明确领域对象时不机械重复“电力”二字。

## 12. 最后一章与参考文献

最后一章只能使用“总结”“总结与展望”或“结论”，按总体目标收束，不按章节编号逐章复述。最后一章只有一级标题，一级标题下直接组织连续自然段，不得再设置二级、三级或更低级标题。正文有效字数固定为700—800字，不随全文目标字数同比例放大。最后一章后必须设置参考文献。

## 13. 标题长度与实验类功能标题

目录标题原则上不超过25个可见字符。实验、评价指标、实验设置、数据集、测试环境和结果分析等功能性标题可以直接、简洁，不需要人为扩展成复杂技术句。简洁标题只适用于功能性二级/三级位置，不适用于X.1—X.N核心技术标题。技术研究章二、三级标题执行“电力领域语义显化 + 中文技术签名显化 > 40%—60%基于句式比例 > 25字符原则”，若压缩会损失技术签名或破坏比例，可保留超长标题并记录例外；当前映射单位的来源标题过长且无法安全缩短时，一级技术章标题也可记录例外理由。

## 14. 目录提交前检查

提交目录前至少检查：

1. 第一章是否准确命名为“项目概述”；
2. 第一章二级标题是否依次且仅为“项目背景与研究意义”“国内外研究现状”“主要研究内容及思路”；
3. 第一章三级标题是否准确为1.1.1“项目研究背景”、1.1.2“项目研究意义”、1.2.1“国外研究现状”、1.2.2“国内研究现状”、1.3.1“主要研究内容”、1.3.2“研究思路”；
4. 1.3.1是否与技术规划书/任务书研究内容逐项对应并作适度展开；
5. 技术章是否从第2章起按报告范围映射：总报告数量和顺序与课题一致，具体课题报告与研究内容小点一致；
6. 技术章标题是否仅由当前映射单位来源标题进行必要名词化整理，没有添加额外信息；
7. 技术章一级标题后是否直接规划无标题章首导入正文，且没有“概述”“技术路线/技术架构”二级标题；
8. 章首导入是否规划背景、研究主题、概括性技术路线和适合的图示；5万字报告是否按约800—1200字规划；
9. 是否默认设置三个核心研究小点，扩展到4—5个时是否有必要且可追溯的来源依据，并共同覆盖预期目标、进度计划主要技术和内部技术要求；
10. 技术研究章节标题是否避免把“机制、建模、体系、定义”作为独立命题、中心名词或落脚点，并避免机械改名；是否已判定 `report_theme_type`，且非评估主题二、三级标题无验证/评估/测试/实验类章节词；
11. 二级、三级技术标题是否都独立同时显化电力领域语义和具体中文语义 `technical_signature`；目录中的英文技术名/缩写是否已转换为能说明路线的中文技术表达；是否避免“Span抽取、双塔匹配、置信校准、参数更新”等任务动作充当技术点；每个技术研究章及全文二、三级技术标题中，“基于具体技术签名的……”句式占比是否均处于40%—60%的硬区间；
12. 是否排除了其他课题内容；
13. 是否默认未设置独立评估/验证二级节；若设置，是否同时满足 `evaluation-related` 主题及大量数据或用户明确要求的记录；
14. 是否设置本章小结，并已按 `references/chapter-summary.md` 完成统一规划与检查；
15. 最后一章是否只保留一级标题且正文控制在700—800字；
16. 是否设置最后一章和参考文献。

能够运行脚本时，使用 `scripts/validate_outline.py` 对结构化目录进行内部校验。校验失败时先修正，不向用户输出独立审查报告。

# 目录结构硬规则：第一章整合研究现状、技术章无标题导入与三个研究小点

本文件约束目录阶段和章节计划阶段，优先级高于通用目录建议。必须严格执行。若用户需要其他整体结构，应在项目档案中记录明确例外，不得由模型自行漂移。

```text
中文摘要
英文摘要（按需）
图、表目录条目（由排版子 Skill 直接续接主目录，不显示独立“图目录”“表目录”标题，也不作为正文一级章节）

第1章 项目概述
  1.1 项目背景与研究意义
    1.1.1 项目研究背景
    1.1.2 项目研究意义
  1.2 国内外研究现状
    1.2.1 国外研究现状
    1.2.2 国内研究现状
  1.3 主要研究内容及思路
    1.3.1 主要研究内容
    1.3.2 研究思路

第2章起 按报告范围映射的技术章节
  [章节标题后直接写无标题章首导入正文]
  X.1 章内研究小点一
  X.2 章内研究小点二
  X.3 章内研究小点三

最后一章 总结 / 总结与展望 / 结论

附录（按需）
```

第一章不得命名为“引言”“绪论”或单独的“概述”。不得再设置独立的“国内外发展现状”一级章。

## 2. 第一章固定结构

第一章二级和三级标题必须严格采用：

```text
1.1 项目背景与研究意义
  1.1.1 项目研究背景
  1.1.2 项目研究意义
1.2 国内外研究现状
  1.2.1 国外研究现状
  1.2.2 国内研究现状
1.3 主要研究内容及思路
  1.3.1 主要研究内容
  1.3.2 研究思路
```

不得增加其他并列二级标题，不默认扩展四级标题。第一章一级标题后必须先规划50—100字无标题过渡正文，再进入 `1.1`；不得让一级标题与首个二级标题直接相邻。技术章继续执行既有800—1200字章首无标题导入，不额外叠加50—100字短引言。统一执行 `references/heading-transition.md`。

### 2.1 项目研究背景与研究意义

“项目研究背景”说明当前电力业务场景、运行对象、现实约束、已有能力和待解决问题；“项目研究意义”说明拟形成的技术能力、工程价值、业务作用和可验证改善。背景与意义均以自然段为主，不写成政策清单或价值口号。

固定先写“国外研究现状”，再写“国内研究现状”。两节围绕当前报告研究主题分别组织代表性路线、已有进展和不足，作者指代样式保持统一。不得逐篇文献机械罗列，不得虚构来源，也不再要求另设与技术章标题一一对应的四级分类。

`1.3.1 主要研究内容`必须与技术规划书、任务书或等效技术文件中当前报告范围的研究内容逐项对应，并在不改变原始边界的前提下稍作展开：说明研究对象、拟解决问题、主要技术方向和预期能力/产物。不得只抄标题，也不得新增无依据技术或结果。

`1.3.2 研究思路`说明各研究内容之间的总体逻辑、依赖关系、输入输出、关键处理链和研究推进思路，适合时安排总体研究思路图。该节不再承担“章节安排”复述职责。

## 3. 技术章从第2章起按报告范围映射

目录生成前先登记 `parent_task_id`、`parent_task_order` 和 `task_role`。前序课题标记为 `technical-research`，最后一个课题固定标记为 `engineering-implementation`。

总报告严格执行“一个课题 → 一个技术章”；具体课题报告严格执行“一个来源研究内容小点 → 一个技术章”。数量、顺序、技术边界和标题名词化规则保持不变。其他课题或其他报告范围的内容不得进入当前技术章。

## 4. 技术章不再设置“概述”和“技术路线”标题

每个技术章一级标题之后直接写章首导入正文，不设置任何二级标题。章首导入正文必须包含：

- 简单背景介绍和本章研究意义；
- 本章研究主题、具体挑战、目标能力、输入输出和边界；
- 概括性技术路线或技术架构，说明主要阶段、模型/算法/模块关系、输出与反馈；
- 适合时配置技术路线图、总体架构图、数据流/知识流/控制流图等。

章首导入正文不是独立编号小节，不得显示“X.1 概述”“X.2 技术路线”“X.2 技术架构”等标题。

以5万字全文为基准，技术章章首导入正文目标约800—1200字。其他全文字数按1.6%—2.4%的比例折算。该范围用于计划和生成控制，不应缩成形式性短引言。

## 5. 每个技术章固定三个核心研究小点

技术章章首导入之后默认形成3个核心技术二级标题；只有预期目标、进度技术点或关键研究事项确实过多，且无法在不失真的情况下合理归并时，才允许最小扩展到4—5个：

```text
X.1 章内研究小点一
X.2 章内研究小点二
X.3 章内研究小点三
X.N 必要时扩展的章内研究小点（N≤5）
X.(N+1) 本章小结
```

三个小点从当前章来源研究内容、预期目标、进度计划和考核要求中拆解，不得凭空凑数。存在更多独立技术时归并到这三个小点下，以三级标题展开。

X.1—X.N默认分别设置2—4个三级标题；只有窄技术点、预期目标或进度技术点确需标题级覆盖且无法合理归并时，单个二级标题最多扩展到5个三级标题。每个技术章默认至少6个三级标题。目录或章节计划一经确认，所有一级、二级、三级标题进入标题锁定清单，正文必须按原编号、名称、层级和顺序输出。

每个技术章还必须从来源研究内容提取 `primary_technical_subject`。X.1—X.N至少一节必须作为该主语的整体技术展开节，标题直接体现主语核心，不能三个二级标题都只写主语的子算法、局部步骤或外围支撑技术。主体技术整体展开节在章节计划中原则上分配不少于X.1—X.N正文计划字数的25%。

## 6. 核心标题规则

核心二级标题必须：

- 与当前技术章研究范围直接相关；
- 分别承担一个清晰且不可互相替代的研究小点；
- 覆盖预期目标、进度计划和考核要求中的主要技术，并建立 `heading_source_term_plan`：概括性关键技术词直接进入二级标题，窄技术点直接进入三级标题，在不破坏X.1—X.N逻辑链的前提下分散覆盖；
- 完整说明“处理什么电力对象或业务约束、采用什么细粒度技术变体/关键机制、承担什么作用”；RAG、图神经网络、Transformer、强化学习等技术族名称不能直接作为最终技术粒度；
- 不使用“关键技术、核心方法、技术实现、模型研究”等低信息标题；
- 技术研究课题标题不得把“机制、建模、体系、定义”作为独立命题、中心名词或落脚点；
- 技术章每个实质二级标题（仅“本章小结”除外）都必须在标题主语中直接识别电力对象、业务场景或运行约束；其中X.1—X.N还必须同时体现具体计算技术和技术作用。若标题含“的”，以“的”之后的完整部分为主语，该主语本身必须包含强电力相关词；直接复合标题去除 `technical_signature` 后的任务主语也必须独立具有强电力语义。
- 目录生成时必须同步形成 `technology_option_sets`。对来源未唯一锁定技术路线的每个核心二级研究点，围绕同一章内问题与作用给出2—3个真正存在路线差异的可选技术，标明中文技术签名、关键机制、适配理由、来源状态与推荐项；正式目录只采用当前推荐/确认的一项，不得把多个候选同时塞进标题。来源已唯一锁定路线时标记 `source_locked=true`，可只保留1个来源技术，不得为了“可选”虚构替代技术。
- 用户可见目录输出采用“正式目录正文 + 可选技术方案”两部分；可选技术方案不编号、不进入Word目录、不计入二三级标题数量。若用户直接确认目录且未另选候选，视为确认推荐项；若用户改选候选，只重算受影响标题及相关句式/结尾分布，不扰动未受影响章节。

三级技术标题必须独立显化可识别的电力对象/业务/运行约束和具体 `technical_signature`，不能只写输入对象、处理动作、Span抽取、双塔匹配、置信校准、样本重加权、参数更新等任务级步骤，也不能依赖上位二级标题补足电力语义或技术。 同一技术章内所有技术类三级标题的任务主语还必须互不重复：对“基于{technical_signature}的{任务主语}”标题，以“的”之后的完整部分作为比较对象；对直接复合标题，去除可见 `technical_signature` 后比较剩余的电力对象/业务与技术作用。不得只更换前置算法而重复同一个“电网故障处置建议生成方法”等后半段任务。每个二级、三级技术标题中的 `technical_signature` 必须采用有实际含义的中文技术路线表达，英文模型名/英文缩写仅保留在内部元数据或正文首次定义中，不得直接裸露在目录标题；不得用生硬长译名替代路线说明。每个三级技术标题应显式写出电力领域信号以及具体模型/算法变体、关键机制、约束或组合方式；“基于具体技术签名的……”实行40%—60%的双向硬门禁：每个技术研究章及全文二、三级技术标题中，该句式占比都必须处于40%—60%，低于40%或高于60%均需重新生成；其余标题使用直接复合技术签名表达。电力领域语义显化与技术签名显化为并列最高硬门禁，二者均优先于40%—60%句式比例和25字符原则。

## 7. 先判定报告主题属性，再决定是否允许评估/验证类目录

目录阶段必须登记 `report_theme_type=evaluation-related | non-evaluation`。主题属性只看报告核心研究问题：考核指标、验收要求、测试数据、试验安排、实验材料或项目最终需要验收，本身都不能把普通技术研究报告判成评估类。

若为 `non-evaluation`，二级和三级标题均不得出现“验证、评估、评价、测评、评测、验收、测试、试验、实验”等类似章节词。有限测试条件、量化结果、证据与边界分析仍可写入X.1—X.N正文，但应转写为精度、可靠性、时延、工况适应性、性能边界、集成能力等实际技术语义，不得再单设验证类二级或三级节；本章小结位于全部核心研究点之后，`standalone_validation_mode=none`。

只有核心研究主题本身属于评估/评价/测试方法/测评体系/验证技术研究时，才可标记 `evaluation-related`。此时若用户明确要求，或当前章存在多组数据集、多类工况、多种基线、消融试验、参数敏感性分析和多张结果表等大量成体系数据，才允许在全部核心研究点之后增加一个评估/验证二级节并登记 `standalone_validation_mode=large-data|user-requested` 与原因，“本章小结”再顺延1位。

## 8. 本章小结

每个技术章必须以“本章小结”结束。默认3个核心研究点时编号为 X.4；核心研究点扩展时编号随之顺延；独立评估/验证例外启用时再顺延1位。

## 9. 研究内容、进度与内部技术要求覆盖

主要方法、模型、算法、知识构建或工程实现技术分配到X.1—X.N；支撑算法、组件和处理阶段进入三级标题。预期目标、进度计划以及考核要求中关键且有实际含义的技术词，必须按 `heading_source_term_plan` 分散映射到二、三级标题：覆盖面较广的概括性词落二级，指向局部结构/机制/算法变体/约束的窄技术点落三级；计划项较多时不得全部堆在同一X.1—X.N分支。内部技术性考核事项同时进入所属技术章X.1—X.N正文，并转写为技术目标、设计约束、性能描述、适用条件、判定规则、结果证据或能力边界。正式正文不得暴露“任务书”“考核指标”“考核要求”“考核细则”“规定指标”或内部编号。

## 10. 最后一章和参考文献

最后一章只能命名为“总结”“总结与展望”或“结论”，按总体目标收束，不按章节编号逐章复述。该章目录只保留一级章标题，`section_outline` 中只能保留与章标题一致的一级标题记录（或为空，取决于调用方表示方式），不得出现任何二级、三级或更低级标题。该章正文有效字数固定为700—800字，建议 `target_words=750`、`minimum_words=700`；不适用普通章节80%字数门禁。最后一章后必须设置参考文献。

## 11. 标题长度与简洁功能标题

一级、二级、三级标题原则上不超过25个可见字符。技术章一级标题以忠实对应当前映射单位为最高优先级；技术研究章二、三级标题则遵循“电力领域语义显化 + 技术签名显化 > 40%—60%基于句式比例 > 25字符原则”，若继续压缩会丢失技术签名或破坏比例，可保留超长标题并记录 `title_length_exception_reason`。技术研究章二、三级技术标题另按每章约40%以“技术”结尾、60%以“方法”结尾，全文“技术”结尾比例35%—45%。只有 `evaluation-related` 主题中确属研究结构的“实验设置、评价指标、数据集、测试环境、结果分析”等功能性标题可保持简洁；`non-evaluation` 主题二、三级目录不得使用验证/评估/测试/试验/实验类标题。

## 12. 目录校验清单

1. 第一章是否准确命名为“项目概述”；
2. 第一章二级标题是否依次且仅为“项目背景与研究意义”“国内外研究现状”“主要研究内容及思路”；
3. 第一章三级标题是否固定为六个指定标题及编号；
4. `1.3.1 主要研究内容`是否与技术规划书/任务书研究内容对应并适度展开；
5. 是否不存在独立的“国内外发展现状”一级章；
6. 技术章是否从第2章起且符合总报告/具体课题报告映射规则；
7. 技术章一级标题之后是否直接安排无标题章首导入正文，而不存在“概述”“技术路线/技术架构”二级标题；
8. 章首导入是否包含背景、主题引入、概括性路线和适合的图示，5万字报告目标是否约800—1200字；
9. 每个技术章是否默认3个核心二级标题；超过3个时是否仅因预期目标/进度技术点无法合理归并而最小扩展到4—5个，并登记来源化理由；
10. 核心二级标题是否分别具有2—4个三级标题；
11. 三个核心标题是否逐项完整说明电力对象/约束、具体计算技术和作用；
12. 是否已判定 `report_theme_type`；非评估主题二、三级标题是否完全没有验证/评估/评价/测评/验收/测试/试验/实验类章节词；评估主题若设置独立评估/验证节，是否有合法例外记录；
13. 本章小结是否编号正确，并已按 `references/chapter-summary.md` 完成统一规划与检查；
14. 是否排除了其他课题内容；
15. 最后一章是否只有一级标题、没有任何二三级标题，正文计划是否为700—800字；
16. 二级标题“的”后完整主语是否都带有电力相关词；
17. 预期目标、进度计划、考核要求中的关键技术词是否按“概括性→二级、窄技术点→三级”分散覆盖；
18. 技术研究章二、三级技术标题是否按约40%“技术”、60%“方法”收束；
19. 是否具有最后一章和参考文献。

# 技术章节标题命名硬规则：课题角色、章内核心研究小点与电力技术结合

本文件约束第2章起技术章的一级、二级和三级标题。标题规则只约束目录和正文标题，不禁止在技术正文中讨论机理、模型建立、变量定义、性能分析或效果评价。目录生成前必须先判定 `report_theme_type=evaluation-related | non-evaluation`；单纯存在考核指标、验收要求、测试数据、试验安排或实验材料，不足以把报告判定为评估类。

## 1. 先区分课题角色

目录生成前必须按任务材料中的课题顺序登记每个来源研究内容小点所属课题，并标记：

- `technical-research`：技术研究课题；
- `engineering-implementation`：工程实现课题。

默认规则为：前序课题均属于技术研究，最后一个课题固定属于工程实现，通常承担系统研发、平台实现、集成部署、示范应用或工程验证。一个课题下的全部研究内容小点继承同一角色。不得把其他课题的小点、进度技术、指标、数据或案例写入当前课题对应章节。

目录内部必须保存：

- 所属课题编号与原始顺序；
- 课题角色；
- 来源研究内容小点编号、原文与原始顺序；
- 规范化章标题及处理说明；
- 对应预期目标、进度技术与考核事项；
- 章内核心研究小点及其来源依据。

## 2. 一级技术章标题按报告范围映射

先读取 `task_book_scope`。

总报告严格执行：

1. 一个课题对应一个技术章；
2. 技术章数量等于总报告范围内课题总数；
3. 技术章顺序跟随课题原始顺序；
4. 课题内全部研究内容小点进入同一技术章，默认通过X.1—X.3展开；确有无法合理归并的来源覆盖需要时最小扩展为X.1—X.N（N=4或5），并通过其三级标题展开；
5. 不得拆分、合并或重排课题。

具体课题报告继续执行：

1. 一个来源研究内容小点对应一个技术章；
2. 技术章数量等于当前报告范围内小点总数；
3. 技术章顺序跟随小点原始顺序；
4. 一个技术章不得承担其他小点或其他课题内容；
5. 不得合并、拆分或重排来源研究内容小点。

一级标题以当前映射单位的来源标题为内容边界：总报告使用课题名称或一级研究内容，具体课题报告使用来源小点原文。只允许必要的名词化和语法整理，不得增加来源未包含的对象、算法、能力、指标或结论。

## 3. 技术研究课题的标题命题边界

### 3.1 不得把任务性概念作为独立标题命题

`technical-research` 课题对应技术章的一级、二级和三级标题，不得把下列概念作为独立章节名、中心名词或标题落脚点：

- 机制；
- 建模；
- 体系；
- 定义；
这里约束的是**标题含义和命题中心**，不是简单的字符串替换。正文仍可讨论作用机制、模型建立、对象定义、体系关系或效果评估。

以下写法仍然不合格，因为只是给任务性概念机械加上“技术/方法/算法/模型”：
- `设备状态建模技术`；
- `对象定义方法`；
- `协同机制技术`；
- `能力体系模型`。

### 3.2 处理原则：识别实际使用技术，不做词语替换

遇到来源中的“机制、建模、体系、定义”等表述时，不得执行“机制→技术”“建模→模型构建技术”“体系→框架”等机械替换。目录标题必须回答“实际使用了什么技术”。

处理顺序为：

1. 从当前研究内容、预期目标、进度计划、技术规划书、已确认章节内容中提取真实使用的具体技术；
2. 用该具体技术及其电力对象、技术作用形成标题；
3. 若来源没有给出足够具体的技术路径，可提出 `technology_origin=model_suggested` 的技术候选，但必须保持研究问题、对象和目标边界，并在目录确认时让用户确认；
4. 在用户确认前，不得把模型候选写成项目已经采用、已经实现或已经取得成果的事实；
5. 若既无来源依据又无法形成合理候选，则标记标题依据不足，不得靠给原词加“技术/方法/算法/模型”制造具体性。

### 3.2.1 生成目录时同步给出可选技术，不把候选直接塞进目录标题

目录阶段除了生成推荐目录，还必须建立 `technology_option_sets`。对每个**尚未由来源材料或用户唯一锁定技术路线**的核心二级研究点，默认生成2—3个可选技术；必要时可对关键三级技术点继续生成候选。候选技术用于用户在确认目录时选择，不作为“/”“或”“A/B方案”直接写进正式目录标题。

每组候选必须：

1. 回答同一个 `problem_or_role`，保持相同电力对象、研究问题、目标和当前章边界，不得通过换候选扩大研究范围；
2. 候选之间要在技术路线、关键结构、约束或组合机制上存在真实差异，不得只换模型名或同义词；
3. 每个候选登记原始 `technology_name`、可用于正式标题的中文 `technical_signature_cn`、1—3个 `key_mechanisms`、`fit_reason`、`origin`、`scope_risk` 和 `recommended`；
4. 默认只推荐1个候选。推荐依据应优先考虑任务书/已有材料一致性、与本章一级标题主线的直接支撑关系、与前后X.i的承接关系以及工程可实现性，不以“更先进”作为理由；
5. 来源材料已经把技术路线唯一写死时，设置 `source_locked=true`，可只保留1个来源确认候选，不得为了形式强造替代方案；
6. `source_grounded` 模式中的模型候选必须标记 `model_suggested`，在用户确认目录前只能表述为“可选技术”，不能写成项目既有方案；
7. 正式目录可先用推荐候选形成标题。用户确认目录且未提出候选变更时，推荐候选视为随目录一并确认；若用户改选其他候选，只重算受影响标题的中文技术签名、标题句式比例和技术/方法结尾分布，不改动无关章节。

用户可见输出应采用“**正式目录正文 + 可选技术方案**”两层结构：可选技术方案放在目录之后或各技术章之后的非编号说明区，不进入Word目录层级，也不计入二/三级标题数量。

### 3.3 标题落脚点

除工程实现课题外，技术研究类**一级标题**可以直接落到实际采用的技术、方法、算法或模型；**二级和三级技术标题统一只以“技术”或“方法”收束**。二、三级标题在每个技术研究章内按最接近40%“技术”、60%“方法”的整数数量分配，全文“技术”结尾比例原则上控制在35%—45%。“模型”“算法”应作为 `technical_signature` 或标题中部的具体技术路线出现，不再作为二、三级标题的最终落脚词。

“框架”不作为技术研究标题的落脚点；“研究”也不作为后备中心词。标题应让读者直接识别使用的技术，而不是描述“要研究、要建模、要评估什么”。

## 4. 工程实现课题的标题用词

`engineering-implementation` 课题位于课题序列末端，标题可以根据来源使用：

- 系统；
- 平台；
- 架构；
- 模块；
- 组件；
- 接口；
- 部署；
- 集成；
- 应用；
- 工程测试、联调与验证内容（仅正文；是否可进入二、三级目录仍服从 `report_theme_type`）。

工程实现课题不适用前述四个任务性概念的绝对禁用，但仍不得使用“总体体系、综合机制、系统实现、工程应用”等无法识别具体对象和作用关系的空泛标题。工程标题必须说明实现什么对象、采用什么技术组织方式、形成什么工程能力。

## 5. 每个技术章默认三个核心二级标题，预期目标过多时最小扩展

每个技术章除固定功能标题外，默认设置3个核心二级标题：

```text
X.1 章内核心技术点一
X.2 章内核心技术点二
X.3 章内核心技术点三
```

三个标题必须从当前章对应的研究内容、预期目标、进度计划和考核要求中拆解。优先通过语义归并、上下游承接和三级标题展开覆盖来源事项。只有当关键预期目标/进度技术点数量确实较多，且继续压入3个二级标题会导致标题过宽、技术职责混杂或实际技术含义丢失时，才允许最小扩展为4—5个核心二级标题。不得因为目录形式、实验安排或“内容较多”笼统理由扩展。

扩展时必须登记：

- `core_section_count`：3—5；
- `core_section_expansion_reason`：仅N>3时填写，明确指出哪些来源目标无法合理归并；
- 新增二级标题的 `source_item_ids / expected_goal_item_ids / schedule_item_ids`；
- 新增标题与前后研究点的输入输出承接关系。

每个核心二级节默认设置2—4个三级标题；只有窄技术点或预期目标无法准确落入现有三级标题时才允许扩展到5个，并登记 `level3_expansion_reason`。能在正文自然覆盖的，不新增标题。

每个核心二级标题至少登记：

- `research_subpoint_index`：按X.1—X.N连续编号，默认1—3，最多5；
- `derivation_basis`；
- `source_item_ids`；
- `schedule_item_ids`；
- `expected_goal_item_ids`；
- `heading_source_term_plan`：把预期目标、进度计划和考核要求中的关键技术词按“概括性→二级、窄技术点→三级”分散落入目录。

### 5.1 二级标题必须与本章一级标题形成直接父子研究逻辑

每个二级标题都必须是当前一级标题研究主线下的**直接子问题、关键技术步骤或核心输出**，并能够回答“这一小节为什么是完成本章一级标题所必需，而不是仅仅与整个项目有关”。判断不得依赖词语黑名单：出现“数据处理、模型训练、参数优化、系统实现、性能分析、应用分析、结果分析”等词本身不构成违规；真正的违规是标题虽然技术上相关，却把研究对象、问题中心或输出目标切换到本章主线之外，导致其更适合相邻章、后续章或可作为另一个独立技术章。例：一级标题聚焦“电力设备视觉事件知识对齐应用的迁移适配技术”时，二级标题应持续围绕视觉对象对齐、事件知识对齐、迁移适配及其必要支撑展开；若突然设置以“运检故障描述关联”为核心任务的二级标题，即使同属电力运检领域，也因没有直接服务于“视觉事件知识对齐/迁移适配”主线而应调整、下沉为支撑内容或移至更匹配章节。

目录生成前建立 `chapter_scope_boundary` 与 `chapter_mainline_map`：前者明确当前章允许展开的对象/输入/输出及 `reserved_for_later_chapters`；后者至少登记一级标题的 `chapter_core_object`、`chapter_core_problem`、`chapter_core_output`，并为每个X.i登记 `parent_logic_link`，说明该二级标题怎样直接支撑一级标题核心问题或输出。X.1—X.N及其三级标题不得提前写入后续技术章的核心方法、独立实验、工程应用或结论。允许正文简短说明当前章产物将作为后续输入，但不得在当前章目录或正文实质展开后续章节职责。

## 6. 核心二级标题统一硬规则：电力对象 + 具体技术 + 技术作用 + 承接链

本节统一原“电力+技术表达”和“创新技术与承接链”两组规则，X.1—X.N全部核心标题必须同时满足，不再分别执行两套重复标准。

### 6.1 标题必须是完整的“电力对象/约束 + 具体技术 + 技术作用”表达

核心二级标题均必须呈现：

`电力对象、业务场景或运行约束 + 具有区分度的具体计算机/人工智能/数据/知识/概率推断/优化/系统技术 + 该技术承担的作用`

不得出现纯计算机标题。例如：

- 不合格：`多模态语义表示方法`；
- 合格：`电力设备图对比多模态表征方法`。
- 不合格：`关系抽取与置信度校准方法`；
- 合格：`基于关系类型感知异构图变换注意力的调度规程关系抽取方法`。
- 不合格：`智能服务接口编排技术`；
- 合格：`电网调度混合检索重排序检索增强知识编排技术`。

每个二级、三级技术标题都必须具有**独立可见的电力领域语义**，但不要求机械重复“电力”二字。优先使用能够唯一限定电力场景的强领域词，如“电网、调度、潮流、配电、输电、变电、变压器、线路、机组、新能源、储能、电压、有功、无功、功率、继电保护、运行方式、安全边界、调控、调峰、调频、供电、台区、变电站、运检”等。`设备、故障、保护、负荷` 等在跨行业场景中可能歧义的词，单独出现时不应作为唯一的电力领域依据，应与“电力/电网/变电/运检/调度”等强领域词或明确电力对象组合使用。

**电力语义显化与技术签名显化是并列的两个硬门禁，互不替代。** 每个X.1—X.N以及其技术类三级标题都必须同时让读者从标题本身识别：①这是哪个电力对象/业务/运行约束；②采用了哪个具体 `technical_signature`；③该技术承担什么作用。不得因为使用“基于……的……”句式就省略电力关键词，也不得因为标题已经出现电力对象就降低技术签名粒度。上位标题中的电力对象不能替下位技术标题补足领域语义。

#### 6.1.1 二级标题主语必须独立带有电力相关词

技术章所有实质二级标题（仅结构性“本章小结”除外）增加主语级电力语义硬门禁。标题中出现“的”时，**“的”之后的完整部分就是主语**；例如 `基于关系类型感知异构图变换注意力的调度知识融合技术` 的主语是“调度知识融合技术”。该主语本身必须包含“电网、调度、配电、输电、变电、线路、机组、储能、负荷、电压、功率、运检”等可确认的电力相关词，不能只靠“的”之前的技术修饰语或上位标题补足。

对于不使用“……的……”的直接复合标题，先去除可见 `technical_signature` 一次，再把剩余的电力对象/业务与技术作用视为任务主语；该主语同样必须独立具有强电力语义。二级标题整体含有电力词但主语不含电力词，仍判为不合格。三级标题继续执行“标题整体独立显化电力语义”以及同章任务主语唯一性，不新增重复的主语级比例规则。

#### 6.1.2 非评估主题不得生成验证、评估类二三级章节

先由模型依据报告**核心研究主题**自动判定 `report_theme_type`。若为 `non-evaluation`，所有二级、三级标题均不得出现或单设“验证、评估、评价、测评、评测、验收、测试、试验、实验”等类似章节词；这一规则同时适用于技术研究章和工程实现章，也不能通过 `heading_kind=functional/validation` 绕过。任务书、进度计划或考核要求中的“验证/测试/验收”只表示证据或考核方式时，应转写为实际技术约束、性能边界、精度、时延、可靠性、工况适应性、联调能力等技术语义，并进入对应X.1—X.N标题/正文或证据位置。

只有报告核心主题本身属于评估、评价、测试方法、测评体系或验证技术研究时，才标记为 `evaluation-related`，相应二三级标题可以使用与主题直接相关的评估类词。**存在考核指标、需要实验数据、最终要验收或计划中写有“验证”都不能单独触发该例外。**

### 6.2 创新技术必须显化到“技术签名”层级，任务动作本身不算创新技术

“人工智能、机器学习、深度学习、神经网络、大模型、优化算法、智能分析、数据驱动”等上位概念不得作为核心二级标题的创新技术依据。进一步地，**RAG/检索增强生成、图神经网络/GNN、Transformer、图Transformer、强化学习、多智能体、知识图谱、扩散模型、状态空间模型、混合专家、元学习、图对比学习等技术族名称本身也不能直接视为足够具体的创新技术**。

此外，下面这类“处理动作、训练动作、校准动作或通用建模步骤”也**不能单独充当技术创新点**：Span抽取、双塔匹配、实体边界识别、关系类型判别、候选生成、语义聚合、术语对齐、一致性筛选、置信度校准、样本重加权、参数更新、迁移适配、相似度计算、规则匹配等。它们可以说明“做什么”，但不能回答“用什么具体技术做”。例如“运检文本提示约束Span抽取方法”“设备图像区域文本双塔匹配方法”“知识抽取置信校准方法”“少样本迁移适配参数更新方法”仍然属于技术显化不足。

二级和三级技术标题都必须显式包含一个可识别的 `technical_signature`。所谓技术签名，是能够区分同类常规方案的**具体模型/算法变体 + 关键机制/约束/组合方式**，至少满足下面一种形式：

1. 明确的具体模型、算法或已命名变体。内部规划字段可以保留其原始英文名或缩写，例如 GlobalPointer、RoBERTa、GraphSAGE、HGT、CLIP、GroundingDINO、LoRA、MAML、PPO、PatchTST、TimesNet、Mamba、ColBERT、RAPTOR 等；但正式二、三级目录标题必须转换为有实际技术含义的中文路线表达；
2. 技术族 + 至少两个能够区分路线的关键机制，例如“混合检索 + 交叉编码重排序 + 检索增强生成”“关系类型感知 + 异构图变换注意力”“多尺度时频 + 稀疏自注意力”“知识图谱约束 + 多查询 + 检索增强生成”；
3. 能够独立区分实现路线的组合机制，例如“温度缩放 + 共形预测”“类别均衡 + 焦点损失”“跨模态原型对比 + 领域蒸馏”。

#### 6.2.1 二、三级技术标题使用中文语义技术名，不直接裸露英文模型名或缩写

正式目录中的技术类二级、三级标题应优先使用**中文技术路线表达**。GlobalPointer、RoBERTa、GraphSAGE、HGT、CLIP、GroundingDINO、LoRA、MAML、PPO、RAG、Transformer 等英文技术名或缩写可以保留在内部规划元数据、技术来源说明和正文首次定义中，但**不得直接裸露在二、三级技术标题中**。

中文化不是逐字展开英文全称，也不是把一个短缩写翻成生硬、冗长、难以辨认的长名词。应优先把英文技术转换为读者能够大致判断技术路线的**简洁中文语义签名**，保留真正区分路线的结构、机制和作用。例如：

- GlobalPointer → `全局指针跨度识别`；
- RoBERTa → `鲁棒预训练语言编码`；
- SpanBERT → `跨区间掩码预训练`；
- GraphSAGE → `图邻域采样聚合`；
- HGT → `异构图变换注意力`；
- CLIP → `对比式图文预训练`；
- GroundingDINO → `开放词汇目标定位`；
- LoRA → `低秩适配`；
- MAML → `模型无关元学习`；
- PPO → `近端策略优化`；
- Mamba → `选择性状态空间`；
- ColBERT → `后交互语义检索`；
- Focal Loss → `焦点损失`；
- RAG → `检索增强生成`，但它仍只是技术族，标题中还必须继续写明混合检索、重排序、多查询、图约束等细化机制。

上述对应关系只是表达方式示例，不是固定翻译词典。若某技术的直译过长或不能反映实际路线，应根据其在当前方案中的实际作用选择更短、更有意义的中文技术表达；不得为了“中文化”丢失技术辨识度，也不得把不同技术都泛化成“智能模型、深度模型、优化算法”等宽泛词。

内部元数据建议按以下方式分工：`specific_computing_technology` / `named_technology` 可以记录可追溯的原始技术名，`technical_signature` 则记录**正式标题中实际使用的中文语义技术签名**。正文首次介绍该技术时，可以采用“中文技术表达（英文原名或缩写）”建立对应关系，后续正文再按需要使用简称；该括注规则不进入目录标题。

#### 6.2.2 任务书关键技术词按粒度分散进入二、三级标题

目录拆解不能只记录“来源依据”，还必须建立 `heading_source_term_plan`。对当前课题范围内的**预期目标、考核指标/考核要求、课题进度计划及对应考核要求**逐项提取关键且有实际含义的技术词；只抽取能够说明技术对象、技术路线、约束、能力或性能含义的词，不把“完成、开展、验收、验证、达到要求”等行政/动作词当成技术词。

- 覆盖面较广、能够统领一个研究分支的概括性技术词，标记 `granularity=broad`，必须直接出现在对应核心二级标题中；
- 覆盖面较窄、指向某一具体结构、机制、算法变体、约束、参数化技术点或局部能力的词，标记 `granularity=narrow`，必须直接出现在对应三级标题中；
- 关键技术词应在不破坏X.1→…→X.N技术链的前提下**分散覆盖**，不得把全部来源词堆到一个标题；计划项达到3个及以上时，原则上至少覆盖两个核心二级分支；
- 对“验证/评估/测试”等非技术来源词不做字面搬运。`non-evaluation` 主题下必须改写成其背后的精度、可靠性、时延、边界、工况适应性、集成能力等实际技术语义后再进入标题；
- `heading_source_term_plan` 至少记录 `source_item_id / source_type / term / granularity / target_heading_number`，并确保 `term` 在目标标题中直接可见。

该规则与“默认3个、必要时最小扩展到4—5个核心二级标题”同时成立：关键技术词优先**分散嵌入既有逻辑链**，只有确实无法合理归并的预期目标/进度技术点才允许新增标题，不得为每个任务书条目机械新增章节。

**“基于……的……”是二级、三级技术标题的优先显化句式，并实行40%—60%的双向硬门禁。** 但该句式只负责显化技术路线，**不能替代电力领域语义门禁**。采用该句式时，优先按 `基于{technical_signature}的{电力对象/业务/约束}{技术作用}{方法/技术}` 组装，例如“基于混合检索重排序检索增强生成的电网故障处置建议生成方法”“基于关系类型感知异构图变换注意力的调度知识关联推理方法”。若电力约束天然属于技术签名的一部分，也必须保证标题整体仍出现可识别的电力领域词。其余标题使用“电力对象/约束 + 具体技术签名 + 技术作用 + 方法/技术”等直接复合表达。

目录生成必须先分别锁定 `power_element` 与 `technical_signature`，再决定是否使用“基于……的……”表面句式。**任何标题不得通过调整句式牺牲其中任一要素。**

比例规则：仅统计技术研究章中的核心二级技术标题和三级技术标题，功能性/验证性标题与“本章小结”不计入。**每个技术研究章分别计算，且全文合计再计算一次；两级统计均必须满足40%—60%。低于40%或高于60%均为硬性错误，必须重新生成或改写标题。** 若某章共有 `N` 个纳入统计的技术标题，则“基于……的……”标题数量必须满足 `ceil(0.40×N) ≤ count ≤ floor(0.60×N)`。不得为了控制比例而删除 `technical_signature`，也不得为了追求“基于”句式而把标题写成“基于RAG的……”“基于图神经网络的……”等族级技术表达。

**标题结尾词分布与“基于……”句式比例是两套独立规则。** 对技术研究章纳入统计的二、三级技术标题，最终落脚词只允许“技术”或“方法”，并按约40%“技术”、60%“方法”分配。每章“技术”结尾数量取最接近 `0.40×N` 的整数（0.5时向上取整），其余使用“方法”；全文“技术”结尾比例控制在35%—45%。不得为了凑比例把相同任务仅互换“技术/方法”，也不得改变实际技术含义。工程实现标题按系统、平台、模块、接口、集成、应用等真实工程对象命名，不强制参加该结尾比例。

**优先级固定为：电力领域语义显化 + 技术签名显化（并列最高） > 40%—60%句式比例 > 25字符原则。** 标题长度仍应尽量控制，但如果为了同时保留电力对象/约束、具体技术签名并满足“基于……的……”最低比例而需要超过25个可见字符，应保留这些信息并记录长度例外。不得为了“基于”句式删掉电力关键词，也不得为了电力关键词把技术签名降级为RAG/GNN/Transformer等技术族，更不得仅为压缩字数牺牲任何一个硬门禁。

下列写法仍然过宽：

- `运检文本提示约束Span抽取方法`；
- `设备图像区域文本双塔匹配方法`；
- `知识抽取置信度校准方法`；
- `故障案例样本重加权方法`；
- `少样本迁移适配参数更新方法`；
- `基于RAG的处置建议生成方法`；
- `基于图神经网络的故障原因推断方法`；
- `基于Transformer的负荷预测方法`。

应继续细化为类似：

- `提示约束全局指针运检故障实体抽取方法`；
- `实体标记鲁棒预训练语言编码缺陷关系判别方法`；
- `术语图谱约束原型对比标准术语对齐方法`；
- `开放词汇目标定位运检设备区域候选生成方法`；
- `领域蒸馏对比式图文预训练运检实体匹配方法`；
- `跨模态原型对比图文实体一致性筛选方法`；
- `类别均衡焦点损失运检故障样本重加权方法`；
- `低秩适配模型无关元学习运检迁移更新方法`；
- `温度缩放共形预测抽取置信校准方法`；
- `基于混合检索重排序检索增强生成的电网故障处置建议生成方法`；
- `关系类型感知异构图注意力电网故障推理方法`；
- `多尺度时频稀疏自注意力电网负荷预测方法`；
- `安全约束分层近端策略优化调度策略生成技术`。

这里的示例只说明**详细程度与技术显化方式**，不是白名单。模型可以在已确认研究边界内提出更合适、相对小众且能够解释其技术差异的候选方案；来源未明确时必须登记 `technology_origin=model_suggested`，经用户确认后才可转为 `user_confirmed_design`。

目录生成必须先形成技术签名，再组装标题，顺序为：

`研究问题/对象 → 独立确定 power_element → 形成2—3个可选技术（来源唯一锁定时可1个）→ 推荐/选择具体变体或关键机制 → 记录原始技术名 → 形成中文语义 technical_signature → 同时校验电力语义、中文技术签名和英文裸露 → 规划“基于……”比例 → 标题`

不得先写一个泛化标题，再用元数据声称“技术其实很具体”。`technical_signature`、`specific_computing_technology` 与标题文本必须相互一致，并在标题中可见。

推荐采用两种标题模板混合生成：

- “基于”型：`基于{technical_signature}的{power_element}{technical_role}{方法/技术}`；
- 直接复合型：`{power_element}{technical_signature}{technical_role}{方法/技术}`。

两种模板都必须同时通过“电力领域语义可见”和“technical_signature可见”检查；“基于”型只参与40%—60%比例统计，不获得任何电力语义豁免。

`technology_specificity_basis` 不得只写“比深度学习更具体”“采用具体计算机技术”等空话，而应明确记录原始技术与中文标题表达之间的技术对应关系，例如“GlobalPointer采用提示约束完成跨度抽取，标题以‘提示约束全局指针跨度识别’表达”“RAG链路采用稠密/稀疏混合检索+交叉编码重排序，标题以‘混合检索重排序检索增强生成’表达”“采用温度缩放+共形预测完成抽取置信校准”。
### 6.3 核心二级标题必须共同回答一级标题问题，并形成先后承接

目录生成时先写出 `shared_chapter_question`。X.1—X.N不是互不依赖的并列技术，而是一条共同回答该问题的章内技术链。默认N=3时关系为：

1. X.1：形成后续处理需要的对象表示、状态、特征、知识、候选空间或基础模型；
2. X.2：显式使用X.1的产出进行关联、推断、预测、识别、求解或中间优化；
3. X.3：继续使用前序产出完成决策、优化、控制、集成、风险约束、工程适配或最终技术闭环；若报告本身为评估类，可在该技术链中承担评估/验证方法。

真实研究逻辑不同，可以调整各核心节角色；扩展到N=4或5时，新增核心节也必须继续承接同一 `shared_chapter_question`，并说明前一节输出如何成为后一节输入。若无法写出明确承接关系，应重新拆解研究点，不得用“协同、融合、联合”等词强行制造关系。

### 6.4 核心技术主语必须有独立的整体展开节

每个来源研究内容先提取 `primary_technical_subject`，即该研究内容的核心技术主语，而不是应用场景、修饰语或若干子算法的并列集合。X.1—X.N中至少一节必须专门整体展开该主语，并登记 `primary_subject_section=true`、`primary_subject_coverage_role=overall`。

该二级标题必须直接体现 `primary_technical_subject` 的词汇核心，不能只写它的子模块、训练策略、适配对象或辅助算法。正文从整体层面说明该主体技术的目标、输入输出、总体原理、关键组成、核心流程、约束、与前后技术点的接口和适用边界，再由三级标题展开。

主体技术整体展开节在章节计划中原则上不得低于X.1—X.N正文计划字数的25%；确有真实结构原因需要低于25%时，必须填写 `primary_subject_share_exception_reason`。该节仍属于既有核心技术链的一部分，不能仅因需要整体展开主体技术就新增核心二级标题；标题扩展仍必须满足“来源目标无法合理归并”的必要性条件。

### 6.5 统一元数据

每个核心二级标题统一登记以下字段，不再保留两套重复元数据要求：

- `power_element`；
- `specific_computing_technology`；
- `technical_signature`：最终必须显式进入标题的**中文语义细粒度技术签名**，不得包含裸露英文模型名/缩写，不得只写任务动作或技术族；
- `technology_specificity_basis`；
- `technology_origin`：`source_confirmed | model_suggested | user_confirmed_design`；
- `technology_option_set_id`：指向目录阶段该研究点的可选技术组；来源唯一锁定时仍登记，但不强造第二候选；
- `shared_chapter_question`；
- `chain_order`：1—N；
- `chain_role`；
- `depends_on_previous`；
- `handoff_from_previous`；
- `output_to_next`；
- `primary_subject_section`；
- 主体整体展开节额外登记 `primary_technical_subject`、`primary_subject_coverage_role`、`primary_subject_target_share`。

其中 `specific_computing_technology` 用于记录完整具体技术并可保留原始英文名/缩写，`technical_signature` 用于记录标题中必须直接可见的中文语义最小区分性技术片段。二者允许语言形式不同，但技术路线必须一一对应，不得互相矛盾。
## 7. 标题层级越深，技术指向越具体

### 7.1 一级标题

一级标题忠实对应来源研究内容小点，表达该章完整技术边界，不添加额外信息。

### 7.2 二级标题

核心二级标题分别承担章内核心研究小点。标题应能直接判断“处理什么、采用什么、解决什么环节”，不依赖正文补全关系。

### 7.3 三级标题

每个技术章的X.1—X.N核心研究小点默认分别设置2—4个三级标题；确有窄技术点或预期目标无法在不失真的情况下归并时，单个核心研究点最多扩展到5个三级标题，目录不得停留在二级。**三级技术标题与二级核心标题执行同等级的“双显化”要求：不得继承上位标题的电力领域语义，也不得继承上位标题的技术具体性。** 每个三级技术标题都必须独立回答：当前小步骤处理什么电力对象/业务/运行约束，以及具体采用什么模型、算法变体、关键机制、约束或组合方式。

三级标题不得只写处理任务或普通操作，例如：

- `故障文本实体边界识别方法`；
- `缺陷记录关系类型判别方法`；
- `技术标准术语对齐方法`；
- `图像设备区域候选生成方法`；
- `视觉对象与文本实体匹配方法`；
- `故障案例样本重加权方法`；
- `少样本迁移适配参数更新方法`；
- `抽取置信度目标验证安排`。

这些标题说明了“做什么”，但没有显式说明“用什么具体技术做”。应改为能够直接看到技术签名的表达，例如：

- `提示约束全局指针运检故障实体抽取方法`；
- `实体标记鲁棒预训练语言编码缺陷关系判别方法`；
- `术语图谱约束原型对比标准术语对齐方法`；
- `开放词汇目标定位运检设备区域候选生成方法`；
- `领域蒸馏对比式图文预训练运检实体匹配方法`；
- `跨模态原型对比图文实体一致性筛选方法`；
- `类别均衡焦点损失运检故障样本重加权方法`；
- `低秩适配模型无关元学习运检迁移更新方法`；
- `温度缩放共形预测抽取置信校准方法`。

各核心二级节的三级标题数量可以不同，但编号必须从1开始连续，不得简单重复上位标题。每个三级技术标题必须登记 `named_technology`、`named_technology_basis` 和 `technical_signature`，其中 `named_technology` 可以保留完整原始技术名，`technical_signature` 必须是标题文本中直接可见的中文语义区分性技术片段。不得要求英文原名本身出现在目录标题中。

**同一技术章内所有技术类三级标题的任务主语必须互不重复。** 对“基于{technical_signature}的{任务主语}”标题，直接以“的”之后的完整部分作为任务主语，例如“基于混合检索重排序检索增强生成的电网故障处置建议生成方法”中的任务主语是“电网故障处置建议生成方法”。同一章其他三级标题不得再次使用相同或仅把“方法/技术/模型/算法”互换的任务主语。对于不使用“基于……的……”的直接复合标题，应在去除标题中的 `technical_signature` 后比较剩余的电力对象/业务 + 技术作用部分。

该规则要求三级标题不仅“算法不同”，还要“承担的技术职责不同”。不得出现“基于技术A的电网故障处置建议生成方法”“基于技术B的电网故障处置建议生成技术”这种只更换前置技术、后半段任务完全相同的拆分。应将同章三级标题分别落到不同处理对象、步骤、输出或职责，例如“故障原因证据检索”“处置规则候选生成”“建议可信度校准”等真实不同环节。确定性门禁负责拦截相同或近似重复的任务主语，语义改写后仍承担同一职责的情况由 `report-reviewer` 继续判定。
### 7.4 二级与三级标题必须独立显化技术签名

二级和三级技术标题都必须独立达到“技术变体/关键机制”粒度，不能依靠父标题替子标题补技术，也不能依靠元数据补正文标题。生成时遵循：

1. 先确定原始具体技术、模型或算法路线，再形成与其一一对应的中文语义 `technical_signature`；
2. 判断该中文签名是否只是技术族、任务动作或生硬直译；若是，继续细化或改写为更能体现技术路线的中文表达；
3. 再将中文技术签名与当前电力对象、技术作用组合成标题，并检查标题中不得裸露英文技术名或英文缩写；
4. 先计算本章二、三级技术标题总数并规划“基于具体技术签名的……”句式数量，使本章和全文均满足40%—60%硬区间；
5. 独立规划标题落脚词，使技术研究章约40%以“技术”结尾、60%以“方法”结尾；在同时满足电力领域语义可见与技术签名可见的前提下组装标题；
6. 标题确认后，正文、章节计划和实验方案均使用同一技术名称，不得在后续阶段悄悄降级成宽泛术语。

推荐结构包括：

- `基于细粒度技术签名的对象处理方法`；
- `具体技术签名 + 电力对象/作用 + 方法/技术`；
- `具体约束/检索/图结构/注意力/训练机制 + 已命名算法变体 + 技术作用`。

“基于”不是每个标题都必须使用的固定前缀，但其**总体分布是硬性要求**：每个技术研究章及全文二、三级技术标题中，采用“基于……的……”句式的比例都必须处于40%—60%。以下两种写法都可以，但目录整体必须按比例混合使用：

- `基于混合检索重排序检索增强生成的电网故障处置建议生成方法`；
- `混合检索重排序检索增强生成电网处置建议方法`。

以下写法仍然不合格：

- `基于RAG的建议生成方法`；
- `基于图神经网络的原因推断方法`；
- `运检文本提示约束Span抽取方法`；
- `知识抽取置信校准方法`。

使用模型建议的新技术名称时必须标记 `technology_origin=model_suggested`。加入具体技术名称不得扩大当前研究问题和对象边界；用户确认后才能作为项目设计方案进入锁定目录。

标题长度仍原则上不超过25个可见字符，但优先级低于技术签名显化和40%—60%句式比例。当“基于……的……”导致标题超过25个可见字符时，先删除重复业务修饰语；若继续压缩会损失 `technical_signature`、改变技术含义或使本章/全文“基于……的……”比例低于40%，则允许保留较长标题并记录长度例外。**不得通过删除 technical_signature、降级为任务动作或破坏40%—60%比例来满足长度限制。**
## 8. 标题关系完整性

核心二、三级标题必须满足：

1. 不以“的、与、及、和、基于、面向、针对、通过、利用”等悬空词结尾；
2. 不以“研究、开展、实现、提升、解决、分析、评估、定义”等任务动作词开头；
3. 至少包含可识别的技术对象和独立可见的 `technical_signature`；纯任务动作、Span抽取、双塔匹配、置信校准、参数更新等不能替代技术签名；
4. 能够说明该具体技术在当前处理链中的作用；
5. 不使用“关键技术、核心方法、技术实现、模型研究、总体方案”等低信息标题；
6. 不把多个不相关技术用顿号或逗号拼成一个标题；
7. 不混入其他课题的技术、指标或工程对象。

## 9. 技术章章首无标题导入与收束标题

技术章一级标题后直接进入无标题章首导入正文，不设置“概述”“技术路线”“技术架构”或“技术路线与总体架构”等二级功能标题。该导入正文应简要完成本章背景与研究意义、研究主题引入、总体技术路线或架构概括、关键输入输出及能力边界说明，并在适合时配置技术路线图或架构图。

以5万字全文为基准，章首导入目标约800—1200字；其他全文目标字数按约1.6%—2.4%同比例规划。

随后默认设置核心二级标题X.1—X.3；只有预期目标/进度技术点确实无法合理归并时才最小扩展到4—5个。`non-evaluation` 主题在最后一个核心研究点后直接进入本章小结，不得新增验证、评估、测试、实验类二级节。只有 `evaluation-related` 主题且确有大量成体系数据或用户明确要求独立验证节时，才允许在核心研究点后设置独立评估/验证节，本章小结再顺延1位。

“本章小结”属于功能性收束标题，其正文组织、篇幅与证据要求统一执行 `references/chapter-summary.md`。

## 10. 标题长度与功能性短标题

目录标题原则上不超过25个可见字符。压缩时只能删除冗余限定词、重复领域词和由上位标题已明确的对象，不得新增技术信息或改变当前映射单位边界。技术章一级标题若因课题名称或来源小点原文本身过长无法安全缩短，记录长度例外理由。

功能性短标题只在不违反主题属性时使用。`evaluation-related` 主题中，“实验设置、评价指标、数据集、测试环境、结果分析”等确属评估研究结构的标题可简洁命名，并标记为 `heading_kind=functional` 或 `validation`；`non-evaluation` 主题的二、三级目录不得出现上述验证、评估、测试、试验、实验类标题，应把有限证据、数据与性能讨论融入X.1—X.N正文或使用不带评估含义的技术/性能标题。功能标题不得占用X.1—X.N核心二级标题。

## 11. 标题检查

每个技术章逐项检查：

1. 是否登记正确的所属课题和课题角色；
2. 映射是否符合报告范围：总报告只关联当前课题并包含其全部小点，具体课题报告只关联当前课题的一个来源研究内容小点；
3. 一级标题是否忠实来自课题名称或来源小点原文；
4. 是否默认设置X.1、X.2、X.3三个核心二级标题；若扩展至4—5个是否有无法合理归并的来源依据；每个X.1—X.N是否默认具有2—4个连续编号的三级标题，必要时单节最多5个；
5. 全部核心标题是否分别有研究内容、预期目标、进度计划或考核要求依据；
6. 全部核心标题是否均为完整的电力对象—具体技术—作用表达；
7. 每个二级、三级技术标题是否都同时出现可识别的电力领域语义和具体 `technical_signature`；是否存在“基于具体技术的……”但把电力对象/约束省略成纯计算机标题；是否仅使用“深度学习/大模型/机器学习/RAG/图神经网络/Transformer/强化学习”等上位概念或技术族名称；若出现技术族，是否进一步写明具体变体、结构、机制、约束或组合方式；
8. X.1—X.N是否逐项直接体现电力对象/约束、具体计算技术和技术作用；
9. 技术研究章节标题是否避免把“机制、建模、体系、定义”作为独立命题、中心名词或落脚点；若 `report_theme_type=non-evaluation`，二、三级标题是否完全未出现验证、评估、评价、测评、验收、测试、试验、实验类章节词；
10. 工程实现标题是否落到具体系统、平台、模块、接口、部署、集成或应用能力；
11. 每个三级技术标题是否独立显化了具体模型/算法变体或关键机制，而不是只写实体识别、双塔匹配、置信校准、样本重加权、参数更新等任务动作；不得依赖上位二级标题补足技术；同一章所有技术类三级标题在去除各自技术签名后，其电力任务主语是否互不重复，尤其“基于……的……”标题中“的”之后的完整任务主语不得重复；
12. 二级和三级技术标题是否都先形成 `power_element` 与中文语义 `technical_signature`，并在各自标题中同时显式呈现；目录标题是否已将RAG、GNN、Transformer、GlobalPointer、RoBERTa、GraphSAGE、HGT、CLIP、LoRA、PPO等英文技术名/缩写转换为能说明实际路线的中文表达；是否仍存在裸露英文技术词；技术族以及Span抽取、双塔匹配、置信校准等任务级技术是否已继续细化；每个技术研究章以及全文二、三级技术标题中，“基于具体技术签名的……”使用比例是否都处于40%—60%的硬区间；
13. 是否存在半句话、悬空修饰语、空泛词或跨课题内容；
14. 标题是否原则上不超过25个可见字符，超长一级标题是否有例外理由；
15. 二级标题若含“的”，其“的”后完整主语是否独立包含电力相关词；直接复合二级标题去除技术签名后的任务主语是否仍有强电力语义；
16. 预期目标、进度计划、课题区域对应考核要求中的关键技术词是否通过 `heading_source_term_plan` 按“概括性→二级、窄技术点→三级”分散可见，且没有破坏X.1—X.N逻辑；
17. 技术研究章二、三级标题是否只以“技术/方法”收束，并按每章约40%技术、60%方法以及全文技术结尾35%—45%执行；
18. 简洁功能标题是否符合主题属性且没有占用核心技术标题。

17. 目录是否已为未锁定的核心研究点生成2—3个 `technology_option_sets` 候选，且候选未直接混入正式标题；来源唯一锁定时是否避免为了形式强造替代技术；

发现问题时必须先修正目录，再提交用户确认。

# 技术章研究小点、电力标题与技术指标覆盖硬规则

本文件约束目录、章节计划、正文生成和最终组装。其要求适用于第2章起的全部技术章节，优先级高于“按内容自由决定核心二级标题数量”和“默认单设实验验证二级节”的旧规则。

## 1. 每个技术章默认拆解为章内核心研究小点，目标过多时才最小扩展

一级技术章的映射单位服从报告范围：总报告一个课题对应一个一级技术章，具体课题报告一个来源研究内容小点对应一个一级技术章。章内核心二级标题数量默认固定为3个，优先形成X.1、X.2、X.3三个连续研究小点。只有当预期目标、进度技术点或当前研究内容中的关键技术事项数量确实较多，且强行归并会导致技术含义丢失、标题过宽或多个无直接关系的目标被塞入同一研究点时，才允许最小幅度扩展为4—5个核心二级标题。不得因为“内容看起来多”“目录更完整”或方便安排实验而扩展。

默认结构为：

```text
[一级标题后无标题章首导入正文]
X.1 章内研究小点一
X.2 章内研究小点二
X.3 章内研究小点三
X.4 本章小结（默认）
```

扩展后结构按实际核心研究小点数N顺延：核心技术二级标题为X.1—X.N，`N=4或5`时必须登记 `core_section_count` 与 `core_section_expansion_reason`，并逐项说明新增标题覆盖了哪些不能合理归并的预期目标/进度技术点；本章小结编号为X.(N+1)。如果为 `evaluation-related` 且确需独立评估/验证节，则该节位于核心技术二级标题之后，本章小结再顺延1位。章首导入和本章小结不计入核心研究小点。

三级标题默认每个核心二级节设置2—4个。若同一二级节对应的窄技术点或预期目标仍无法在2—4个三级标题内准确覆盖，可最小扩展到5个，并登记 `level3_expansion_reason`；没有明确来源覆盖需要时不得增加。

任何扩展都必须遵守“最少必要标题”原则：能通过重写标题边界、合并同类技术点或在正文中自然承接解决的，不新增二、三级标题。新增标题必须有明确 `source_item_ids`，不能生成可放到任意技术章的通用章节。

## 2. 独立实验、测试或应用验证二级节默认不设置

不得为了目录完整、指标覆盖或报告形式感，默认增加“实验与结果分析”“系统测试”“应用验证”等独立二级标题。技术说明、参数边界、测试条件、量化结果和适用范围应优先穿插到X.1—X.N中与其技术主张直接对应的位置。

只有 `report_theme_type=evaluation-related`，并且满足下列任一条件时，才允许在X.3之后单设一个评估/验证类二级节X.4，并将本章小结顺延为X.5；`non-evaluation` 主题不进入本例外：

1. 用户明确要求设置独立实验、测试或应用验证章节；
2. 当前章拥有大量、成体系的数据，包含多组数据集、多类工况、多种基线、消融试验、参数敏感性分析或多张结果表，嵌入核心研究小点会明显破坏论证结构。

启用例外时，章节计划和结构化目录必须记录：

- `standalone_validation_mode`：`large-data`或`user-requested`；
- `standalone_validation_reason`：说明数据规模或用户要求；
- 验证内容与X.1—X.N技术主张的对应关系。

没有上述记录时，独立验证二级节视为目录违规。即使启用例外，也不得把技术原理、关键方法或性能约束全部推迟到验证节。

## 3. 核心研究小点的拆解依据与本章边界

核心研究小点不得由模型凭空凑数。拆解时依次读取：

1. 当前一级技术章的来源范围：总报告为所属课题及其全部研究内容小点，具体课题报告为当前研究内容小点原文；
2. 该小点对应的预期目标；
3. 课题进度计划中的技术研发、构建、实现和验证事项；
4. 内部考核要求中的功能、性能、阈值、测试条件和判定标准；
5. 用户已确认的补充技术材料。

全部核心研究小点应共同覆盖本章完整技术链，优先按照“基础对象与输入处理—核心技术处理—输出应用与质量保障”或其他真实逻辑拆解。不得把其他课题事项拿来补足研究小点，也不得把一个数字阈值直接升格为独立研究小点。

进一步要求各核心研究点之间存在可追溯承接：前一节形成后一节所需的表示、特征、知识、状态、候选空间或中间结果，后续研究点基于前序产出完成推断、预测、识别、求解、优化、决策、控制、集成、风险约束或工程适配。全部核心二级标题必须共享一个一级章核心问题，不允许仅靠“协同/融合”字样把独立技术并列在一起。每个核心二级标题还必须显式使用细化到技术变体/关键机制层级的计算机技术名称，并记录技术来源状态；RAG、图神经网络、Transformer、强化学习等技术族名称本身不满足这一要求。

每个章内研究小点必须在结构化目录中登记：

- `research_subpoint_index`：按X.1—X.N连续登记，默认1—3，扩展时最多到5；
- `derivation_basis`：说明来自研究内容、预期目标、进度计划或内部要求的哪些条目；
- `source_item_ids`：对应内部来源事项编号；
- `technical_object`、`technical_method`、`technical_role`；
- `power_element`、`specific_computing_technology`、`technology_specificity_basis`、`technology_origin`；
- `shared_chapter_question`、`chain_order`、`chain_role`、`depends_on_previous`、`handoff_from_previous`、`output_to_next`；
- 对应三级标题和技术约束融入位置。

## 4. 二级标题必须服从一级标题并把电力对象与技术方法结合起来

全部核心二级标题均不得是纯计算机或纯人工智能标题。每个标题必须同时表达：

```text
电力设备、业务对象、运行状态或安全约束
+
具体人工智能、数据、知识、算法或系统技术
+
该技术在当前处理链中的作用
```

例如：

- 不合格：`多模态语义表示方法`；
- 合格：`电力设备多模态语义统一表示方法`。

- 不合格：`关系抽取与置信度校准方法`；
- 合格：`调度规程实体关系抽取与置信度校准方法`。

- 不合格：`智能服务接口编排技术`；
- 合格：`电网调度知识服务接口编排技术`。

标题不要求机械重复“电力”二字。“电网、调度、潮流、配电、输电、变电、运检、设备、线路、机组、负荷、新能源、储能、电压、功率、故障、保护、运行方式、安全边界”等均可承担电力语义。

## 5. 核心二级标题逐项电力语义与章节专属性

X.1—X.N每个核心二级标题必须直接写明当前电力对象、业务场景或运行约束，并与具体计算技术及技术作用形成完整表达；不得依靠其他标题替当前标题补足领域语义。更重要的是，每个二级标题必须是当前一级标题研究主线下的直接子问题、关键步骤或核心输出。判断不采用“数据预处理、模型优化、系统实现、性能分析、应用分析”等词语黑名单；这些词能否使用取决于其具体研究任务是否直接服务于本章一级标题。若标题只是与项目总体相关，却切换到另一研究对象、另一核心问题或另一独立输出，即使电力语义和技术签名都完整，也属于一级—二级逻辑偏离。

## 6. 三级标题保留并进一步具体化，禁止越界到后续章节

核心二级标题X.1—X.N必须分别按真实复杂度设置2—4个三级标题，编号从1开始连续；确因窄技术点/预期目标覆盖需要时可最小扩展到5个，并登记扩展理由。三级标题继续执行以下规则：

- 每个核心二级节不得缺少三级标题；默认每节2—4个，仅有明确来源覆盖需要时最多5个；
- 比二级标题更具体；
- 落到具体输入对象、处理动作、算法、模型、组件、接口或结果分析对象；
- 当需要区分多条技术路线、突出关键创新实现或避免标题过宽时，可采用“基于细粒度技术变体的对象处理方法”形式显式写入来源支持或已确认的技术名称，例如“基于关系感知异构图变换注意力的电网故障关联识别方法”或“基于混合检索重排序检索增强生成的电网故障处置建议生成方法”；“基于图神经网络/检索增强生成/自注意力变换的……”仍属于过宽写法；
- 具体技术名如果既未被材料支持、也未作为当前核心二级标题的 `model_suggested` 候选提出，则不得补造。三级标题可以沿用同一核心二级标题的候选技术来源状态，但**不得继承技术具体性**：每个三级技术标题都必须独立显化具体 `technical_signature`。如果仍属于同一技术体系，可写该体系下不同的具体模块、模型变体或关键机制；“基于具体技术签名的……”可用于突出技术点。只有用户确认后才进入标题锁定；
- 不使用“数据处理、模型训练、参数设置、模块设计”等空泛词；
- 不说半句话，不使用无关系的并列拼接；
- 技术研究课题标题不得把“机制、建模、体系、定义”作为独立命题、中心名词或落脚点；
- 工程实现课题应落到系统、平台、模块、接口、部署、集成或应用对象；
- 目录或章节计划确认后，所有已设置的三级标题进入标题锁定清单，正文必须按原编号、原名称、原层级和原顺序逐项输出；
- 不得把已确认三级标题合并进自然段、改成列表或加粗短语、降级为四级标题或直接省略。确需修改时必须回到章节计划阶段重新确认。

需要呈现有限测试数据或结果时，优先在所属X.1—X.N下设置具体三级标题，例如“调度知识抽取准确率与错误样本分析”“电网策略生成时延及边界工况分析”，而不是单设泛化的“实验与结果分析”二级节。正文展示前应运行`validate_heading_coverage.py`确认三级标题保留率为100%。

## 7. 技术章节内容边界：当前章不得提前承接后续章职责

目录生成前必须建立 `chapter_scope_boundary`，至少登记当前一级标题的 `in_scope_objects`、`in_scope_outputs`、`reserved_for_later_chapters` 和 `forbidden_future_terms`。X.1—X.N及其三级标题只能描述当前章为完成一级标题核心问题所必需的研究对象、方法、输入输出和实验分析，不得把后续技术章的核心对象、核心输出、独立算法职责或工程应用提前写入当前章标题。

允许在正文中用一两句说明当前章输出将作为后续研究输入，但不得在当前章展开后续章的方法、实验或结论；目录标题尤其不得使用后续章专属技术词。若一个标题删除章节编号后仍可以原样放入后续章，或其主要技术作用由后续章负责，则视为越界，应回到目录阶段重写。

二级标题与本章一级标题必须存在直接的“对象—问题—输出”父子关系。审核时先抽取一级标题的核心研究对象、核心问题和预期输出，再逐项判断X.i是否为完成该主线不可或缺的子任务。不能只因为标题用了电力词、具体算法或与项目总体方向相关就判为合格；若X.i的核心任务换成了本章主线之外的另一类关联、识别、预测、决策或应用问题，则应判为章内逻辑偏离。

## 8. 技术指标与任务书硬指标的章节分配

每个技术章都应有与本章研究内容直接对应的 `chapter_technical_indicators`，用于说明本章技术效果；这些指标只服务本章技术主张，不需要把任务书全部硬指标平均分散到各章。

任务书中带有明确阈值、数量、精度、时延、可靠性、覆盖率、规模、成功率或其他验收边界的硬指标，统一建立 `task_hard_indicator_plan`，原则上集中放在**最后一个技术章节**承接。最后一个技术章先判断这些硬指标能否自然融合进已有X.1—X.N对应实验/结果分析：

1. 能与该节研究对象、数据、实验条件和技术主张直接对应的，融入原实验位置，不新增标题；
2. 无法与任何既有实验节自然融合，但必须完成总体性技术展示的，才在最后一个技术章最末核心研究点之后增加一个专门的总体实验三级标题；只有内容规模确实无法由三级标题承载时，才允许增加一个专门二级研究点，并计入4—5个核心二级标题的扩展上限；
3. 新增总体实验标题仍必须服从报告主题门禁：`non-evaluation` 不使用“实验/测试/验证/评估”等标题词，改写为“总体性能边界分析方法、综合运行性能分析方法”等技术语义标题；
4. 最后技术章本章小结必须覆盖这些硬指标对应的**实际结果与技术效果**，但不得复述“超过××、不低于××、小于××”这类任务书门槛句式，也不得写“达到考核指标”。应写成自然结果，例如“在典型工况下响应时间为8.2 s，支撑调度知识快速调用”，而不是“满足不超过10 s的指标要求”。
5. 任务书中的**定性指标同样属于必须形成结果的考核事项**。没有数值阈值不等于可以只写目标；应在最后技术章与摘要证据中写出对应能力、功能、成果状态、适用性或工程效果，例如“形成跨专业知识统一检索与可追溯调用能力”“完成多场景策略生成模块集成并具备受控回退能力”。

如果任务书硬指标与最后技术章研究对象完全无关，不得硬塞进标题；应在总体实验位置用跨模块输入输出或系统级工况把它们组织成整体性能展示，同时保持各指标的真实来源与证据状态。

## 9. 实验分析与小结指标数量控制

技术章正文的单个实验分析单元可以计算和展示多个指标，但**分析正文最多选择2个指标作为重点解释对象**。其余指标可以保留在表格、图或结果清单中，用于完整展示，不逐项展开原因分析。优先选择最能证明当前研究主张的主指标和1个必要的约束/代价指标。

本章小结按每个核心二级研究点最多总结1个代表性效果指标：每个X.i根据其研究内容只选择最能说明效果的1项指标，不在小结中堆叠多个指标；某一二级节没有实验或没有可靠量化结果时，不强行写指标，改用定性技术效果归纳。最后一个技术章除各X.i代表指标外，还必须在收束段自然覆盖任务书硬指标对应的结果与效果，但不得复述任务书阈值口吻。

## 10. 内部考核事项必须在正文中隐性覆盖

内部映射中的技术性考核事项不能只保存在覆盖矩阵、第一章、总结章或附录中。每项事项必须进入所属技术章正文，但正文不得暴露其外部来源身份，不得出现“任务书”“考核指标”“考核要求”“考核细则”“规定指标”或内部编号。

内部事项应转写为报告自身的技术内容：

- 阈值和目标值转写为技术目标、设计约束或性能边界；
- 测试条件转写为适用工况、数据范围或运行环境；
- 判定标准转写为方法有效性的判断规则；
- 已有结果转写为量化结果和能力结论；
- 缺失结果转写为设计目标、验证方案或明确待补充数据，不得写成已达到。

例如，内部记录为“知识检索响应时间不超过10 s”，正文直接写：

> 在典型调度知识查询负载下，知识检索响应时间目标设定为不超过10 s。

不得写：

> 根据任务书考核指标，知识检索响应时间应不超过10 s。

每项内部事项至少覆盖：

1. 所衡量的技术能力；
2. 适用的电力对象、业务场景或运行条件；
3. 计算方法或判定方法；仅在确有技术意义时使用公式；
4. 单位、阈值、目标值或允许范围；
5. 数据范围、环境或工况条件；
6. 有真实证据时给出结果和比较对象；没有结果时明确写成目标或验证安排；
7. 能力成立的边界、例外或代价。

内部覆盖计划必须登记：

- `assessment_item_id`；
- `planned_section`：默认落在X.1—X.N或其三级标题；
- `content_form`；
- `prose_realization`：技术目标、设计约束、性能描述、条件与阈值、结果证据或边界说明；
- `source_identity_hidden=true`；
- `evidence_status`；
- `confirmed_location`；
- `evidence_section`（可选，仅在确有独立数据分析位置时使用）。

默认不得要求单独的验证位置。不得只在本章小结中一句带过，也不得把目标值写成已经达到的结果。

## 11. 每章生成前后必经检查

生成每个技术章计划前：

- 确认默认形成3个章内研究小点；若扩展到4—5个，必须有不可合理归并的预期目标/进度技术点作为来源，并登记扩展理由；
- 确认默认结构为“无标题章首导入正文 + X.1—X.N核心研究小点 + X.4本章小结”；扩展时按X.1—X.N与X.(N+1)本章小结顺延；若为 `non-evaluation`，确认二三级标题完全不存在验证/评估/测试/实验类章节词；
- 需要独立评估/验证节时，确认 `report_theme_type=evaluation-related` 且存在大量数据或用户明确要求，并记录例外原因；
- 确认全部核心研究小点共同覆盖当前章研究内容、预期目标和主要进度技术，且没有跨入后续技术章的研究职责；
- 确认当前章自身技术指标已有X.1—X.N正文融入位置；若当前章是最后一个技术章，同时确认任务书硬指标已有集中承接位置；
- 确认全部核心二级标题均为“电力对象+具体技术+作用”的完整表达，并且都是本章一级标题主线下的直接子问题、关键步骤或核心输出，不存在一级—二级逻辑偏离；
- 确认未混入其他课题内容。

正文展示给用户前：

- 检查X.1—X.N是否均已实质展开；
- 检查技术目标、条件、单位、阈值、证据状态和边界是否完整；
- 检查没有把目标冒充为完成结果；
- 检查正文没有出现任务书、考核指标、考核要求、考核细则、规定指标或内部编号；
- 检查每个核心标题是否仍逐项显式体现电力对象/约束、具体计算技术和技术作用；
- 检查不存在纯计算机标题、一级—二级逻辑偏离、跨课题内容或提前涉及后续技术章研究职责的标题。

### 目录技术词分散覆盖与主题冲突消解

预期目标、进度计划以及考核要求中的关键技术词必须进入 `heading_source_term_plan`：概括性技术词分配到X.1—X.N二级标题，窄技术点分配到对应三级标题；不得为覆盖来源词破坏核心研究小点的技术链，也不得把全部词堆到同一分支。`non-evaluation` 主题下，验证/评估/评价/测试/试验/实验/验收等来源动作词不得作为二三级章节词，改为其背后的性能、约束、边界或工程技术语义。

技术研究章二、三级技术标题以“技术/方法”收束，按每章约40%“技术”、60%“方法”分配；“模型/算法”作为技术签名进入标题中部而非结尾。二级标题含“的”时，“的”后完整主语必须独立包含强电力相关词。

# 课题角色、研究内容小点、章内核心研究小点与考核指标全量覆盖规则

本文件约束从任务书、实施方案、预期目标、进度计划、考核要求和用户补充材料中提取当前报告范围内的研究内容，并将其稳定映射到第一章1.3.1“主要研究内容”、第一章1.2“国内外研究现状”、技术章节、验证证据和摘要。

任务材料中的课题必须按原始顺序登记。前序课题标记为 `technical-research`，最后一个课题固定标记为 `engineering-implementation`，通常承担系统研发、平台实现、集成部署、示范应用或工程验证。每个来源研究内容小点、预期目标、进度事项和考核事项都必须登记 `parent_task_id`，并继承所属课题角色。

任何来源事项除匹配研究内容小点外，还必须匹配所属课题。其他课题内容不得因主题相近、可以补足篇幅或技术上可复用而进入当前章。

## 2. 先确定当前报告范围

任务材料可能同时包含多个课题、专题、承担单位或成果包。建立映射前，必须将事项分为：

- `in-scope`：属于当前报告研究范围；
- `shared-approved`：确属多个研究内容共同需要，且经用户确认可共用；
- `excluded-other-task`：属于其他课题、专题或报告范围；
- `administrative`：人员、经费、组织、节点管理等非技术事项。

只有 `in-scope` 和经确认的 `shared-approved` 内容可以进入正文。`excluded-other-task` 不得通过改名、概括或并列压缩进入标题、正文、公式、图表、实验和结论。

## 3. 区分课题、来源研究内容小点与章内研究小点

先读取 `task_book_scope`，再提取任务材料中的课题、一级研究内容和来源研究内容小点。

总报告按课题设置一级技术章节：

```text
课题原始名称与顺序
→ 课题内全部来源研究内容小点
→ 必要名词化章名
→ 一个技术章节
```

具体课题报告继续按来源研究内容小点设置：

```text
一级研究内容
→ 来源研究内容小点原文
→ 小点原始顺序
→ 必要名词化章名
→ 一个技术章节
```

每个技术章内部再拆解为章内核心研究小点：

```text
来源研究内容小点
+ 对应预期目标
+ 对应进度计划技术
+ 对应考核要求
→ 章内研究小点1（X.1）
→ 章内研究小点2（X.2）
→ 章内研究小点3（X.3）
```

必须区分层级：总报告由课题决定一级技术章，具体课题报告由来源研究内容小点决定一级技术章；章内研究小点始终决定该章的核心二级标题。内部映射必须同时保留课题和研究点关系。

## 4. 技术章数量和顺序

总报告：

- 有几个课题就设置几个技术章；
- 技术章顺序与课题原始顺序一致；
- 一个课题只对应一个技术章；
- 同一课题下的多个来源小点归入该章，不得各自另设一级章。

具体课题报告：

- 有几个来源研究内容小点就设置几个技术章；
- 技术章顺序与小点原始顺序一致；
- 一个来源小点只对应一个技术章；
- 不得合并或拆分来源小点；
- 技术章从第2章开始编号，因为国内外研究现状已并入第一章。

## 5. 技术章标题按课题角色整理

章标题以当前映射单位的来源标题为唯一依据：总报告使用课题名称或一级研究内容，具体课题报告使用来源小点原文。

允许：

- 删除开头的“研究、开展、研发、构建、建立、提出、实现”等任务动作词；
- 调整少量语序；
- 技术研究课题在原文和已确认方案已明确实际技术时，标题落到“技术、方法、算法、模型”等技术中心词；不得用中心词机械包装“机制、建模、体系、定义”等任务性概念；
- 工程实现课题可补足“系统、平台、架构、模块、接口、部署、集成、应用”等工程中心词；
- 统一术语和缩写。

禁止：

- 根据问题分析另行生成扩写标题；
- 增加原文没有的电力对象、人工智能方法或技术作用；
- 在技术研究课题的一级章标题中把“机制、建模、体系、定义”保留为独立命题、中心名词或落脚点，或通过机械增加“技术/方法/算法/模型”改名；
- 增加能力、指标、结果、应用价值或评价词；
- 将进度计划中的多项技术全部堆入一级标题；
- 混入其他课题内容。

## 6. 全文固定章节落点

### 第一章“项目概述”

- `1.1 项目背景与研究意义`：下设`1.1.1 项目研究背景`与`1.1.2 项目研究意义`；
- `1.2 国内外研究现状`：下设`1.2.1 国外研究现状`与`1.2.2 国内研究现状`；
- `1.3 主要研究内容及思路`：下设`1.3.1 主要研究内容`与`1.3.2 研究思路`。

其中`1.3.1 主要研究内容`必须与技术规划书、任务书或等效材料中的当前报告范围研究内容逐项对应，并作适度展开说明；`1.3.2 研究思路`说明总体研究逻辑和技术关系。

### 第2章起技术章节

技术章一级标题之后先直接写无标题章首导入正文，合并原概述和总体技术路线/架构功能，不设置对应二级标题。随后固定为：

```text
X.1 章内研究小点一
X.2 章内研究小点二
X.3 章内研究小点三
X.4 本章小结（默认）
```

问题、背景、研究意义和总体技术路线优先进入章首无标题导入；主要进度技术分配到X.1—X.N；支撑算法、组件和处理步骤进入相应三级标题；各章自身技术要求的能力含义、条件、结果和判定默认融入X.1—X.N或其三级标题，任务书硬指标统一由最后技术章集中承接。`non-evaluation` 主题不得增加独立验证/评估/测试二级节，本章小结紧随最后一个核心研究点；只有 `evaluation-related` 主题且存在大量成体系数据或用户明确要求时，才可在核心研究点后增加独立评估/验证二级节，并将本章小结顺延。

章首无标题导入继续按本文件既有篇幅规则规划；本章小结的篇幅与内容要求统一执行 `references/chapter-summary.md`。

## 7. 章内核心研究小点的拆解

每个技术章默认形成3个核心二级标题；只有预期目标、进度技术点或关键研究事项确实过多且无法合理归并时，才最小扩展到4—5个。拆解时依次读取：

1. 当前技术章来源范围：总报告为所属课题及其全部研究内容小点，具体课题报告为当前来源研究内容小点原文；
2. 预期目标；
3. 进度计划中的技术事项；
4. 考核要求中的功能、性能和测试事项；
5. 用户已确认的补充材料。

核心小点应互不重复并共同构成完整技术链。默认优先归并为3个，不得为了凑足数量引入其他课题内容；扩展到4—5个时必须逐项说明哪个预期目标/进度技术点无法合理归并，也不得把纯管理节点或单一考核数字作为独立小点。

技术链必须有方向性。目录内部同时登记全部核心小点的共同章级问题、chain_order、chain_role、前序输入与后序输出。X.1—X.N每个标题都应使用一个足够具体的计算机/人工智能技术名称；RAG、图神经网络、Transformer、强化学习、大模型等仅表示技术族，不视为足够具体，必须进一步写明具体变体、结构、机制、约束或组合方式。若细化方法由模型在已确认研究边界内提出而非来源已有，应标记 `model_suggested` 并在目录确认时一并让用户确认。

每个章内研究小点必须登记：

- `research_subpoint_index`；
- `derivation_basis`；
- `source_item_ids`；
- `technical_object`、`technical_method`、`technical_role`；
- `power_element`、`specific_computing_technology`、`technology_specificity_basis`、`technology_origin`；
- `shared_chapter_question`、`chain_order`、`chain_role`、`depends_on_previous`、`handoff_from_previous`、`output_to_next`；
- 对应三级标题；
- 对应内部技术要求、正文融入位置和可选证据位置。

## 8. 第一章国内外研究现状与技术章对应

第一章1.2的文献检索主题、技术进展和技术缺口应与报告范围内研究内容保持可追溯关系；总报告按课题研究主题组织，具体课题报告按研究内容小点组织。1.2.1国外研究现状与1.2.2国内研究现状采用一致的研究主题口径，但不要求三级标题机械复制技术章标题。1.3.1“主要研究内容”必须与技术规划书、任务书或等效技术文件中的研究内容逐项对应，并在不增加研究边界的前提下对每项内容稍作展开说明。

每个类别按以下逻辑组织：

```text
对应来源研究内容小点
→ 国内或国外代表性路线
→ 已经解决的问题
→ 现存不足
→ 当前技术章需要处理的技术问题
```

不得把其他课题的研究内容作为第二章技术类别。

## 9. 进度计划、预期目标和考核指标全量覆盖

从预期目标、进度计划和考核要求中提取：

- 研究、研发、构建、实现和集成事项；
- 数据、模型、算法、系统和平台事项；
- 仿真、实验、测试、示范和应用事项；
- 功能、性能、时延、精度、可靠性和安全指标；
- 测试条件、判定标准和能力边界。

映射规则：

- 主要方法、模型、算法、知识构建或工程实现技术进入核心二级标题；
- 支撑技术进入更具体的三级标题；
- 每项内部技术性考核事项必须进入所属技术章X.1—X.N正文或其三级标题，不能只存在于内部矩阵、第一章、总结章或附录；
- 正文至少说明技术能力、电力对象或业务条件、计算或判定方法、单位、阈值、数据或工况条件、证据状态和能力边界；
- 对 REAL_PROJECT_EVIDENCE，有真实结果时给出结果、比较对象和条件；没有结果时只能写成设计目标、验证方案或明确占位，不能写成已达到。该限制不禁止为用户生成明确标记的 REFERENCE_EXPERIMENT、模拟数据和参考结果分析；
- 正式正文不得出现“任务书”“考核指标”“考核要求”“考核细则”“规定指标”或内部编号。

每项内部事项必须登记：

- `assessment_item_id`；
- `planned_section`；
- `content_form`；
- `prose_realization`；
- `source_identity_hidden=true`；
- `evidence_status`；
- `confirmed_location`；
- `evidence_section`（可选）。

## 10. 电力标题语义逐项追溯

X.1、X.2、X.3每个核心二级标题都必须能够从当前研究内容追溯到明确的电力对象、业务场景或运行约束，并在标题中直接体现该对象/约束、具体计算技术和技术作用。

## 11. 章节计划必填映射

每个技术章计划必须记录：

- 所属一级研究内容编号；
- 所属课题编号、课题顺序与课题角色；
- 当前映射单位编号、来源标题和原始顺序；总报告另列课题内全部来源研究内容小点；
- 名词化章标题和处理说明；
- 第二章对应三级类别；
- 章内核心研究小点的标题、序号、来源依据和技术职责；
- 每个小点对应的预期目标、进度技术和考核事项；
- 当前章范围内的内部技术要求隐性覆盖计划；
- 每项内部事项的X.1—X.N正文融入位置、可选证据位置、正文表述方式、来源身份隐藏状态和证据状态；
- 其他课题排除清单。

## 12. 每章生成前后

生成前：

1. 读取当前映射单位的来源标题和名词化章名：总报告读取课题，具体课题报告读取来源小点；
2. 确认本章只使用当前技术章范围相关的 `in-scope` 与 `shared-approved` 事项；
3. 确认一级章标题后直接规划无标题章首导入正文，并覆盖背景与意义、研究主题、概括性技术路线/架构和适合的图示；
4. 确认X.1、X.2、X.3且仅有章内核心研究小点；
5. 检查三个小点覆盖当前章预期目标和主要进度技术；
6. 检查所有内部技术要求均有X.1—X.N正文融入位置，并标记来源身份隐藏；
7. 检查三个核心标题均为完整的电力对象—具体技术—作用表达；
8. 检查三级标题比上位标题更具体；
9. 技术研究课题标题检查任务性概念是否被误作独立命题、中心名词或落脚点。

生成后：

1. 更新每项来源事项和内部技术要求的覆盖状态及正文位置；
2. 检查X.1—X.N均已实质展开；
3. 检查技术能力、条件、单位、目标、证据状态和边界是否完整，且来源身份已隐藏；
4. 检查是否遗漏进度技术或内部技术要求；
5. 检查是否混入其他课题；
6. 检查每个核心标题均可追溯并直接体现电力对象/约束、具体计算技术和技术作用；
7. 更新摘要证据包。

## 13. 覆盖状态

技术事项使用：

- `unmapped`；
- `planned`；
- `drafted`；
- `confirmed`；
- `covered-by-appendix`；
- `not-applicable`。

考核事项还必须登记 `assessment_kind=quantitative|qualitative|mixed`。定量事项需要实际值/范围/相对结果；定性事项也必须在章节确认后登记 `result_realization`，写明已形成的能力、功能、成果状态、适用性或工程效果，不能因无数值阈值而只保留要求原文。摘要阶段按此字段逐项形成 `task_book_assessment_results`。

考核指标额外使用证据状态：

- `target-only`；
- `test-designed`；
- `evidence-partial`；
- `evidence-confirmed`；
- `not-applicable`。

最终组装前，所有范围内技术事项必须为 `confirmed`、`covered-by-appendix` 或有充分理由的 `not-applicable`。内部技术性考核事项必须在所属技术章X.1—X.N正文中具有确认位置，且正文表述不得暴露任务书、考核指标、考核要求、考核细则、规定指标或内部编号，不能只标记为附录覆盖。

## 10. 预期目标、进度与考核技术词的标题级追溯

对每个技术章，除维护来源事项覆盖状态外，还必须维护 `heading_source_term_plan`。从 `expected-output`（预期目标/预期技术能力）、`schedule-plan`（课题进度计划及对应课题区域技术点）和 `assessment-requirement` 中提取关键且有实际含义的技术词。覆盖面较广、能够概括一个研究分支的词标记为 `broad` 并直接进入X.1—X.N二级标题；覆盖面较窄、仅指向具体结构、机制、算法变体、局部约束或局部能力的词标记为 `narrow` 并直接进入相应三级标题。关键技术词应分散到既有技术链中；先尝试在默认3个核心二级标题及其三级标题内合理归并，只有确实无法归并的独立预期目标/进度技术点才允许最小扩展到第4或第5个核心二级标题。

`non-evaluation` 主题中，来源出现“验证、评估、测试、验收、实验”等字样时不得把这些动作词搬进二三级标题；必须追溯其背后的技术含义，例如精度、时延、可靠性、鲁棒性、工况边界、接口适配或联调能力，再选择有实际意义的技术词进入标题。单纯存在这些来源事项不能改变 `report_theme_type`。

## 11. 目录阶段可选技术追溯

每个技术章在正式目录之外维护 `technology_option_sets`。来源未唯一锁定技术路线时，每个核心二级研究点给出2—3个同问题、同作用、同章节边界的候选技术，并记录中文技术签名、关键机制、适配理由、来源状态和唯一推荐项；来源明确唯一路线时使用 `source_locked=true` 且只保留1个来源技术。候选技术是用户确认目录时的伴随选择，不是正式标题，也不能用于把后续章节职责提前引入当前章。

# 课题角色、研究内容小点与核心标题对齐硬规则

本规则用于论证架构、目录、章节计划和每章生成前检查。

## 1. 课题角色必须先于章节设计确定

目录生成前必须先按任务材料建立课题清单，并登记：

- `parent_task_id`；
- `parent_task_order`；
- `task_role`；
- 当前课题包含的研究内容小点；
- 当前课题的进度技术、考核事项和可用材料。

前序课题按 `technical-research` 组织，最后一个课题固定按 `engineering-implementation` 组织，通常承担系统研发、平台实现、集成部署、示范应用或工程验证。一个课题下的全部小点继承同一角色。

## 2. 技术章按报告范围映射

总报告中，每个课题必须形成且只形成一个技术章，技术章数量、顺序、对象和技术边界与课题保持一致；同一课题下的多个研究内容小点默认归入该章X.1—X.3，确有来源覆盖需要时最小扩展为X.1—X.N，并通过其三级标题展开。具体课题报告继续按每个明确研究内容小点形成一个技术章。

章名只允许对当前映射单位的来源标题作必要名词化和标题用词整理，不得扩写为来源没有支持的完整解决方案。技术研究课题的标题不得把“机制、建模、体系、定义”作为独立命题、中心名词或落脚点；工程实现课题的标题应落到具体系统、平台、架构、模块、接口、部署、集成或应用能力。

## 3. 第一章国内外研究现状与技术点对应

第一章`1.2 国内外研究现状`固定下设`1.2.1 国外研究现状`和`1.2.2 国内研究现状`。两节围绕后续技术章节覆盖的主要研究主题组织代表性路线、已有进展和不足。不得设置与技术章一一对应的额外四级标题；对应关系通过正文技术主题和内部检索映射维护。

## 4. 核心二级标题与当前技术章范围对齐

每个技术章一级标题后的无标题章首导入正文不属于核心技术标题。X.1—X.3默认承担章内核心研究小点；只有预期目标/进度技术点无法合理归并时才最小扩展到X.4—X.5，全部作为核心技术标题管理。

每个核心标题必须：

1. 只服务当前技术章范围；总报告可覆盖所属课题的多个研究内容小点，具体课题报告只覆盖当前小点；
2. 只使用当前课题范围内的进度技术和考核事项；
3. 逐项体现电力对象/约束、具有区分度的具体计算技术、技术作用及其可追溯或经确认的来源状态；
4. 显式采用具有区分度的细粒度计算机/人工智能技术；不仅要避免“人工智能、机器学习、深度学习、神经网络、大模型、优化算法”等上位概念，也不得把RAG、图神经网络、Transformer、强化学习等技术族名称直接当作已经足够具体，必须继续落到具体变体、结构、机制、约束或组合方式；
5. 与另外两个核心标题共享同一个一级章核心问题，并说明本节从前序接收什么、向后序输出什么。
4. 完整说明技术对象、技术方法和该方法承担的作用；
5. 不引入其他小点或其他课题的技术；
6. 不使用空泛评价词和悬空修饰语；
7. 技术研究课题中不得把“机制、建模、体系、定义”作为独立命题、中心名词或落脚点，也不得机械改名。

结构化目录中必须记录：

- `technical_object`；
- `technical_method`；
- `technical_role`；
- `specificity_basis`；
- `parent_task_id`。

## 5. 三级标题必须比二级标题更具体

三级标题用于说明二级技术内部的具体输入对象、处理动作、算法、模型、组件或接口。不得只是重复二级标题，也不得使用“数据处理、模型训练、参数设置、模块设计、相关分析、进一步研究”等低信息名称。

三级标题应能够回答：

- 处理哪个具体对象；
- 使用哪项具体方法或算法；
- 在上位技术中完成什么步骤或形成什么输出；
- 当具体技术名称是关键区分点时，是否需要采用“基于具体技术名的背景/目的技术（方法、模型）”形式显式写入，以及该名称来自哪项材料或确认。

二级和三级技术标题都必须显式加入具体技术签名；只有功能性/验证类标题可以不写技术名。技术族名称不等于细粒度技术名。来源只写“图神经网络、Transformer、强化学习、知识图谱、RAG”等时，目录仍需结合当前研究问题进一步明确其实际变体、关键结构、检索策略、约束方式或组合机制；若细化方案由模型提出，则标记 `model_suggested` 并在目录确认时一并让用户确认。三级标题可以在同一候选技术边界内继续细化，但不得另行发明无关算法；用户确认目录后再将该技术视为已确认设计。每个三级技术标题必须独立显化当前步骤的电力对象/业务/运行约束与 `technical_signature`，不能因为上位标题已经明确电力场景或细粒度变体就只写“实体识别、置信校准、参数更新”等任务动作。可以沿用同一技术体系，但应写出该步骤实际采用的具体模型变体、关键机制或约束；“基于具体技术签名的……”不要求每条标题都使用，但每个技术研究章及全文二、三级技术标题中的使用比例必须处于40%—60%的硬区间；无论采用哪种句式，每条技术标题仍必须独立出现电力领域信号。

## 6. 进度计划技术落点

主要方法、算法、模型、知识构建和工程实现技术应归并到核心二级标题；支撑算法、组件、接口或处理阶段进入三级标题；内部技术性考核事项必须进入所属章X.1—X.N正文或其三级标题，并隐去外部来源身份。主要技术和性能要求不得只在内部矩阵或总结中顺带提及。

任何映射事项都必须同时匹配当前 `parent_task_id` 和允许的 `research_point_id`。总报告一个技术章可匹配所属课题的多个研究点；具体课题报告仍只匹配当前小点。只匹配研究点但属于其他课题的内容仍视为越界。

## 7. 每章生成前检查

- 当前章属于哪个课题，课题角色是什么；
- 当前章对应哪个研究内容小点；
- 一级章标题是否仅为该小点的允许整理；
- 当前章是否混入其他小点或其他课题内容；
- 技术研究标题是否避免把“机制、建模、体系、定义”作为独立命题、中心名词或落脚点，并避免机械改名；
- 是否默认设置三个核心标题；扩展到4—5个时是否具有必要且可追溯的来源依据；全部核心标题是否完整说明电力对象、具体技术和作用；
- 每个X.1—X.N核心二级标题是否均直接体现电力对象/约束、具体计算技术和技术作用；
- 每个三级技术标题是否独立显化具体 `technical_signature`，并避免只写任务动作；功能性/验证类标题除外；
- 一级章标题后是否直接存在无标题章首导入正文，并覆盖背景、研究主题和概括性技术路线/架构；
- 是否不存在“概述”“技术路线”“技术架构”功能性二级标题；
- 5万字报告的章首导入是否按约800—1200字规划。

# 报告范围与技术章节映射硬规则

本规则在目录生成前执行，优先级高于“研究内容小点一章一对应”的旧口径。先读取项目档案中的 `task_book_scope`，再确定技术章映射单位。不得在未判断报告范围时直接按研究内容小点生成技术章。

## 1. 报告范围分支

### 1.1 总报告：一个课题对应一个技术章

当 `task_book_scope=total_report` 时，必须按任务书课题原始顺序建立 `report_tasks`：

- 每个课题且仅对应一个技术章；
- 技术章数量必须等于总报告范围内课题数量；
- 技术章顺序必须与课题原始顺序一致；
- 不得把一个课题拆成多个技术章，也不得把多个课题合并成一个技术章；
- 同一课题下的全部研究内容小点、预期目标、进度技术和内部技术要求统一归入该课题技术章；
- 课题内多个研究内容小点默认通过X.1、X.2、X.3组织；确有来源覆盖需要时最小扩展为X.1—X.N，并通过其三级标题展开，不再各自形成一级技术章；
- 章标题以课题名称或课题一级研究内容为边界，只做必要名词化，不得增加来源没有的对象、算法、指标或结论；
- 前序课题仍标记为 `technical-research`，最后一个课题仍标记为 `engineering-implementation`。

结构化目录必须登记：

```json
{
  "task_book_scope": "total_report",
  "report_tasks": [
    {
      "task_id": "TASK-01",
      "task_order": 1,
      "task_title": "课题原始名称",
      "normalized_chapter_title": "名词化技术章标题",
      "task_role": "technical-research",
      "research_point_ids": ["RP-01", "RP-02"]
    }
  ]
}
```

每个技术章还必须登记 `source_task_title`、`source_task_normalized_title`、`task_title_normalization_basis`、`parent_task_id`、`parent_task_order` 和该课题全部 `source_research_point_ids`。

### 1.2 具体课题报告：保持研究内容小点一章一对应

当 `task_book_scope=specific_topic` 时，继续执行原有规则：

- 当前报告范围内每个来源研究内容小点对应一个技术章；
- 技术章数量、顺序与小点数量、原始顺序一致；
- 一个小点不得拆分为多个章，多个小点不得合并为一个章；
- 章标题只对来源小点原文作必要名词化。

`task_book_scope=not_applicable` 且材料中没有课题层级时，默认沿用具体课题报告的小点映射规则。

## 2. 第一章国内外研究现状与技术范围一致

研究现状固定放在第一章：

```text
1.2 国内外研究现状
  1.2.1 国外研究现状
  1.2.2 国内研究现状
```

两节围绕当前报告范围内的主要技术主题组织代表性路线、已有进展和不足。技术主题必须覆盖后续技术章所对应的课题或研究内容小点，但不再设置与技术章一一对应的额外三级标题，因此不存在原“国内/国外三级标题逐项匹配技术章”的要求。

## 3. 目录生成前检查

1. 是否已明确 `task_book_scope`；
2. 总报告是否已列全课题，并做到一个课题一个技术章；
3. 具体课题报告是否仍按一个研究内容小点一个技术章；
4. 每个技术章是否只使用所属课题范围内的内容；
5. 第一章1.3.1“主要研究内容”是否与技术规划书、任务书或等效技术文件中的范围内研究内容逐项对应并保持原始顺序；
6. 第一章1.2.1国外与1.2.2国内研究现状是否采用一致的研究主题组织口径，并能够导向对应研究内容。

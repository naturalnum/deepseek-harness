### 0.9 独立报告口吻、跨章互引与 Markdown 文件交付

正式报告必须被写成一个脱离任务来源也能够独立成立的技术文本。任务书、申报书、申报材料、合同条款、课题分工、会议纪要、结题材料、验收材料、最终材料、交付材料和用户补充说明等只能在内部用于提取信息，不得以文件名称、行政任务名称或材料身份进入正式正文。

正文中禁止出现下列表述及其同义变体：

- “任务书中指出／规定／要求／提出……”；
- “根据任务书要求……”；
- “课题一／课题二中要求……”；
- “按照课题分工……”；
- “为完成任务书指标……”；
- “课题一／课题2／子课题三……”等以课题编号标识研究内容的表达；
- “最终材料／结题材料／验收材料／申报材料／交付材料中……”等外部材料名称；
- “第六章中的应用／第二章构建的规则库／如第三章所述……”等具体章节编号互引；
- “上一章／下一章／前一章／后一章……”等章序关系互引。

第一章1.3.2“研究思路”只说明研究内容之间的逻辑、依赖、输入输出与推进思路，不承担逐章复述目录的职责。正式正文各处均不得依赖“第二章、第三章”等具体章节编号说明内容关系。

必须将来源性和编号式互引改写为独立技术陈述。例如：

- “任务书要求知识检索时间不超过 10 s”改为“知识检索响应时间设计目标为不超过 10 s”；
- “课题一提出人机协同框架”改为“人机协同智能决策框架由数据、知识、模型和人员协作关系共同构成”；
- “第二章中构建了电子规则库”改为“前文构建的电子规则库为规则约束匹配提供基础”，更自然时直接写“电子规则库为规则约束匹配提供基础”；
- “第六章中的应用结果表明”改为“应用验证结果表明”；
- “下一章将介绍模型演进机制”改为“后文进一步研究模型演进机制”或直接说明尚需解决的技术问题。

跨部分衔接优先直接使用明确技术对象，其次使用“本文”“前文”“后文”“前述方法”“在此基础上”“进一步”“随后”等自然表达。正文任何位置均不得通过章节编号或章序关系定位其他内容。

最终组装默认生成一个 `.md` 文件，而不是在聊天中重新铺开整篇报告。默认文件名采用“报告简称-科技报告.md”或用户指定名称。只有用户明确要求其他格式时，才在已确认 Markdown 成稿基础上另行转换；Markdown 始终作为默认源文件和首要交付物。最终组装规则必须读取 `references/independent-report-voice.md`。组装完成后必须调用 `scripts/normalize_markdown.py` 做确定性清洗：默认将各种长划线统一为ASCII连字符`-`（用户明确要求时可统一为`—`），并删除数字与汉字之间的空格。该步骤只由脚本完成，不再调用大模型改写正文。

### 0.10 参考文献真实性与摘要结构

参考文献规则必须读取 `references/citation-and-evidence.md`，摘要规则必须读取 `references/abstract-and-introduction.md`。二者均为强制规则。

#### 参考文献

- 网络可用时，必须主动搜索原始论文、标准和官方文档，并核验题名、作者、年份、出版物、DOI或稳定标识；
- 不得仅根据搜索结果摘要、博客、聚合站或模型记忆生成文献；
- 后续章节新增方法来源、指标定义或比较基线时，在章节计划阶段补充定向检索；
- 不能联网时，先明确请求用户提供论文题目、DOI、官方链接、论文全文或已确认参考文献表；
- 若网络不可用且用户也无法提供任何可识别来源，允许使用且只允许使用统一占位 `【待补充来源】` 继续生成依赖文献的内容；不得据此编造作者、题名、年份、DOI或参考文献条目；
- 使用占位时，必须在全局状态中登记对应主题、正文位置和所需来源类型，并在最终附录生成“待补充来源清单”；
- 已核验参考文献必须与正文引用双向对应；
- 对已核验论文，最终附录必须给出 DOI、官方网页或合法下载链接；不得提供侵权镜像或来源不明的下载地址。

#### 摘要

摘要不得等到主体全文完成后，仅依赖长上下文临时概括。目录和论证架构确认后，必须初始化 `abstract_evidence`，结构见 `schemas/abstract-evidence.schema.json`，模板见 `templates/abstract-evidence.json`。每个技术章的计划阶段先登记其对应关键挑战与研究点、技术名称、核心机制、预期能力、待验证证据以及可支撑的研究或应用前景；每章正文经用户确认后，立即把已确认内容、任务书定量/定性考核结果、必要测试或适用条件、少量可选补充指标、适用边界和前景证据更新到摘要证据包。定性考核要求不能因为没有数值阈值而遗漏。

摘要生成前必须重新读取 `references/abstract-and-introduction.md` 和 `abstract_evidence`，形成内部三段式提纲，再生成摘要。摘要固定采用三个连续自然段：

1. 第一段写领域现状、现实需求、现有不足及技术原因，并归纳关键挑战；挑战数量原则上与主要研究点数量一致；
2. 第二段将全部主要研究点合并为一个自然段，每个研究点仍按“简洁挑战或问题—技术或方法—核心机制—能力或效果”形成独立句组；
3. 第三段以任务书考核指标对应结果为主：定量指标写实际结果，定性指标写形成的能力/功能/成果；非任务书指标仅按需补充1—2个，然后写总体结论、研究前景、工程价值、适用条件和应用前景。

摘要不使用分点，不写成章节目录。第二段必须覆盖全部主要研究点，不能因合并段落而省略问题、技术名称、核心机制或能力，也不能把所有内容压缩成一个逗号、顿号堆叠的超长句。核心技术章多于三章时，先按共同问题或机制归并，再为每条研究线选择主机制和代表性能力。第三段必须先覆盖任务书考核结果，定量、定性两类都不能漏；非任务书指标最多补1—2个且必须有明显解释价值。研究与应用前景不得超出已验证能力。关键词默认严格为五个：前两个为通用领域词，后三个必须是与三个核心研究点对应的计算机/人工智能/算法技术词，优先选择深度学习、图神经网络、马尔科夫链、扩散模型、贝叶斯优化、对比学习、知识图谱等可检索技术术语，而不是电力业务对象或泛化“智能化/数字化”词。除非用户明确指定其他数量，不得增减。摘要表达同时执行 `references/narrative-focus-and-power-grounding.md`。

摘要草案展示给用户前，必须在内部检查三段结构、挑战—研究点对应关系、第二段研究点全覆盖、第三段量化结果与前景边界、证据一致性和五关键词结构。语义与证据一致性检查由模型完成；集成编排器另执行确定性摘要门禁，仅校验篇幅、段落结构、顺序词和中英双语字段。任一检查不通过时先修订，再输出草案。

### 阶段 G：摘要、关键词和总结收束

主体章节全部确认后才能执行。

#### 摘要准备

不得直接根据整篇长报告临时概括摘要。进入 `BODY_CONFIRMED` 后，先在内部完成 `ABSTRACT_PREPARED`：

1. 重新读取 `references/abstract-and-introduction.md`；
2. 读取并补全 `abstract_evidence`，不得只依赖早期章节摘要；
3. 将已确认技术章归并为主要研究点；默认可按三条主要研究线组织，核心技术章数量可以多于三章，但每章对应的研究内容和证据不得在归并过程中丢失；
4. 检查关键挑战数量是否原则上与主要研究点数量一致，并确认每个研究点均具备“问题—技术名称—核心机制—能力—验证证据—适用条件”；
5. 逐项核对当前报告范围内任务书考核要求：定量指标登记实际结果/条件/正文位置，定性指标登记能力、功能或成果结果/适用条件/正文位置；若需使用非任务书指标，最多选择1—2个；
6. 基于业务对象、现实问题和能力需求生成3—5个中文摘要首句候选，标记1句推荐首句；候选不进入正式摘要正文计数；
7. 提前锁定五个关键词；
8. 形成内部三段式提纲。

证据缺失时使用保守、可追溯的表述，不得为了补齐三段结构虚构指标、效果或前景。

#### 摘要草案

完成摘要准备后，按 `templates/abstract.md` 的顺序生成三个连续自然段。默认结构为：

1. 第一段说明领域现状、现实需求、现有不足及其技术原因，并归纳关键挑战，不提前展开方法；关键挑战原则上与主要研究点一一对应；
2. 第二段合并介绍全部主要研究点，按第一段挑战顺序为每个研究点形成“挑战或问题—技术或方法—核心机制—能力或效果”的完整句组，并说明必要的承接、集成或反馈关系；
3. 第三段先写任务书定量/定性考核要求的对应结果，再按需最多补充1—2个非任务书指标，随后写总体结论、研究前景、工程价值、适用范围、推广条件和有证据支撑的应用前景。

`generate_abstract` 的结构化产物必须同时返回 `opening_sentence_candidates_cn`（3—5句）、`selected_opening_sentence_cn`、`assessment_result_coverage` 和 `supplementary_metrics_used`。候选首句用于用户选择，不属于摘要正文；若用户未单独选择，`abstract_cn` 第一整句必须等于 `selected_opening_sentence_cn`。`assessment_result_coverage` 逐项登记任务书定量/定性考核结果，`supplementary_metrics_used` 最多2项。

摘要必须恰好使用三个连续自然段，不使用分点，不写成目录，不加入正文没有的技术、结果或前景判断。三个自然段分别围绕“背景与挑战、合并研究工作、结果与前景”三个主旨。第二段可使用多个完整句子，但不得用多个逗号或顿号将技术、机制、动作和效果压缩为长串并列；无法形成同一逻辑链的内容应拆句或删去次要细节。关键词默认严格生成五个：第1—2个为与报告主题直接相关的通用领域词，第3—5个分别对应三个核心研究点，并使用计算机/人工智能/算法领域的技术名词或名词短语。后三个关键词不要求与二级标题逐字相同，但必须能追溯到对应研究点的核心技术。除非用户明确指定其他数量或结构，不得增加第六个关键词。

#### 摘要内部检查

草案生成后、展示给用户前进入 `ABSTRACT_CHECKED`。内部检查至少包括：

- 是否恰好为三个自然段；
- 第一段是否包含现状、需求、不足、技术原因和挑战；
- 挑战数量是否原则上与主要研究点数量一致，二者对应关系是否明确；
- 第二段是否覆盖全部主要研究点，且每个研究点均包含问题、技术名称、核心机制和能力；
- 是否生成3—5个业务需求背景首句候选，推荐首句是否实际成为中文摘要第一整句；
- 第三段是否覆盖当前范围任务书全部考核指标的对应结果，定性指标是否写成能力/功能/成果结果；
- 非任务书指标是否最多1—2个且确有解释价值；
- 第三段是否在结果之后包含总体结论、研究前景、工程价值、应用前景和适用条件；
- 技术名称、能力和数值是否均可在 `abstract_evidence` 或已确认正文中找到依据；
- 是否出现新技术、新缩写、未经登记的普通指标、章节编号、任务书口吻、“考核指标/考核要求”等外部规定口吻或目录式复述；摘要可以写考核事项对应的实际结果，但不能暴露来源身份或复述验收条款；
- 是否存在过多过渡词、无信息过渡句或逗号顿号堆叠的并列；
- 三个自然段是否分别具有清晰主旨，第二段各研究点的技术、机制和效果是否形成逻辑链；
- 是否严格形成两个通用领域词和三个研究点技术词。

语义、事实、证据边界和中英文对应关系由模型完成内部检查；集成编排器可运行摘要专用确定性校验，只检查中文摘要总字数、第一/第二段字数、三段结构、排序词以及英文摘要字段是否同时存在。任一检查不通过时先自行修订，不得把未检查草案直接交给用户。

摘要草案通过内部检查后再等待用户确认，不同时输出最终组装稿。

#### 总结与展望

如果总结与展望已作为最后一章逐章完成，则不重复生成；只根据用户要求进行收束修改。最终总结章必须保持“单一一级标题 + 700—800字连续正文”，不得在定稿阶段重新拆出“总结”“展望”“主要成果”等二级或三级标题。总结中的每条主要成果必须把可追溯的定量结果、目标阈值、数据规模或工况范围，与定性技术判断结合，并明确其对电网设备运行、调度决策、故障处置、运检业务或工程部署的意义。缺少真实结果时，“已实现成果”使用已确认设计条件或明确数据占位，不得把 REFERENCE_EXPERIMENT 模拟数值写成真实成果；如需提及模拟结果，只能明确说明其参考实验身份和待真实实验核验状态，也不得只写抽象的“性能提升、效果良好”。

如果尚未生成，则单独作为一个阶段生成并等待确认。

### 阶段 H：最终组装

只有以下条件全部满足时才能组装：

- 项目档案已确认；
- 中心主旨已确认；
- 目录已确认；
- 所有主体章节已确认；
- 摘要已确认；
- 总结与展望已确认或已作为主体章节完成；
- 用户明确要求“组装全文”或同等表达。

最终组装只负责：

- 按确认目录排列内容；
- 统一编号、Markdown 标题层级和格式；
- 保留必要的数据和图表占位；网络不可用且用户也无来源时，可保留统一的 `【待补充来源】` 引用占位；
- 清除正文中的任务书、申报材料、课题编号、最终材料、结题材料、验收材料、考核指标、考核要求、考核细则、规定指标等外部文件或规定来源词汇，以及编号式章节互引；
- 对已核验来源生成真实参考文献表；不得为占位编造文献条目；
- 对已核验来源在附录生成“参考文献来源与获取链接”，列出 DOI、官方网页和合法下载链接；
- 文中存在 `【待补充来源】` 时，附录必须另设“待补充来源清单”，列明主题、正文位置和建议来源类型；
- 检查 `research_content_coverage`，确认所有技术性研究内容、进度事项和考核细则均已在正文、图表、公式、实验或附录证据中覆盖；
- 检查技术章公式需求是否落实，统一公式编号、符号和 Markdown 数学格式；
- 对 `must` 章节运行 `scripts/validate_formulas.py` 的基础校验，发现公式缺失或符号说明缺失时回退修改；
- 能够运行脚本时，对覆盖矩阵执行 `python scripts/validate_research_coverage.py research-content-coverage.json --mode final`；
- 使用 `python scripts/validate_word_count.py 完整报告.md --outline 已确认目录.json --min-ratio 0.8` 复核每章正文均不低于计划字数的80%；不足时回退对应章节补充，不得在组装阶段静默扩写；
- 所有模型参与的组装与校验完成后，最后调用 `python scripts/normalize_markdown.py 完整报告.md --in-place --dash-style hyphen`。该脚本统一长划线并删除数字与汉字之间的空格；用户明确要求保留中文长划线时改用 `--dash-style em-dash`；
- 默认生成可下载的 `.md` 文件。

除非用户明确指定其他格式，最终成果不得只以内联长文本交付，也不得默认生成 DOCX、PDF 或 HTML。需要其他格式时，应先生成并保留 Markdown 源文件，再基于该文件转换。

不得借组装阶段重新大幅改写已确认章节。发现需要实质修改时，应指出受影响章节并回退到对应阶段，而不是静默改写。若仅发现“任务书中要求”“课题一中提出”“最终材料中显示”“第二章中说明”“第六章中的应用”“上一章已经”等外部来源、行政任务或编号式互引表达，可在不改变技术含义的前提下统一改为技术目标、明确技术对象以及“本文、前文、后文、前述”等独立报告口吻。若发现通过具体章节编号说明全文组织的内容，应改为研究对象、技术关系、输入输出或研究推进关系的自然表述。

# 摘要、项目概述与发展现状生成规则

## 1. 摘要不得在全文结束后临时概括

摘要规则属于强制状态约束，不是仅在最终阶段参考的写作建议。不得等主体全文完成后，才依赖模型对长上下文的临时记忆自由提炼摘要。

目录和中心主旨确认后，必须初始化 `abstract_evidence`，结构见 `schemas/abstract-evidence.schema.json`，模板见 `templates/abstract-evidence.json`。该证据包用于持续记录：

- 领域现状和现实需求；
- 现有技术不足及其技术原因；
- 关键挑战及其与研究点的对应关系，挑战数量原则上与研究点数量一致；
- 各主要研究点的问题、技术名称、核心机制和形成能力；
- 各研究点对应的已确认章节；
- `task_book_assessment_results`：当前报告范围内任务书考核指标的对应结果，包括定量指标的实际数值/结果与定性指标的能力、功能或成果结果，以及证据状态、测试/适用条件和正文位置；
- `supplementary_result_metrics`：仅在确有解释价值时补充的非任务书指标，全文摘要最多1—2个，不按研究点机械配指标；
- 总体结论、研究前景、应用价值、应用前景、适用条件和能力边界；
- 默认五个关键词的候选与最终方案。

每个技术章节的计划阶段应说明该章是否贡献于某个摘要研究点、对应哪项关键挑战，以及准备形成哪些摘要证据。每个章节正文经用户确认后，必须立即更新 `abstract_evidence`，而不是只保存笼统的章节摘要。未由正文或实验确认的内容只能标记为 `planned`、`partially-verified` 或 `insufficient`，不得提前写成已实现效果。

## 2. 摘要生成时点与独立准备阶段

摘要必须在主体技术章节和总结性结论基本确认后生成，以已确认正文和 `abstract_evidence` 中的证据为依据。不得根据早期目录猜测成果，不得写入正文尚未出现的方法、指标或结论。

从 `BODY_CONFIRMED` 进入摘要生成前，必须完成独立的摘要准备阶段：

1. 重新读取本文件，而不是依赖项目开始时的旧记忆；
2. 读取 `abstract_evidence`，检查关键挑战、研究点及其对应关系是否完整；
3. 将全部技术章节归并到主要研究点，默认可归并为三条主要研究线，但研究点数量应服从项目实际内容；
4. 检查每个研究点是否均具备“问题—技术—核心机制—能力—证据—条件”；
5. 逐项核对当前报告范围内任务书考核指标：定量指标准备实际结果、条件和正文依据；定性指标准备对应的能力/功能/成果结果和正文依据。任务书考核指标是摘要第三段指标性结果的主集；非任务书指标仅在明显有助于解释核心效果时补充1—2个，超过2个必须删减；
6. 基于业务对象、现实痛点和业务能力需求生成3—5个“业务需求背景分析”首句候选，写入 `business_need_opening_candidates`；候选之间应采用不同切入角度但保持同一事实边界；选出1句作为推荐首句并写入 `selected_business_need_opening`；
7. 锁定五个关键词：前两个通用领域词，后三个选择最具代表性的研究点技术词；
8. 锁定中文摘要篇幅：正文总有效字数700—800字；第一段200—250字；第二段300—350字；第三段不另设固定区间，以补足总字数并完成结果、结论与前景表达为准；
9. 锁定挑战与研究点的排序表达方案。第一段和第二段必须在连续自然段中使用明确顺序词，可采用“第一、第二、第三……”或“首先、其次、再次……”等同类表达，前后顺序必须对应；
10. 形成内部三段式提纲后，先生成中文摘要，再基于已定稿中文摘要同步生成英文摘要和英文关键词。英文摘要不得独立扩写新的技术、指标、结果或前景。

生成摘要时，应以“摘要规则 + 摘要证据包 + 三段式内部提纲”为主要输入。全文只用于必要的事实回查，不得把整篇长文作为唯一输入后自由概括。

## 3. 摘要固定组织方式与篇幅

中文摘要固定采用三个连续自然段，摘要正文总有效字数控制在700—800字。有效字数按“中文字符逐字计数，连续英文或数字记为一个词”的方式统计，不计摘要标题与关键词。第一段控制在200—250字，第二段控制在300—350字；第三段不单设固定字数区间，以补足700—800字总篇幅并完成结果、结论、研究前景和应用前景表达为准。

第一段提出现状、需求与挑战；第二段将原有各研究点内容合并为一个研究工作段；第三段以任务书考核指标对应结果为主，集中说明定量/定性结果、总体结论、研究前景与应用前景，非任务书指标按需最多补充1—2个。无论项目研究点数量如何变化，三段结构均不得改变。

### 3.1 内容摘要首句：先生成业务需求背景候选，再选一句入正文

正式中文摘要仍只有三个自然段，但在生成第一段前必须先形成 **3—5个首句候选**。这些候选是摘要产物的伴随选择项，不计入摘要正文，也不得全部写进最终摘要。

候选首句必须直接从当前电力业务场景切入，至少体现“业务对象/运行场景 + 现实问题或能力缺口 + 需要具备的业务能力”中的两项，优先回答“为什么当前业务需要这项研究”，而不是泛泛介绍技术发展。候选可以分别从运行压力、人工处置瓶颈、数据/知识使用困难、时效/可靠性需求或工程协同需求等角度切入，但不得为了差异化新增事实。

首句候选规则：

- 默认生成3—5句，彼此不能只是同义词替换；
- 不以“近年来，随着……快速发展”“随着人工智能技术不断发展”等泛化句式开头；
- 不在首句提前写具体算法、模型、实验指标或研究结果；
- 每句都必须能够单独作为第一段第一句，并与后续现实需求、现有不足和挑战自然衔接；
- 生成后标记1句 `selected_business_need_opening` 作为推荐首句；若用户未单独指定，最终 `abstract_cn` 第一整句必须使用该推荐句；用户选择其他候选时，只替换首句并同步调整英文摘要对应首句，不改变事实边界。

### 第一段：现状、需求与挑战

先说明研究领域或应用场景的现状，再指出现实需求及现有技术的不足，最后归纳本文需要解决的若干关键挑战。

本段必须同时写清：

- 问题发生的实际场景；
- 当前业务或科学任务需要具备的能力；
- 现有技术表现出的不足；
- 形成这些不足的技术原因；
- 本文需要解决的关键挑战。

关键挑战应与第二段中的研究点建立清晰对应关系。项目有几个主要研究点，原则上就归纳几个关键挑战；默认三研究点项目通常对应三项挑战。确需一项挑战由多个研究点共同解决，或一个研究点同时回应多项挑战时，必须在 `abstract_evidence` 中登记对应关系和原因，不得为了凑数量机械拆分或合并。

本段必须对关键挑战使用明确的顺序词进行排序。默认三项挑战时，可使用“第一、第二、第三”或“首先、其次、再次”等自然衔接方式；挑战多于三项时按实际数量继续排序。排序词必须嵌入自然段，不得改写为项目符号或编号列表。该要求是摘要专属结构规则，不属于机械列举。

挑战既要描述现象，也要说明困难形成的原因，但不得在本段提前展开具体方法、模型结构和实验结果。不得以“近年来，随着……快速发展”作为默认开头，也不得把本段写成政策背景或意义口号。

### 第二段：合并说明全部研究点

将原第二、第三、第四段的研究内容合并为一个连续自然段，按第一段挑战的顺序依次介绍全部主要研究点。每个研究点仍必须保留以下内部语义链：

`挑战或问题 → 提出的研究点 → 核心技术机制 → 实现的能力或解决效果`

默认三研究点项目应在本段形成三个逻辑清晰的句组，每个句组分别对应一个研究点；句组之间可使用必要的承接关系，但不得使用编号列表、段内小标题或章节编号。研究点数量不是三项时，按实际数量组织句组，不能遗漏任何主要研究点，也不能把多个研究点压缩成只有技术名称的并列清单。

本段必须按照第一段挑战的顺序，用明确的顺序词介绍对应技术点。可使用“第一、第二、第三”或“首先、其次、再次”等表达；排序位置必须与第一段挑战逐项对应。允许第一段和第二段采用不同但等价的顺序词体系，但不得改变挑战—研究点映射顺序。

各研究点应保持逻辑平行，但不要求句式和长度完全一致。若后续研究点依赖前序研究点，应使用少量文字说明输入、承接、约束、集成或反馈关系。承担系统集成、工程应用或综合优化作用的研究点，应写清其如何整合其他成果并形成面向实际场景的完整解决方案。

本段的主要表达任务是完整说明“本项目开展了哪些研究以及如何解决对应挑战”。虽然包含多个研究点，但每个句组仍应只突出一个主机制和一个代表性能力，避免用一个超长句连续堆叠多项技术、动作和效果。

### 第三段：任务书考核结果、总体结论与研究应用前景

第三段的指标性结果必须以**当前报告范围内任务书考核指标**为主线，不再从各技术章节自由挑选大量普通实验指标。任务书中的定量指标和定性指标都必须建立对应结果：

- **定量考核指标**：写正文已有依据的实际数值、范围、相对结果或可确认结果，并尽量交代必要测试条件/比较对象；不要在摘要中机械复述“应达到/不低于/不超过××”的任务书门槛。
- **定性考核指标**：即使没有数值阈值，也不得遗漏。应写成正文已经形成或证实的能力、功能、流程、系统成果、适用性或工程效果，例如“形成了……能力”“实现了……功能”“建立了……支撑关系”，并能追溯到正文位置。
- 同类考核指标较多时允许压缩成一个句组，但 `abstract_evidence.task_book_assessment_results` 中仍须逐项登记，不能因为摘要篇幅而静默漏掉。

除任务书考核指标外，**非任务书指标默认不写**。只有某个普通实验指标能够明显帮助解释核心方法效果、且不写会使结论难以理解时，才允许补充；整个中文摘要最多补充1—2个非任务书指标，不得按每个研究点分别配一个，也不得把摘要第三段写成指标流水账。 若当前项目确无任务书或当前报告范围不存在可用考核指标，则不虚构“任务书指标”，改为从已确认正文中选择1—2个最能代表整体效果且证据充分的结果指标作为第三段结果支撑。

在这些结果基础上，总结各研究点共同解决了什么总体问题，形成了什么综合能力。随后说明仍需深入研究的技术问题、可继续拓展的研究方向，以及成果的工程价值、适用场景、推广条件和应用前景。研究前景与应用前景必须建立在已经确认的定量/定性结果和明确适用条件上，不得脱离证据作宽泛展望。

摘要整体逻辑固定为：

`业务需求背景首句 → 领域现状与现实需求 → 按顺序归纳关键挑战 → 按对应顺序说明全部研究点及其技术机制与能力（同一段） → 任务书定量/定性考核结果 → 可选1—2个补充指标 → 总体结论 → 研究前景 → 应用价值、条件与前景`

### 3.2 英文摘要同步生成

`generate_abstract` 阶段必须在同一次产出中同时生成中文摘要、中文关键词、英文摘要和英文关键词。英文摘要以最终中文摘要为唯一内容基准，保持相同的三段结构、挑战顺序、研究点顺序、技术名称、数值、结论和能力边界，不另行增加材料；三个英文自然段之间留空行，不能用段内换行代替分段。英文关键词应与中文关键词逐项对应并保持相同顺序。

英文摘要不设置独立字数或词数门槛；其首要要求是忠实、完整地对应中文摘要，不因翻译压缩而遗漏关键挑战、核心技术点或代表性结果。

## 4. 摘要生成后的内部一致性检查

摘要草案生成后、展示给用户前，必须在内部完成语义检查。语义、证据和中英文逐段对应关系仍由模型依据下列规则检查；编排器另使用确定性门禁校验中文摘要篇幅、中英文各三自然段、顺序词和双语字段是否齐全。以下任一项不满足时必须先自行修订：

- 中文摘要正文是否恰好形成三个连续自然段；
- 中文摘要正文总有效字数是否为700—800字，第一段是否为200—250字，第二段是否为300—350字；
- 第一段关键挑战和第二段研究点是否均使用明确顺序词，并保持挑战—研究点的对应顺序；
- 是否在同一次摘要产出中同时提供英文摘要和英文关键词，且英文内容与中文摘要逐段对应；
- 第一段是否同时包含现状、需求、不足、技术原因和关键挑战；
- 关键挑战数量是否原则上与主要研究点数量一致，挑战与研究点对应关系是否清晰；
- 第二段是否覆盖全部主要研究点，并且每个研究点均包含问题、技术名称、核心机制和能力；
- 是否已生成3—5个业务需求背景首句候选，推荐首句是否属于候选集合，且中文摘要第一整句是否使用推荐/用户选定候选；
- 第三段是否以任务书考核指标结果为主，是否同时覆盖定量和定性考核要求；定性指标是否给出了对应能力/功能/成果结果，而不是只保留要求原文；
- 非任务书指标是否确有必要且全文摘要最多1—2个；是否存在按研究点机械堆指标或自由挑选大量普通实验指标；
- 第三段是否在结果之后包含总体结论、研究前景、应用价值、应用前景和适用条件；
- 摘要中的技术名称、能力声明、数值和前景判断是否能在 `abstract_evidence` 或已确认正文中找到依据；
- 是否出现正文中不存在的新技术、新缩写、新指标或新应用结论；
- 是否出现章节编号、任务书口吻、目录式复述或分点；
- 是否存在过多过渡词、无信息过渡句或长串并列；
- 三个自然段是否分别承担“背景与挑战、合并研究工作、结果与前景”的唯一主要任务；
- 关键词是否符合默认五关键词结构。

检查的是语义字段是否完整，不是机械要求每个研究点句组都出现“针对、提出、通过、实现”等固定词语。允许句式变化，但不允许信息缺项。

## 5. 摘要表达要求

摘要表达同时执行 `narrative-focus-and-power-grounding.md`。三个自然段分别承担背景与挑战、研究工作、结果与前景三个主要表达任务。除摘要专属排序词外，过渡词只在逻辑关系无法由内容本身体现时使用，不得为了显得连贯而连续加入“此外、同时、进一步、在此基础上、因此、综上”等过渡句。第一段用于排序挑战、第二段用于排序技术点的“第一、第二、第三”或“首先、其次、再次”等表达属于本摘要结构的必要标记，不按模板化过渡词处理。

第二段虽然合并多个研究点，但不应写成一个充满顿号和逗号的超长句。优先用多个完整句子或清晰句组分别表达各研究点，按“问题—机制—能力”重组，再用必要的因果、先后、约束、包含或反馈关系连接。核心技术章多于三章时，先归并研究线，不把所有章名压缩为一串并列短语。

- 摘要必须使用三个完整、连贯的自然段，不使用分点；
- 不出现章节编号、图表编号、公式编号和参考文献标号；
- 不写“任务书要求”“课题安排”等材料来源表述；
- 不引入正文没有出现的技术或结果；
- 任务书定量考核结果必须与正文、表格和结论保持一致；任务书定性考核要求必须在摘要中转写为有正文依据的对应能力、功能或成果结果；
- 非任务书指标按需最多补充1—2个，除非用户明确要求，不得在摘要中继续增加；
- 方法名称应稳定，不在摘要中临时创造新缩写；
- 研究前景应指出可继续解决的技术问题或可验证方向，不写抽象口号；
- 应用前景应落到具体业务能力、工程条件、适用场景或部署路径；
- 摘要正文可使用 `templates/abstract.md` 组装，但正式输出不得保留内部占位、段落标签或注释。

## 6. 关键词

关键词默认严格为五个，并在摘要准备阶段提前锁定：

1. 第一个关键词：通用领域词，表明所属研究领域；
2. 第二个关键词：通用领域词，表明核心研究对象或业务领域；
3. 第三个关键词：对应第一核心研究点的计算机/人工智能/算法技术词；
4. 第四个关键词：对应第二核心研究点的计算机/人工智能/算法技术词；
5. 第五个关键词：对应第三核心研究点的计算机/人工智能/算法技术词。

默认三研究点项目中，后三个关键词分别对应三个研究点，并优先选用可检索、稳定、具有明确计算机技术含义的名词或名词短语，例如深度学习、图神经网络、马尔科夫链、扩散模型、贝叶斯优化、对比学习、强化学习、知识图谱等。研究点多于三项时，应选择区分度最高、最能代表主要技术链的三个计算机技术词；研究点少于三项时，可从核心算法、模型、概率推断、优化、知识或系统技术中补足。后三个关键词不得仅使用电网、调度、设备、智能化、数字化、技术研究、系统应用等业务对象或泛化词。

关键词应使用规范、稳定、便于检索的名词或名词短语，不使用完整句子，不选择“技术研究”“智能化”“数字化”等过于宽泛且缺少区分度的词，也不选择仅在正文局部出现的次要术语。第3—5个关键词属于技术关键词专位，即使对应技术词在一般写作风格规则中被视为专业术语，也不得因为术语化或计算机领域属性被改写成业务词。

除非用户明确指定其他数量或排列方式，必须只生成五个关键词，不得增加第六个关键词。

## 7. 第一章“项目概述”

第一章必须命名为“项目概述”，不得使用“引言”“绪论”或其他名称。二级、三级标题固定为：

```text
1.1 项目背景与研究意义
1.1.1 项目研究背景
1.1.2 项目研究意义
1.2 国内外研究现状
1.2.1 国外研究现状
1.2.2 国内研究现状
1.3 主要研究内容及思路
1.3.1 主要研究内容
1.3.2 研究思路
```

第一章不得再增加同级二级标题，也不再单设“国内外发展现状”一级章。技术章节从第2章起按报告范围映射。

### 7.1 项目研究背景

从具体电力业务场景、运行对象、现实需求和已有条件开场，说明项目面对的实际问题、当前能力缺口及问题形成的业务或技术背景。背景用于说明“为什么需要开展这项研究”，不提前展开后续技术方案，不写成政策、行业口号和技术发展史的长篇堆叠。引用政策、行业数据、工程指标或权威结论时必须有来源。

### 7.2 项目研究意义

在背景基础上说明解决上述问题后能够改善的运行能力、工程效率、安全水平、技术认识或业务支撑能力。研究意义必须与项目真实问题和预期成果对应，不做脱离研究边界的价值拔高。

### 7.3 国外研究现状

按当前报告范围内的研究主题组织国外代表性工作。每个主题先概括共同技术路线，再综合代表性文献，说明取得的进展、成熟度、适用条件和仍未解决的问题。不得逐篇文献机械罗列，也不得为了形成对比虚构差异。

### 7.4 国内研究现状

采用与国外研究现状一致的研究主题和比较口径，综合国内代表性工作、工程应用、成熟度、适用条件和不足。国外与国内两节文献数量可以不同，但研究主题应可对应，便于归纳与本项目相关的技术缺口。

生成1.2前必须在章节计划中锁定一种作者指代样式：默认“XXX等人”，也可以统一选择“XXX团队”。1.2.1和1.2.2必须沿用同一选择。机构、标准组织和官方项目直接使用正式名称，不纳入人名指代样式。

### 7.5 主要研究内容

`1.3.1 主要研究内容`必须与技术规划书、任务书或等效技术文件中的当前报告范围研究内容逐项对应，并保持原始顺序和边界。对每项研究内容可以稍作展开，以便说明研究对象、主要问题、核心任务和预期形成的技术能力，但不得增加来源文件没有的研究方向、算法、指标、成果或应用结论。

总报告中，每个课题或一级研究内容与后续一个技术章一一对应；具体课题报告中，每个来源研究内容小点与后续一个技术章一一对应。此节是目录映射和后续章节边界的主要依据。

### 7.6 研究思路

`1.3.2 研究思路`说明各研究内容之间的总体逻辑、依赖关系、输入输出、关键处理链、研究推进顺序和验证思路。适合时安排总体研究思路图。

本节不再承担“章节安排”职责，不逐章复述目录，不使用“第二章、第三章”等章号说明全文组织。

## 8. 技术章节的章首无标题导入正文

技术章节从第2章起。一级章标题之后直接写章首导入正文，不设置“概述”“技术路线”“技术架构”“技术路线与总体架构”等二级标题。原概述和路线/架构信息在该无标题正文中合并完成：

1. 简要说明与本章主题直接相关的背景、现实问题和研究意义，类似第一章背景与意义，但只服务当前技术主题；
2. 自然引出本章研究对象、核心问题和研究主题；
3. 概括本章总体技术路线或系统架构，说明关键输入、主要处理链、模型/算法/模块关系、输出和能力边界；
4. 适合时优先采用“文字说明 + 技术路线图/架构图”的图文结合方式。

以5万字全文为基准，该章首导入正文目标约800—1200字；其他全文目标字数按约1.6%—2.4%同比例规划。该范围用于章节计划和写作控制，不应通过重复背景或空泛过渡凑字数。

章首导入之后默认进入X.1、X.2、X.3三个核心研究小点；若存在经确认的必要扩展，则继续进入X.4或X.5核心研究小点。

## 9. 技术章节“本章小结”

本章小结的结构位置、篇幅、总—分—总组织、成果归纳、实验结果使用方式、生成时机与验收统一执行 `references/chapter-summary.md`。本文件不再维护另一套小结正文规则。

## 10. 独立报告口吻

摘要、项目概述、国内外研究现状和技术章节均不得出现“任务书中要求”“课题一提出”“根据最终材料”等来源口吻。外部要求应转化为报告自身的研究目标、性能约束和验证标准。

正式正文不得使用具体章节编号、上一章或下一章进行跨章互引。需要说明研究关系时，直接使用技术对象名称、研究内容名称或“本文、前文、后文、前述方法、在此基础上”等自然表达。

# 总结与展望规则

## 0. 结构与篇幅硬规则

最后一章只能使用“总结”“总结与展望”或“结论”作为**唯一一级标题**。该章正文直接连续写在一级标题下：

- 不设置任何二级标题；
- 不设置任何三级标题或更低级标题；
- 不使用“X.1 总结”“X.2 展望”“主要成果”“不足与展望”等分节标题；
- 可以通过自然段完成成果归纳、局限与展望，但不能用标题把正文再次切分；
- 中文正文有效字数必须为 **700—800字**；该范围为最终总结章专属硬门禁，不按全文总字数同比例折算，也不适用普通章节“达到计划字数80%即可”的规则；
- 建议目录将该章 `target_words` 设为750、`minimum_words` 设为700，并以800作为最大允许字数。

总结围绕第一章提出的总体问题和关键挑战收束，不按目录逐章复述。每项成果写清问题、具体技术、证据、形成能力和适用边界。

## 1. 定量与定性必须结合

总结中的每项主要成果必须同时包含：

- **定量表述**：来自已确认正文的性能值、误差、时延、阈值、数据规模、设备规模、工况范围、资源消耗或其他可核验数字；
- **定性判断**：解释该数字反映了什么能力、为什么形成该结果、在什么条件下成立以及仍有哪些边界；
- **电力意义**：说明成果对电网设备运行、调度决策、潮流安全、故障处置、运检业务、供电可靠性或工程部署的实际作用。

定量和定性不应割裂为互不相关的两句话。优先采用“条件或数值—能力判断—电力作用—适用边界”的逻辑链。例如，先给出在某类电网工况下的响应时间或准确率，再说明该结果能否支撑调度时限、设备状态识别或故障处置。

没有真实结果时，只能使用已确认的设计阈值、运行条件或明确的 `【待补充数据：……】`，并写明仍需验证。不得编造数字，也不得用章节数量、技术点数量、标题数量等无技术意义数字充当定量成果。

## 2. 组织方式

控制过渡词和并列堆叠。多个成果应按总体问题下的逻辑关系组织，不写成“提出了……、构建了……、实现了……”的长串清单。每个成果段只突出一个主要判断，必要的多个数值应围绕同一能力解释。

## 3. 局限与展望

局限具体到数据规模、场景覆盖、物理假设、设备条件、实时性、部署复杂度和维护要求，并尽可能给出相应范围或阈值。展望由这些局限自然推出，不写无证据的宽泛前景，也不脱离电力系统实际运行需求。

# 表达与成稿风格

正式正文必须同时遵循 `narrative-and-heading-style.md` 与 `narrative-focus-and-power-grounding.md`。项目档案、目录说明和章节计划可以结构化分点；进入报告正文后，默认采用自然段落，只有离散且需要逐项核对的内容才使用列表。

## 1. 基本风格

- 专业、准确、克制；
- 从对象、任务和矛盾出发；
- 以机制和证据支撑判断；
- 章节有主次，段落长短自然；
- 保留条件、代价和局限；
- 避免模板腔、宣传口号和汇报提纲式正文；
- 通过真实的因果、对比和承接建立逻辑，不依赖大量编号分点。

## 1.1 独立报告口吻

- 把任务书、申报材料和课题分工视为内部素材，不在正文中提及其来源身份；
- 不写“任务书中要求”“课题一中提出”“按照课题分工”等表达；
- 将外部要求改写为设计目标、性能约束、验证条件或工程边界；
- 正文不使用“第二章中说”“如第四章所述”等编号式互引；
- 跨部分衔接优先使用“本文、前文、后文、在此基础上、进一步”以及明确的对象名称；
- 第一章1.3.2“研究思路”只说明研究内容之间的逻辑和推进思路，不逐章报号；其他正文同样不使用章号互引；
- 详细规则见 `independent-report-voice.md`。

## 2. 正文叙述优先级

正文优先采用：

- 问题—原因—方案；
- 结论—证据—解释；
- 场景—约束—设计；
- 比较—差异—机制；
- 能力—条件—边界。

分析性段落通常应包含“明确对象、具体事实、技术机制、实际影响”中的至少两项，但不要把这四项机械拆成四个分点。

背景、发展现状、技术动机、机理解释、结果分析和总结收束应以段落为主。模块清单、流程步骤、约束条件、参数设置和指标体系可按实际需要分点。

## 3. 分点使用边界

分点必须具有必要性。出现以下任一情况时可以使用：

- 内容是可独立核对的并列项；
- 顺序本身影响理解或执行；
- 需要清楚展示字段、模块、参数、条件或职责；
- 使用段落会掩盖对象边界。

以下情况不要分点：

- 几个句子共同解释同一个原因或机制；
- 发展现状只是按文献逐条介绍；
- 结果分析需要解释趋势和原因；
- 为了显示“逻辑清晰”而把普通段落拆碎；
- 每个分点只有一句空泛判断。

分点后如仍需解释原因，应在列表前后使用自然段衔接，不让整页正文都变成列表。

## 4. 避免的写法

避免无内容支撑的：

- 随着……不断发展；
- 具有十分重要的意义；
- 提供有力支撑；
- 全面赋能；
- 实现整体提升；
- 填补行业空白；
- 达到国际领先水平；
- 具有广阔应用前景；
- 效果显著、性能优异。

这些表达只有在后文紧跟具体对象、机制、数据和条件时才可使用。

## 5. 活人感与自然度

- 不让每节使用完全相同的开头；
- 不机械重复“首先、其次、再次、最后”；但摘要第一段和第二段按 `abstract-and-introduction.md` 对挑战与技术点进行对应排序时属于强制例外，不得删除这些必要顺序词；
- 不让每段都用总结句收尾；
- 复杂问题可先给判断再解释，也可先描述现象再归纳；
- 避免连续等长段落和连续同构句式；
- 对技术选择写清取舍，而不是只写优点；
- 适当保留“不适用于什么”“为什么没有采用另一方案”等真实判断；
- 章节小结与最终总结保持不同抽象层级；
- 不将章节契约或提纲原样展开成正文。

## 6. 标题层级与用词

- 技术章X.1—X.N核心研究小点默认分别继续拆分为2—4个三级标题，必要覆盖时单节最多5个；章首导入正文不设置标题，本章小结统一执行 `references/chapter-summary.md`，一般非技术章节仍按内容密度决定是否展开；
- 同一技术章三个核心二级节的三级标题数量可以在2—4个之间不同，但不得有任何一节缺少三级标题；
- 不追求全篇小节数量和标题句式完全对称，强制的是核心二级节均有三级展开，不是标题措辞对称；
- 一级技术章标题直接采用对应研究内容小点的名词化表达，只允许进行必要语法整理，不得添加来源没有的技术信息；
- 目录生成前先区分课题角色：前序课题为技术研究，最后一个课题为工程实现；
- 技术研究课题的一级、二级和三级标题不得把“机制、建模、体系、定义”作为独立命题、中心名词或落脚点，也不得机械改名；应直接描述实际采用的具体技术、方法、算法或模型；
- 工程实现课题的标题可使用系统、平台、架构、模块、接口、部署、集成或应用等工程中心词；
- 二级标题完整说明技术对象、具体方法和作用，三级标题进一步落到具体输入、处理动作、算法、模型、组件或接口；
- 一级标题可以包含必要的对象、场景和问题边界，但不把全部子技术、指标和结果压入标题；
- “总体方案、关键技术、核心方法、技术实现”等词不得在技术区单独成题；
- 默认不设置独立实验验证二级区；有限测试与结果内容优先在X.1—X.N下使用能够说明电力对象和分析内容的具体三级标题。只有 `evaluation-related` 主题且存在大量成体系数据或用户明确要求时，才允许使用与评估研究直接相关的“实验与结果分析、系统测试、应用验证”等二级功能标题；`non-evaluation` 主题二三级目录不得出现验证、评估、测试、试验、实验类章节词；
- “电力”仅在需要限定领域对象时加入标题；标题已含“电网、调度、潮流、配电”等领域词时通常不再重复添加；核心二级标题必须自身含有这类可识别电力元素，并同时含有具体人工智能方法；
- 标题不是越短越好。一级章表达完整技术边界，二级标题表达完整技术关系，三级标题进一步具体化；不得只说半句话，也不得使用“关键技术、数据处理、模型训练、参数设置、模块设计”等低信息标题。

## 7. 篇幅

- 核心技术及其直接证据和结果分析充分展开；
- 背景、常识和基础概念适度压缩；
- 无证据章节不能靠扩展意义和展望增加字数；
- 目标字数使用范围而不是机械精确值；
- 不通过增加列表数量或标题数量人为扩充篇幅。

## 8. 占位符

统一格式：

- `【待补充数据：……】`
- `【待补充来源：……】`
- `【待确认参数：……】`
- `【待补充实验结果：……】`
- `【图X-X占位：……】`

占位应说明缺少什么、用于支持什么，不使用模糊的“待补充”。

# 独立报告口吻与 Markdown 成果规则

## 1. 报告必须独立成立

正式报告应被视为一个已经完成技术组织的独立成果。任务书、申报书、申报材料、合同条款、课题分工、会议纪要、结题材料、验收材料、最终材料、交付材料和用户补充说明只用于内部提取技术目标、研究内容和数据，不得以文件名称、行政任务名称或材料身份进入正文。

正文应直接陈述研究背景、技术目标、方法、系统、必要证据和结论，使不了解材料来源的读者也能够完整理解全文。

## 2. 禁止暴露材料来源

正文禁止使用：

- 任务书中指出、任务书规定、任务书要求；
- 根据任务书、按照任务书；
- 课题一中要求、课题二提出、各课题分别负责；
- 根据申报书、根据合同、按照验收要求；
- 为完成任务书指标、满足课题要求；
- “考核指标要求……”“按照考核要求……”“考核细则规定……”等外部规定口吻；
- 课题一、课题2、子课题三等带编号的课题称谓；
- 最终材料中、结题材料显示、验收材料要求、根据申报材料、交付材料表明；
- 用户提供的材料显示、根据现有材料可知。

材料来源、真实性等级和待补充项应保存在内部状态、证据登记表或编辑占位中，不写入正式叙述。

### 改写示例

| 不允许 | 应改写为 |
|---|---|
| 任务书要求知识检索时间不超过10 s。 | 知识检索响应时间设计目标为不超过10 s。 |
| 课题一提出人机协同智能决策框架。 | 人机协同智能决策框架统一组织数据、知识、模型与人员协作关系。 |
| 为完成任务书中的部署指标，系统在两地开展试点。 | 系统在两个试点区域开展部署验证。 |
| 根据课题分工，电子规则库由第二项研究完成。 | 电子规则库为调度知识的统一存储、检索和约束匹配提供基础。 |
| 任务书规定策略有效率不低于95%。 | 非典型故障恢复策略有效率目标设定为不低于95%。 |
| 考核指标要求模型识别准确率不低于90%。 | 电力设备异常识别准确率目标设定为不低于90%。 |
| 最终材料中给出了三类应用场景。 | 验证范围覆盖三类典型应用场景。 |
| 课题2完成了知识图谱构建。 | 电网调度知识图谱实现了多源对象与关系的统一组织。 |

## 3. 禁止编号式章节互引

目录和标题可以正常使用章节编号，但正式正文不使用具体章号来组织叙述。第一章1.3.2“研究思路”只说明研究内容之间的总体逻辑、依赖、输入输出和推进思路，同样不使用“第二章、第三章……”复述全文结构。

除上述小节外，正文不得通过具体章节编号或章序关系互引其他内容。禁止：

- 第二章中介绍了……；
- 第六章中的应用……；
- 第四章提出的方法……；
- 如第三章所述……；
- 上一章已经说明……；
- 下一章将详细介绍……；
- 前一章形成了……；
- 后一章将验证……。

跨部分衔接优先使用：

- 本文；
- 前文；
- 后文；
- 在此基础上；
- 进一步；
- 随后；
- 前述方法／前述模型／前述规则库；
- 后续研究／后续验证。

| 不允许 | 应改写为 |
|---|---|
| 第二章构建的规则库用于第四章的策略生成。 | 前文构建的规则库为后续策略生成提供约束知识。 |
| 如第三章所述，模型采用两阶段训练。 | 前文所述模型采用两阶段训练。 |
| 第五章将开展综合验证。 | 后文将进一步开展综合验证。 |
| 第一章分析了现有方法的不足。 | 前文已归纳现有方法的主要不足。 |

第一章1.3.2“研究思路”中说明全文结构的段落可以逐章报号，例如：

> 第二章研究统一知识表示与电子规则库构建技术，第三章研究自主决策智能体构建方法，第四章开展系统集成与应用验证。

除该唯一位置外，其他正文应写成：

> 本文首先分析……，随后研究……；在此基础上，进一步构建……并开展……验证，最后总结主要成果及其适用边界。

## 4. “本文、前文、后文”的使用边界

- “本文”用于全篇研究目标、技术路线、方法贡献和综合结论；
- “前文”用于承接已经定义的对象、方法、结论和数据；
- “后文”用于提示随后将展开的技术或验证；
- 能直接复用对象名称时，优先写“前述规则库”“该模型”“上述方法”，避免连续重复“前文”；
- “本章”“本节”仅在局部组织确有必要时少量使用，不用于替代技术内容，也不用于频繁互引；
- “本章小结”作为固定标题允许保留。

## 5. 指标和要求的独立化表达

从任务材料提取的要求应转换为以下类型：

- 设计目标：响应时间设计目标为……；
- 性能约束：系统应满足……；
- 验证条件：测试覆盖……；
- 判定标准：当……时判定为有效；
- 工程边界：模块不直接下发控制命令。

不得保留“谁要求”“哪项课题规定”的来源口吻。正文也不直接使用“考核指标、考核要求、考核细则、规定指标”等词，而应写成报告自身的技术目标、性能约束、测试条件、判定规则和能力边界。需要追溯来源时，在内部证据登记表中记录，不在正文中展开。

## 6. 默认 Markdown 文件交付

最终成果默认生成 UTF-8 编码的 Markdown 文件：

- 扩展名：`.md`；
- 默认文件名：`报告简称-科技报告.md`；
- 使用规范 Markdown 标题层级；
- 图表占位、公式、代码和表格均保留为 Markdown；网络不可用且用户也无来源时，可保留统一的 `【待补充来源】`；
- 最终回复提供文件链接和一句简要说明，不在聊天中重复粘贴全文。

用户要求 DOCX、PDF、HTML 或其他格式时：

1. 先完成并保存 Markdown 源文件；
2. 再根据明确要求转换；
3. Markdown 文件仍作为可追溯源稿保留。

## 7. 成稿阶段内部检查

最终组装前在内部检查：

- 是否出现“任务书中、根据任务书、课题一、按照课题分工、最终材料中、结题材料显示、考核指标、考核要求、考核细则、规定指标”等外部文件、行政任务或规定来源表达；
- 是否在任何正式正文中出现具体章节编号，或“上一章、下一章、前一章、后一章”等章序互引；
- 是否已经改为独立技术陈述；
- 是否默认生成 Markdown 文件；
- 是否未在最终回复中重复铺开全文；
- 若存在 `【待补充来源】`，是否确因网络不可用且用户也无来源，并已生成“待补充来源清单”；
- 已核验来源是否已生成真实参考文献表和“参考文献来源与获取链接”附录。

检查只用于内部修正，不向用户输出独立审查报告。

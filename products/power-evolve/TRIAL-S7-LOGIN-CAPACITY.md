# S7 登录容量与准入回归探针

`qa-s7-login-capacity.mjs` 启动独立的 PostgreSQL 17 容器、两台真实 Platform 和 S7a Platform LB，预置 128 个额外测试账号，然后经公开 LB 并发发起真实 HTTP 登录。探针只输出汇总计数和资源采样，不保存账号口令或登录令牌。每次运行使用独立端口、数据库卷和 Docker `/28` 网络，完成后移除容器、网络及私密文件；聚合 JSON 留在 `.artifacts/power-evolve/s7login-*/login-capacity.json`。

在仓库根目录构建后运行：

```sh
pnpm run build:power-evolve
node products/power-evolve/scripts/qa-s7-login-capacity.mjs
```

2026-09-30 本机实测一轮如下。p50/p95/p99 是每个请求从发起到完整读取 HTTP 响应的延迟；进程 CPU 是 `ps` 采样百分比，PostgreSQL CPU/内存来自 `docker stats`，后者的 CPU 可以超过一个核的 100%。

| 阶段 | 结果 | 延迟 p50 / p95 / p99 | 批次耗时 | PG 连接峰值 | PG 锁等待峰值 |
| --- | --- | ---: | ---: | ---: | ---: |
| 无 PG 的 `/config` 对照，128 并发 | 128/128 为 200 | 70 / 80 / 80 ms | 101 ms | 4 | 0 |
| 128 个不同账号登录，经 LB | 128/128 为 200；两后端各 64 | 7,076 / 8,010 / 8,095 ms | 8,143 ms | 21 | 19 |
| 128 个无效 JSON，请求先计全局限额 | 128/128 为 400 | 475 / 582 / 593 ms | 609 ms | 21 | 19 |
| 同账号 20 个并发登录，伪造不同 `X-Forwarded-For` | 20/20 为 200；第 21 次为 429 | 321 / 1,026 / 1,059 ms | 1,060 ms | 22 | 14 |

128 账号登录阶段的 PostgreSQL CPU 峰值为 104%，容器内存采样峰值约 242 MiB；两台 Platform CPU 峰值分别为 215% 和 244%，RSS 峰值约 160 MiB 和 156 MiB。无效 JSON 阶段 PostgreSQL CPU 峰值只有 5.8%，但仍出现共享计数行的锁等待。将全局计数从多次往返事务改为单条原子 `UPDATE` 后，无效 JSON 的 p95 从优化前一轮的约 1,001 ms，降至优化后两轮观察的 373–582 ms；运行负载有波动，这不是受控微基准。单账号计数仍严格跨副本生效；另有 30 个并发争抢 20 个全局名额的真实 PG 测试，恰好 20 个成功、10 个拒绝。

探针还将全局计数强制置于配置上限，确认登录返回 429，窗口过期后恢复 200。注入 10,000 条已过期账号窗口后，下一次登录删除了约 10,130 条过期记录，单次 HTTP 延迟为 76 ms，未观察到清理阶段的锁等待；这是单轮 1 万条记录的结果，不代表更大表或持续攻击下的上界。

本轮 128 个登录约 8.1 秒完成，即约 16 次成功登录／秒；另一优化后运行约为 19 次／秒。两台 Platform 的密码哈希 CPU 已很忙，**不能用 100,000 次／分钟的全局拒绝阈值推断两台实例能承载该吞吐量**。该阈值限制总量，目标部署仍需按实际硬件、实例数、入口与持续流量做容量规划和压力测试。锁等待说明并发请求会排队；单条更新降低了无效请求的排队时间，但没有消除共享计数行。此探针不覆盖跨机器网络、真实模型、长时负载或大规模过期窗口。

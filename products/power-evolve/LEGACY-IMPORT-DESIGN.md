# Schema 37 → cloud-native Schema 2 离线导入设计

2026-10-09，Asia/Shanghai。此参考设计供迁移负责人审阅，定义首版可实现的输入、保留与拒绝规则；不表示导入代码、真实旧库导出、系统迁移或恢复验收已经完成。范围由[迁移方案](CLOUD-MIGRATION-PLAN.md)、[M0](TRIAL-CLOUD-MIGRATION-M0.md)和[来源记录](TRIAL-CLOUD-MIGRATION-BASELINE.md)确定。本次只读取仓库源码、DDL、清单与文档，没有访问来源运行数据库、文件根或私有配置，也没有修改共享清单、manifest、生产源码及[原 56 例证据](EMPLOYEE5-HANDOFF.md)。

## 已确认的实现缺口

目标 [database.ts](application/src/platform/database.ts)当前接受 `cloud-native` 家族的版本1、2、3，空库经固定V1和相邻V2／V3 DDL初始化为3；本设计冻结的离线导入目标仍为2，随后通过正常启动器相邻升级至3。旧库、部分库及未来版本被拒绝。当前application包没有Schema37离线导入export或维护Profile；错误信息要求隔离导入，并不提供该生产入口。完整接线与分段产物见[下一版本提案](#下一版本的生产入口与分段产物v2-提案)；本设计不修改普通启动器。

[migration-data-map.json](migration-data-map.json)仍声明 `targetVersion: 1`。来源 37 阶段 DDL 的静态列清点为 77 表、844 列；目标 V1 为 69 表、731 列，V2 为 71 表、742 列。清单映射 67 个来源表中的 724 列，另列出目标 schema 身份的两列；来源映射列均存在，120 个来源列不在映射内。目标列清点与 V2 manifest 的表／列名一致。清单中的 724 条来源字段规则都是笼统的“保留事实并核验 owner 和所选行”，没有定义具体行闭包、状态、JSON 版本、停止证明及物理字节准入。

清单中的 `newTables`只描述 `pe_native_preferences`，未逐列描述其五列，也未覆盖 V2 的 `pe_native_file_receipts`七列和 `pe_native_prompt_inputs`四列。映射中的生成列 `pe_stdio_v2_actions.cloud_execution_id`不能直接写入。目标 manifest 的现有检查只比较表／列名称，不核验列类型、约束、索引、触发器、函数及生成表达式；列名一致不能作为完整兼容证据。

这些是源码审计结论。静态列解析器没有执行 DDL，也没有证明来源数据库实际已达到 Schema 37 或 SQL 对象完全等价。实施前由 M0 拥有者冻结版本 2 的列清单、行规则和导出格式；本设计保持共享清单原文件供其审阅。

## 固定输入与行选择

首版只接受已停止写入的 Schema 37 离线导出包和独立的文件清单。导出由旧版本运维流程生成，导入器只读取脱离运行根的包；不连接旧库、不扫描旧运行目录、不执行包内 SQL、脚本、Profile、任务或技能。包记录来源 schema、匹配代码／镜像／配置标识、导出 cut、schema 对象摘要、逐表行数、主键列表、原始行摘要、逐文件归属／相对路径／大小／摘要／权限及停止证明索引。秘密材料存入受保护的匹配配置备份，公开报告只记录 key ID 和摘要。

导出包的关系数据采用具名表、具名列与参数化插入；整数和 bigint 不经浮点往返，时间保留原值及精度，NULL、空字符串、缺列与 JSON null 分别表达。`json`列另携带数据库 `::text`原文及摘要，`jsonb`保留数据库中的语义值。包版本、重复字段、重复主键、未知表／列、缺失必需字段、超限记录或摘要错误在任何目标写入前拒绝。限制来自具名维护配置，不能靠截断、默默跳行或反序列化默认值通过。

首版迁入所有纳入用户和全局账号／准入事实；Session、Workspace、连接器、技能和执行记录采用 M0 明确的纳入 ID 集合与依赖闭包。关联按 FK、复合 owner 键和 JSON 内标识共同闭合，包括软删除用户、审计 actor、历史配置与凭据版本、已撤销权限、原动作、受理请求和续接。不能从当前 enabled 状态推出历史版本可省略，不能仅按表名或 `state`自动丢弃不合格行。每个来源行归入“原样迁入、显式转换、排除能力留旧备份、纳入但拒绝”之一，四组行数及主键摘要相加必须覆盖导出范围。

来源 Device／Desktop 与 Cloud 共用的 Session、operation、STDIO 或 JSON 记录须按消费者实际类型验证。若纳入记录引用排除实体、出现目标不支持的分派类型，或同一 Session 混有无法完整解释的日志，首版拒绝该纳入闭包并报告标识，由拥有者重新确定纳入集合或完成格式适配。不能删除日志中的几条事件、重排 seq、把 Desktop 改写为 Cloud，或把引用改为 NULL 来满足约束；整个旧记录与相应文件仍由旧版本及匹配备份保留。

## 停止前置与禁止重放

导出前旧 Host、Platform、Scheduler、Cloud Runner、SSH／MCP／STDIO worker、Office 转换器及 Workspace／Home 文件写者均停止。停止证明绑定原执行 ID、Pod UID、Runner／进程实例、挂载代次、dispatch digest 和实际通道；证明内容按拥有者验证。租约到期、无 Agent 心跳、取消请求、撤权、Pod 名消失或 NULL grant 均不能单独证明物理执行已停止。数据库导出与文件复制必须属于同一停止后 cut。

首版拒绝仍可被目标 worker 接管、审批后分派、产生新结果或补续接的纳入记录。需要取消或对账的工作由旧版本真实流程完成后重新导出。导入器不调用网络、Kubernetes、SSH、模型、连接器或 Runner，不 enqueue continuation，不发送业务 `pg_notify`，不发新 grant、start permit 或 dispatch。没有“归档后不会运行”的目标列可供首版安全地保留可接管状态，故不能只在导入进程中关闭 worker 然后照常启动目标。

| 持久记录／消费者 | 首版拒绝状态或条件 | 可保留的结束事实 |
| --- | --- | --- |
| `pe_operations`／[TaskStore](application/src/platform/tasks.ts) | `queued`、`running`；未结束 attempt；活动 Session grant／租约 | `completed`、`failed`，原 input、settings、selection、source、请求 ID、错误及结束时间一致 |
| `pe_cloud_executions`／[Cloud worker](application/src/platform/executions.ts)与 STDIO worker | `queued`、`starting`、`running`、`cancelling`、`uncertain` | `succeeded`、`failed`、`cancelled`；`closed_unknown`仅作为已验证物理停止与正式 closure 的未知结果事实保留，禁止再次执行 |
| `pe_cloud_execution_resolutions`／[resolution worker](application/src/platform/cloud-execution-resolution.ts) | `accepted`、`stopping`、未闭合 `blocked`，缺少精确 stop evidence | 已完成或取消的正式回执；原 final state、stop evidence、continuation ID／queued 标志一致 |
| `pe_connector_actions`／[Connector worker](application/src/platform/connectors.ts) | `pending`、`approved`、`dispatching`、`uncertain` | `rejected`、`succeeded`、`failed`，结果及续接闭包已结算 |
| `pe_mcp_actions`、`pe_mcp_checks`／[MCP](application/src/platform/mcp-actions.ts) | action 为 `pending`、`approved`、`preparing`、`dispatch-intent`、`uncertain`；check 为 `queued`、`running` | 拥有者支持的终态，原 decision、权限版本、catalog、dispatch、结果、错误与续接一致 |
| `pe_ssh_execute_actions`、`pe_ssh_calls`／[SSH](application/src/platform/ssh-calls.ts) | action 为 `pending`、`approved`、`uncertain`；call 为 `accepted`、`preparing`、`ready`、`dispatch-intent`、`running`、`uncertain`；终态 cleanup 尚未完成 | 拒绝／取消／成功／失败事实与原 sealed result；cleanup 已完成且旧 Pod／Runner 不可复用 |
| `pe_stdio_mcp_calls`／[旧 STDIO Cloud worker](application/src/platform/stdio-mcp.ts) | `accepted`、`preparing`、`ready`、`dispatch-intent`、`running`、`uncertain`，cleanup 或结果续接仍待处理 | 已清理的 `succeeded`、`failed`、`cancelled`事实与一次回流 |
| `pe_stdio_v2_actions`及 Cloud execution／[V2 worker](application/src/platform/stdio-v2-worker-store.ts) | action 为 `queued`、`preparing`、`pending`、`approved`、`dispatch-intent`、`running`、`stopping`、`blocked`；关联 execution 为活动／uncertain；停止、结果或 no-start 闭包不成立 | `succeeded`、`failed`、`cancelled`、`rejected`、`expired`也须关联 execution 已结束；rejected／expired 仍可能随活动 execution 被 worker 选择 |
| `pe_office_preview_jobs`／[Office worker](application/src/platform/office-previews.ts) | `queued`、`creating`、`running`、`stopping`、`blocked`；解析 Pod 未停；旧 artifact 来源 | 获授权文件来源的 `succeeded`、`failed`、`cancelled`，缓存与停止证明可核对 |
| `pe_mount_slots`、`pe_sandbox_instances`／[Sandbox](application/src/platform/sandbox.ts) | slot 非 `free`、instance 非 `deleted`，仍可写的挂载／实例、unknown 停止身份 | 已释放 slot、已删除实例的历史代次和合法 snapshot；不得借旧身份创建新 Pod |

此表是首版导入拒绝规则，状态合法性仍由实际消费者和固定 DDL 验证，未知字符串一律拒绝。仅终态不足以通过：原 request digest、结果签名、停止身份、不可变 task、start／no-start 互斥事实及 continuation operation 必须完整一致。历史 `continuation_queued=true`不能重新排队；其原 operation 若仍 queued／running，整个纳入闭包拒绝。无许可启动、dispatch-intent 后未知结果及未完成停止均不伪造成 failed／cancelled／succeeded。首次尚未执行的 queued 任务也不自动接管；若后续需要迁移这类任务，需另行冻结显式首次启动规则和真实回归。

Session grant 必须已在旧拥有者处失效，活动 lease 消失并与停止证明对应。结束记录中的过期 lease owner／until 可保留为历史字段，epoch 与挂载 generation 保持单调；不批量置零或编造结束时间。任何旧 bearer、审批 ticket、upload intent、preparation 或 start permit 都不能在目标重新获得首次动作授权；首版要求其已撤销、过期、消耗或仅关联不可重放的已结束动作，并验证目标实际授权查询不会把它当成有效许可。有效的旧 bearer 摘要必须先由旧账号流程撤销后重新导出，不能只依靠换 Profile 签名 key 假设失效。

## 原生 Session 格式兼容

两端 writer 的 `SESSION_FORMAT_VERSION`均为 V4，但产品 Schema 37 不能代表每条历史 Session 的格式。来源 [session-records.ts](application/src/session-records.ts)的对应旧文件只写严格的 `id/version/createdAt/isSeeded:false` header；目标允许 boolean seed 与可选 `parentSession`，仍拒绝额外 header 字段。目标[原生格式目录](../../packages/session/session-format-catalog/src/index.ts)包含 V0—V4 codec 与完整相邻链；PG 中的逻辑 event 和 JSONL codec 的物理 row 是不同输入。

| 输入 | 首版处理 | 必须保留／核验 |
| --- | --- | --- |
| Schema 37 中合法 V4 PG 逻辑事件、普通未 seed Session | 支持原样保留候选；逐条用目标 `headerSchema`、`parseEvents`和原生 detached restore 验证 | header ID 等于 Session PK；物理 seq 为 `0..event_count-1`且等于 JSON seq；无缺洞、重复、尾部越界；完整事件关系可重建 |
| V4 PG fork／seed／subagent／额外 header 元数据 | 仅在原始导出可证明、完整前缀及父闭包可表达且格式拥有者已批准适配时纳入；首版固定输入不声称覆盖 | parent lineage、inherited cut、seed、origin、delegationDepth、agentPreset、cwd 不得剥离；目标 header 不可表达则拒绝 |
| V0—V3 PG 逻辑记录 | 首版拒绝，等待拥有者提供已验证的逻辑记录桥接／旧 writer 导出适配 | 不把逻辑 event 喂给物理 codec，不把 version 改为 4；转换必须经过原生相邻迁移及完整验证 |
| 脱离运行根的 V0—V4 物理 JSONL generation | 作为单独格式适配候选，通过公开 `sessionFormatCatalog.createRestore`、strict recovery、current validation 与相邻链转换；首版 PG 导入不据此宣称已支持 | 不覆盖、移动或删除旧 generation；校验完整 EOF、继承前缀、父引用及转换后事件坐标映射 |
| 未来版本、坏 header、未知必读 event、损坏／截断前缀 | 在写目标前拒绝 | 仅原生拥有者允许的 `ignorable: true`按其规则读取；仍保留原记录，不能借该标志丢日志 |

V4 `pe_events.event`是 PG `json`；导出原 `event::text`并在参数化 `::json`插入时保持字节原文，解码副本用于验证。其他 `json`列同样处理，不能统一转成 jsonb 或先 JSON.stringify 再写回而改变重复键、转义及数值表示。jsonb 的原文顺序已不属于可保留的数据库事实，只要求其语义等价。原始摘要和逻辑比较分别记录，校验者拒绝目标 JavaScript 消费者无法无损解释的数值或歧义记录。

`event_bytes`按原 EventStore 写入时 `Buffer.byteLength(JSON.stringify(event))`累计的定义核验，不能误用 PG 原 JSON 文本长度替代；V4 无转换时保留原累计值。真正的格式转换必须显式记录旧／新摘要、事件 seq／inherited cut／引用坐标变化，并据目标定义重新计算 count／bytes，不改历史动作的业务 request digest 来掩盖转换。当前 PG 首版没有此类转换适配，遇到不兼容记录即拒绝。

导入后在同一事务内通过[原生 projection 拥有者](application/src/platform/native-projections.ts)从完整已验证事件重建 `session-projections:<id>`，watermark 为 `event_count-1`；这只是纯 fold 和 checkpoint，不激活 Session、不触发任务。非空 Session 若没有 checkpoint，原生 list／snapshot 会拒绝，故不能按清单把整个 native preferences 表永远留空。独立复查 page／snapshot／after 的连续历史、模型／inbox／标题与原生日志一致。

## 身份、配置与新增目标记录

用户 ID、username、password_hash、角色、enabled、软删除、credential version、account revision、审计 actor、bootstrap 和账号 mutation 的请求／结果保持原事实。不得重建用户 ID、把已删除 actor 丢弃、重新选管理员或执行 bootstrap。login window 和全局窗口按同一 cut 保留，不清零尝试计数；全局 singleton/window_since/attempts/tracked_accounts 与实际 account windows 无法闭合则拒绝。Platform 用户身份与官方模型账号分别拥有状态，不迁造官方登录、余额或授权。

保留每个受理 operation 的 settings、技能版本及 MCP／SSH／STDIO 选择 snapshot，不能用目标当前默认配置重算历史输入。MCP／SSH 密文、sealed result、credential key ID、摘要、AAD 所需身份与配置保持匹配。目标必须具备受保护的旧密钥读取能力，或拥有者审核的显式重加密转换；不同 key／AAD 的配置不允许直接复制密文后宣称可恢复。Provider URL、模型／工具目录、Kubernetes namespace、Runner／Converter 镜像和本地／节点/PVC 文件根按具名目标配置核验；新目标不用旧 Pod、端口或写者身份。报告不输出密钥、token、密码 verifier 或用户数据正文。

`pe_native_preferences`的 UI preference 和 session-model intent 初始不存在，保留“没有历史个人选择”的事实，不从共享 Profile 或当前 user settings 生成它们。Session projections 必须按上一节派生；workspace layout 可保持不存在，由[workspace layout 拥有者](application/src/platform/native-workspace-layout.ts)从所选云工作区元数据按当前确定规则读取，不能宣称已保留来源从未持久化的 archived／pinned 顺序。若导出包另有可证明的个人设置，必须增加具名转换规则后才能写入。

`pe_native_prompt_inputs`首版不生成历史行。旧用户 operation 只有 accepted text input，目标 [TaskStore.accept](application/src/platform/tasks.ts)已对无新表记录的重复请求使用原 `input`构造文本内容比较；claim 也允许 nativeContent 缺省。保留原请求 ID／input，独立验证重试不会新增 operation。不能据本文重放任务或把新含附件请求解释成旧文本请求。`pe_native_file_receipts`首版为空；Workspace 上传回执不是原生 Session 附件授权，不能把 `pe_file_mutations`伪造成此表。

历史 Session 中的附件／图像／offload 引用另须校验实际来源、归属、摘要、大小、名称、storage Session 和读取语义。缺少这类证据的纳入 Session 首版拒绝；普通工作区文件照常按文件映射迁入。若后续需要原生附件转换，必须由附件拥有者明确只读历史引用的落盘位置与 receipt／request 关联，不依据文件名或客户端 JSON 生成授权事实。

## 空目标、事务和重复导入

首版只接受专用新建数据库和全新的 owned 文件根；数据库仅有默认 public schema 与 PostgreSQL 必需系统命名空间，没有用户对象。已有非系统 schema、pe_schema、业务行、未知表／view／sequence／函数／type、未声明扩展、附加对象或文件均在写入前拒绝，不能只查 public 表。连接角色、search_path 和必需系统／扩展对象由可信目标维护配置核验；预初始化的 cloud-native 2 空业务库也不属于首版入口。来源版本不是 37、目标已是旧家族／部分 schema／未来 schema，同样拒绝。禁止 UPSERT 合并、TRUNCATE、DROP 清空、恢复进旧库或仅靠行数为零接受部分 DDL。

导入预检为纯读取：冻结完整包，校验源与目标约束、owner、状态、Session、密钥兼容、文件与容量，输出具体可审阅计划和拒绝原因。通过后仅在目标事务内获取与普通初始化相同的 schema advisory lock，重新核验空对象与排他维护状态，用固定 V1＋V2 DDL 建立目标并写入 `pe_schema(family='cloud-native',version=2)`；不调用旧来源初始化、不把旧 `version=37`复制到新家族，也不改 database.ts 的普通启动规则。

按实际 FK 和触发器依赖构造插入顺序；明确可延迟的循环关联在同一事务内成组插入，例如 Cloud execution／STDIO action、当前配置／connection。目标还存在立即 FK 循环：`pe_user_skills.package_version_id`引用 package version，version 的 skill_id 又引用 user skill。固定完整 DDL 建立后逐行 INSERT 无法直接导入这个闭包。负责人审核的具名 DDL 创建阶段计划仅针对真正空的新目标事务，将这两个 Skill FK 及本文末节的单条 STDIO current catalog FK 的固定 ADD CONSTRAINT 语句留到原值插入后创建并全量验证，提交前得到与固定资产相同的全部约束；其他对象和触发器按原定义建立。不得对现有库暂时解除约束，也不把资产拆分成包内任意 SQL。

不可变表与 BEFORE／constraint trigger 保持启用，生成列从 INSERT 列表省略并读取比较；不得设置 `session_replication_role=replica`或关闭触发器来绕过不一致。两阶段创建计划需用 SQL 解析器或审核过的具名固定语句定位实现，不能用分号 split 拆坏函数体；最终复核全部 SQL 对象定义与约束有效性，再提交。未覆盖的立即循环先拒绝并提出拥有者修订，不能用临时 NULL／伪值完成业务事实。

复制文件先写入独立候选 owned root，整根发布以前禁止目标 Profile 启动。SQL 事务只能保证数据库原子性，不能与文件发布形成跨系统事务。数据库失败时仅回滚本次事务及删除有独占 ownership receipt 的本次 staging；绝不清理旧库、旧根或其他试用资源。数据库提交后发布失败时保留候选数据库、文件、完成进度与错误，目标保持不可启动，由运维对同一 owned 候选执行明确恢复或弃置；不自动把它当空目标重导。

独占维护 operation root 中保存 durable 完成回执，包括包 ID／摘要、输入文件摘要、目标标识、逐表／逐文件比较、转换清单、数据库提交与根发布阶段、非重放检查结果。它不是新增业务 schema 表，不能替代空目标检查。重复导入相同或不同包都拒绝已有目标且零业务写入；并发导入必须在共享锁后再次检查，最多一个成功。普通重复启动只运行目标当前 schema 的合法初始化及读取，不重新导入。

目标启动由迁移负责人以后接入具名 `dsh`维护／运行 Profile；不增加独立 SDK argv 或隐式自动启动。先取得离线比对、格式读取与无旧授权／候选任务证据，再在新的隔离 namespace、存储根与端口启动匹配版本验证新意图。恢复／回退以停止后匹配代码、配置、数据库和文件备份为单位，不让旧 launcher 直连新家族，也不通过还原 PG 假设已发生外部副作用被撤销。

## 首批模块与接线前置条件

v3 冻结实现位于 [列及关系清单](application/src/platform/legacy-import-layout.ts)、[包与 JSON 编解码](application/src/platform/legacy-import-codec.ts)、[纯预检](application/src/platform/legacy-import-preflight.ts)、[候选文件根](application/src/platform/legacy-import-storage.ts)、[新库事务写入](application/src/platform/legacy-import-write.ts)、[纯 detached exporter](application/src/platform/legacy-import-export.ts)、[必需 owner 路由](application/src/platform/legacy-import-owners.ts)和[语义引用示例](application/src/platform/legacy-import-owner-references.ts)，专项入口为 [原 87 例](application/tests/employee5-legacy-import.spec.ts)、[MCP 13 例](application/tests/employee5-legacy-import-mcp.spec.ts)和[纯适配接口 24 例](application/tests/employee5-legacy-import-adapters.spec.ts)。普通 database.ts、业务 DDL、生产入口和 Profile 未由本批修改。固定 77 来源表／844 列及 71 目标表／742 列明确列出；来源列属性还应用完整迁移 SQL 的 12 条 SET／DROP NOT NULL，不能以初始 CREATE／ADD COLUMN 属性代替 Schema 37 最终定义。

wire 包固定为 `power-evolve-legacy-offline/1`；必须提供 source.schema=37、固定来源 DDL 摘要、UUID snapshotId、codeId、stoppedAt、cut、全部来源 tables、每行 disposition／完整原值／sha256、四分类 counts、files、cutProof、stops。即使没有数据的表也必须出现；不接受额外字段或 SQL。维护调用方显式配置 maxBundleBytes、maxRows、maxCellBytes、maxJsonDepth、maxJsonNodes、maxFiles、maxFileBytes、maxStorageBytes；超限整体拒绝，不截断。bigint 和微秒时间使用原字符串；json 写回原文，jsonb 做无损语义比较。重复键、数值丢失、文本 UTF-8 损失、非法 JSONB Unicode、来源摘要／计数错误均在预检拒绝。目标 PG clock 再核对 cut 不是未来时间，避免按未来 cut 把当前仍有效的凭据误当作已到期。

`LegacyImportOwners`的 verifyCut、validateRow、references、verifyStopped、verifyFiles 五接口全部必需，且为同步纯验证。references 由所属表的 owner 明确声明 JSON 列、带类型的精确路径、目标 tuple 和 ownership；缺失 owner 拒绝。预检不再按任意 JSON 属性名猜测外键，也不以跳过 inputSchema 绕过校验。三个真实路径示例为 operation.remote_mcp_selection 数组中的工具选择、MCP action.tool，以及 Cloud resolution.binding_snapshot；MCP 示例按原 SDK 类型解析 catalog／configuration 身份，binding 示例按原 storageBinding 类型核对 workspace／space／root_key。历史 snapshot 不被当前可变配置或挂载代次替换。生产拥有者仍必须验证匹配导出／代码／配置／文件 cut、完整 JSON／request digest／key/AAD、原物理停止身份及完整文件快照；任何接口拒绝都阻止计划签发。专项用例使用固定 fixture 和合成停止事实；生产 cut／stop／密钥／文件证据 provider、STDIO／Office／历史附件完整适配仍未完成，接线不得用空函数替代。

预检先检查全部固定唯一键与 FK、跨 owner 和声明的 JSON 语义引用、操作终态、旧凭据／许可、连续原生历史、正式 closed_unknown closure 和 no-start 互斥，再签发冻结计划。Cloud resolution 的 execution_id 没有 SQL FK，模块另核对 execution 的 user、Session、sandbox、Pod、Runner、request digest 和最终状态。写入器只接受当前进程实际签发的计划，使用固定 V1＋V2 资产、普通 schema advisory lock、明确 INSERT 列及参数 cast；两条已审核 Skill FK、STDIO current catalog FK 及 remote MCP current catalog FK 留到原值插入并 SET CONSTRAINTS ALL IMMEDIATE 后按原文创建，再全量验证。生成列不写入，读取原值比对。纯 checkpointNativeProjections 重建 preferences，历史 promptInputs／fileReceipts 不制造。

文件候选使用全新独占根；归属和源／目标 UID/GID 映射显式提供，完整相对路径及所有祖先目录必须出现在 inventory，路径别名与孤立 surrogate 拒绝。只接收已验证的普通文件与目录；当前 symlink、硬链接、ACL／xattr、跨节点/PVC 根的 qualified adapter 尚未完成，均不能据安全拒绝计为兼容能力。Skill 包必须具备完整 manifest、SKILL.md 及逐文件摘要／大小／目录闭包；复制后由原 verifyPublishedSkillPackage 核对完整发布树。真实存在的原 archive.zip 校验来源 archive_digest／archive_size 后放入候选 `legacy-backup/skill-archives/<userId>/<archiveDigest>/archive.zip`，不混入运行包目录；原本没有 ZIP 时不生成。

事务写入后逐行按 PK 独立查询全部目标列，核对 json::text、bigint、精确时间、jsonb、生成列、全部表计数、143 条 FK 的名字／有效性／deferral 与 projection watermark。固定资产指纹保证输入 DDL；完整 pg_catalog 对象定义的独立指纹、连接丢失／COMMIT 不确定／回执发布失败的实测故障矩阵及系统恢复验收仍需补齐。失败前提交路径只回滚本次新库事务、回收具备本次 inode ownership 的新候选；提交不确定或提交后失败保留候选与阶段回执供明确对账。返回的 complete 回执表示本次模块比对完成，未授权运行 Profile 自动启动。

STDIO 当前 catalog 的最短立即 FK 循环为 connection.current_catalog → catalog → configuration → connection；另一条为 catalog → result → action → configuration。permit／preparation 属于有关运行闭包，固定 result.action_id 直接引用 action，不经 permit 的 FK。准确切点为 `pe_stdio_v2_connections_current_catalog`，从 connection `(current_catalog_id,user_id,id,revision)`引用 catalog `(id,user_id,connection_id,config_revision)`；反向约束为 `pe_stdio_v2_configurations_connection_id_user_id_fkey`。v3 经负责人另行批准第四条原始 ADD CONSTRAINT `pe_mcp_remote_catalog`，从 remote connection `(current_catalog_id,user_id)`引用 catalog `(id,user_id)`；反向 catalog.connection_id／user_id FK 保持原定义。只有两 Skill＋一 STDIO＋一 remote MCP 四条具名语句在全新空库事务内延后。全部原值插入后先 SET CONSTRAINTS ALL IMMEDIATE，完成现有 deferred FK／constraint trigger 校验，再按原文创建，最终全部 143 FK 有效且保留原属性。未改 NULL、删除闭环、改共享 DDL、关闭 trigger 或改 replication role；其余立即循环仍报 `unhandled_immediate_foreign_key_cycle`。真实普通角色的两种 catalog 闭环及 Native／STDIO／MCP 消费者读取已通过模块测试，MCP 例另独立核对全部 FK 属性与该条完整定义。

来源合法 json 可包含 `\u0000`或 lone surrogate。owned PG 已确认 json::text 保留原文，但原 PG JSON 提取路径会因 NUL 返回 22P05；读取与投影兼容修复由 root 拥有。v3 仍分别报 `native_json_nul_adapter_missing`／`native_json_surrogate_adapter_missing`，保留整个旧记录及匹配备份。解除拒绝必须基于负责人当前版本全部用户读取路径的合格证据；这些兼容缺口与 V0—V3 PG 逻辑、fork／seed、混合 Desktop、历史附件都不得计为 F20 完成。

`exportLegacyDetached`只接收已经脱离数据库的完整 77 表及原 scalar cells，调用必需纯 reviewRow 审查每一行，包括固定排除能力的行；保留原值、摘要、逐行与逐表四分类审计。owner 只能接受或拒绝，不能自行把行改归 excluded。V0—V3、future、fork／seed、额外 header 和无合格桥接的历史附件归 rejected，原值仍在包中；该拒绝包不能进入预检写入。`createLegacyImportOwners`要求恰好 68 个所选目标表 provider，无缺失、额外表或缺失回调，只负责必需路由。两者没有读取实际来源库、生成 cut／停止证明或完成历史转换，也没有默认生产 provider；正式来源导出与证据采集、维护入口、包导出和 Profile 接线由负责人另行交付。

负责人拥有application子路径导出、源码tsconfig paths、依赖与锁、正式bundle／构建入口及Profile，并分别登记 [migration-data-map](migration-data-map.json)中的来源37、导入目标 `cloud-native/2`与正常运行目标 `cloud-native/3`。当前具名私有Profile已通过公共源码子路径实际启动并消费阶段产物；该证据不覆盖正式bundle和构建产物入口。各段仍须使用所属生产消费者检查，直接helper import不能代替入口验证。

捕获只允许固定只读投影，在 `REPEATABLE READ READ ONLY`事务中读取经过身份核对的离线恢复库；本批工作只能连接自己的新建 fixture。不得连接、停用或写入实际旧生产源。完整77表包括空表、排除能力、生成列和重复行的原始事实；先保留原始数据，再由 prepare 分类。每列使用明确文本投影：json 原 `::text`、jsonb 数据库语义文本、整数／bigint字符串、UTC微秒时间、bytea十六进制和独立NULL。时间 infinity 仍留原始证据，但不自动获准迁入；不以 JavaScript 数字、JSON SQL 提取或归一化过程改变来源事实。catalog 比对包含类型、空值、默认值、生成表达式、约束、索引、触发器和函数，不能以77／844计数或pe_schema=37替代。捕获采用显式配置的有界游标和输出预算；超限报错，完整行数和摘要不能由截断结果生成。

新包采用独立的 `power-evolve-legacy-offline/2`，保留不可变原始表／cell／row digest，另存具名目标派生结果及其原始记录索引，不重新哈希改写后的值冒充原始来源。历史账本记录实际存储类别、writer／header约定、每级相邻转换的新旧坐标、单条展开／派生事件、父子发现事实、inherited cut、目标 count／bytes／projection 和带类型的外部引用重写。外部签名绑定证据原始字节、表／文件摘要和来源身份，可信公钥来自独立受保护输入；签名有效不能代替拥有者核验实际停止、密钥、文件或关系闭包。包中不携带可执行SQL或Profile。

历史桥接使用[维护的格式目录](../../packages/session/session-format-catalog/src/index.ts)及完整0→1→2→3→4相邻链；PG逻辑event与物理JSONL row分开处理。V3→V4需要[明确完整的child facts](../../packages/session/session-format-catalog/src/children.ts)，空数组也必须来源于已核验的完整父子闭包。Schema37当前PG writer只声明普通V4 header，不能从schema版本推断早期PG body等于released JSONL。实际旧header/body样例及其writer约定是PG V0—V3适配的前提。维护的公开API尚未提供通用的来源SQL seq→目标SQL seq账本；适配必须由格式／各引用拥有者给出准确映射，不按JSON属性名猜测，也不改历史业务request digest掩盖坐标变化。

当前[header parser](application/src/session-records.ts)保留可选 `cwd/origin/delegationDepth/agentPreset`等SDK元数据；[Host persistence](application/src/host/persistence.ts)从实际seed marker取得继承前缀。新writer保留普通V4 json原文，并对转换后历史明确重算count／bytes；search按canonical event_bytes核对，PG原文字节仍单独受预算限制。当前真实PG测试验证原生restore、projection、page／snapshot／after／search及新grant下追加完整turn，包含NUL／surrogate／数值原词法、parent lineage和seed cut。实际Host／模型turn及完整系统恢复仍需所属入口证据。

历史附件需要独立的不可变绑定权限记录。来源没有 `pe_native_file_receipts`；当前 [TaskStore grant catalog](application/src/platform/tasks.ts)与 [NativeAttachments byte lookup](application/src/platform/native-attachments.ts)均只读取已绑定的该表回执，因此只复制文件不能使历史附件进入可读catalog或通过read／copy。提案由负责人增加历史绑定消费者：核验当前owner／Session／grant、不可变迁移清单、原持久引用位置、继承lineage、实际对象摘要及storage Session，然后分别用于grant catalog与字节读取；不能生成假的旧upload receipt或requestId。图像保持已规范化的原字节、hash、mediaType／dimensions和原引用类型，offload与请求变体通过其真实消费者验证，不靠file consumer通过代替。

来源附件根按实际原DSH_HOME／Profile和用户分配取证；[维护的本地存储](../../packages/attachment/attachment-local/src/index.ts)与[file store](../../packages/attachment/attachment-local/src/file-store.ts)的canonical object及硬链接alias需作为同一内容对象核对。新适配需证明源／目标root分离、描述符与inode稳定、alias归属及只读权限，并由实际存储消费者读回，不能直接放宽旧storage拒绝或重新规范化图像。Workspace、Home、Skill、Office缓存、ACL／UID／GID／PVC仍使用前文各自拥有者的完整清单与停止后字节cut。

全部68表生产owner必须覆盖所属durable parser、状态／身份／request digest、密钥ID与AAD、物理停止、准确JSON引用和目标消费者。当前router只证明接口齐全，不能提供这些语义。来源真实停止后快照、停止身份回执、匹配密钥、原始历史header/body／父子事实、实际附件根和字节、M0纳入集合及存储部署映射仍是缺失输入；独占PG fixture和合成证据只验证实现，不能把它们标为真实源数据或F20系统完成。

## Original images and image/offload

The v2 image inventory uses the public strict `legacyMigrationImagesInput` parser before signing its file-cut representation. Each declaration identifies the source user, origin Session, source root, original event-row digest, image index and unchanged SDK metadata. The image ledger grants only exact original occurrences and inherited prefixes; it never grants a browser upload receipt or an old request identity. All business files, ordinary attachments and original image objects share the selected count and byte budgets.

Original normalized bytes are descriptor-checked and passed unchanged to the maintained attachment publisher. The maintained reader verifies media type and dimensions; the migration also checks size, digest, file inode and directory identities. Original images now share the selected Platform attachmentRoot: the SDK publishes below userId/storageSessionId/attachments/v1/objects, while ordinary files keep their maintained file-object and alias layout. The existing attachment backup root covers both; the Host derivative cache has its own configuration. Platform reads hold the current account and Session authorization while checking the private ledger and immutable occurrence, and recheck the grant after reading. Host uses an exact native Agent scope key and captured grant; request variants use the maintained cache and encoder without replacing the durable original reference.

`image/offload` is a durable message projection selecting image occurrences, rather than another physical spill object. Current replay uses the public official projection. The schema3 image fixture retained original image events and offload decisions through the actual public maintenance Profile and exercised the SDK reader through a real RuntimeScope and PG adapter. Its ordinary new fork failed because shared command wiring does not yet inherit image permissions. The full Host／Platform Profile, browser image consumer and model request paths remain unverified. Root owns the separate wiring proposals and formal schema4 initialization; schema3 results remain schema3 evidence.

## Retained account metadata

The v2 account owner module validates retained bootstrap, mutation, audit, settings-mutation and plugin-mutation rows without replaying authority changes. Account receipts use the current public parser and must retain their exact actor, target, request and kind, a historical revision no newer than the source account, and matching audit metadata. Password verifiers remain original salted records and apply only to their original mutation category. Bootstrap owner/name/mode must match the retained ledger and audit; later role changes do not cause bootstrap replay to regrant an administrator.

Settings and notes-plugin mutation digests are checked against the original historical result and expected previous revision. Current model grants and enabled choices do not replace historical receipt values or grant new authority. A nonempty Schema37 fixture exercised these five owners through the public maintenance Profile into formal schema4, then read/replayed their metadata through ordinary account, settings, plugin and bootstrap services. This bounded account work leaves the original crypto, files and exact-stop requirements for other retained subsystems intact.

The schema4 fourteen-case run completed with 13 passed, one failed and no skipped cases. Its sole failure was ordinary fork image-permission inheritance, which remains in the shared command wiring proposal. The full run recorded 1,025 source inputs with no before/after drift and no missing imports. Sixteen raw V8 process files were retained; the failing behavior run emitted no coverage acceptance report, and the raw files do not establish a qualified merged child-process report.

## Retained fixed MCP metadata

That fixed-preset batch did not implement generic encrypted remote-MCP owners.

The schema4 fixed MCP fixture passed both new cases through the actual public maintenance Profile and ordinary per-user metadata consumers. [并发目录校验](application/src/platform/legacy-migration-v2-mcp-catalog-races.ts) 为同一原正式连接／authority下每对重叠的成功检查要求唯一原完成顺序和连接读回。先创建的检查可保存自己的不可变目录，但已有更新检查时不会改当前pointer；无论新检查先完成还是后完成，当前pointer最终指向新检查的目录。proof与原created_at、updated_at、catalog_id及原配置／凭据版本配对，最终pointer还与本来源最后一次有发布权的原finish核对；取消／过期不补造finish或撤销既有目录。所有原目录由既有raw descriptor／digest／tool ID及各checkRuns验证，原历史读回和普通TaskStore新接受仍保留原最新目录，不派发远程调用。缺少／重复并发proof、完成身份／时序错配、旧检查覆盖当前pointer及丢失历史目录均拒绝。当前资格覆盖两个worker同时持有同一固定authority的检查以及两种完成顺序；draft并发、同时更换配置／凭据、三worker交错和closure期间另一worker发布目录尚无实际资格证据。

The overlapping-catalog qualifier requires one original completion-order proof and connection readback for every pair of overlapping successful checks under the same formal connection/authority. The older check may retain its immutable catalog but cannot change the current pointer while a newer check exists. Whether the newer check finishes first or last, the final pointer selects its catalog. Proofs bind original created_at, updated_at, catalog_id and configuration/credential revisions. The final pointer also agrees with the last original finish authorized to publish in this source; cancellation/expiry neither invents a finish nor revokes an existing catalog. Existing raw-descriptor/digest/tool-ID and checkRuns validation authenticates every original catalog. Historical reads and a new ordinary TaskStore acceptance retain the original current catalog without dispatching a remote call. Missing/duplicate race proofs, mismatched completion identities/times, older publication replacing the current pointer and lost historical catalogs reject. Actual qualification covers two simultaneous worker-held checks of one fixed authority and both completion orders. Concurrent drafts, simultaneous configuration/credential changes, three-worker interleavings and another worker publishing during closure have no actual qualification evidence yet.
